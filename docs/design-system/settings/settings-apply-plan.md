## Rules for every PR

- NO file-count limit per PR (user decision 2026-11-16: "reset that limit completely"). Do not
  restore a limit. One PR per settings tab (or larger when the files do not conflict). A PR that
  changes a file in the audit baselines (`tools/ui-class-audit/baseline.json` = B1,
  `tools/ui-class-audit/baseline-spacing.json` = B2) lowers its rows. It never raises a row.
- Two lanes in one worktree: only ONE lane edits B1/B2. Other lanes write their row changes in
  their notes, and the coordinator applies them.
- Each PR has its own branch and worktree from `main` when the earlier PR is not merged.
- Settings paths are below `libs/frontend/chat/src/lib/settings/` (short form `S/`). UI pattern paths
  are below `libs/frontend/ui/src/lib/patterns/` (short form `P/`). Most components use inline
  templates, so one component is one `.ts` file plus its spec.
- Keep every `id`, `data-testid`, `aria-label`, role and behavior from `settings-inventory.md` section 6.
  The PR rows list only the hooks that are at risk.
- Lane checks (focused only): `npx jest --config <project>/jest.config.ts --runInBand --coverage=false
--runTestsByPath <specs>`, `npx tsc --noEmit --project <tsconfig>`, `npx eslint <changed files>`.
- Coordinator checks: `npm run verify -- --related -p <projects>`, then `npm run verify -- -t
lint,typecheck -p <projects>`, then `npm run verify -- -t typecheck-templates -p
ptah-extension-webview` (all PRs change templates). Full gate `npm run verify -- -p <projects>`
  before the first push. Projects: `ui` and/or `chat`, plus `ui-class-audit` when B1/B2 change.
- New worktree setup (before any test): from PowerShell run
  `cmd /c mklink /J "<worktree>\node_modules" "<main-checkout>\node_modules"`.
  Reason: `jest.preset.js` maps `marked` to `<worktree>/node_modules/...` with an absolute path.
  Do not copy or install packages. Do not stage the junction. Never delete the junction target.
- Project names must be confirmed with `npx nx show projects` before the first gate (assumption:
  the lib names are `ui` and `chat`).
- Field appearance (user finding F3, 2026-11-16): a settings field that always has a value (number,
  select, saved text) uses `<ptah-field appearance="stacked">` (label above the box). Use the
  default `floating` notch label only for inputs that are empty by default (filter, search,
  new-item forms). Applies to PR 6, 7, 9–15, 17 and later tab PRs.
- No overlap (F1): a hint, a `ptahFieldBeforeHint` value or a notice must never be covered by the
  next field or its label at any width. The row gap of a field grid must hold the full footer.
- Responsive grid (F2): a field grid is driven by the CONTAINER width (`container-type:
inline-size` + `@container`), not the viewport: 1 column narrow, 2 medium, 3 wide. A number field
  must not stretch so far that its value sits far from its label (cap the field width).
- Visual gate before each tab PR push: Electron screenshots at 1440, 1168, 1024 and 784 px, dark
  and light, FULL PAGE (scroll to the end of the tab). Look at each shot for overlap, clipped text
  and column count before the report. Add a spec assertion for F1 where a layout spec can hold it.
