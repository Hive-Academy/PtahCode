# Merged PR task status: root cause

## Path to the uncommitted write

The Electron host starts `startTaskEndHook` during activation. It scans each registered workspace folder at startup and on `TaskIndexService.onDidChangeIndex`; the scan reads `index.list(root)`, accepts valid `in_progress`, `in_review`, or `done` rows, finds a session organization entry with **both** `worktreePath` and `branch`, and passes `mainRoot: root` to `TaskPrReconcilerService.reconcile` (`apps/ptah-electron/src/activation/task-end-hook.activation.ts:78-120,141-142`). The reconciler calls `prs.prStatus(task.mainRoot, task.branch)` (`libs/backend/task-end-hook/src/lib/close-out/task-pr-reconciler.service.ts:107-125`). Electron's port calls `GitInfoService.readPrStatus(mainRoot, branch)`; it requires an exact head branch match and accepts `MERGED` only when the base is `main` (`apps/ptah-electron/src/di/task-end-hook-composition.ts:448-474`). The reader queries `gh pr list --head <branch>` (`libs/backend/vscode-core/src/services/git/github-pr-status.reader.ts:453-460`). There is no GitHub merge event subscription in this path: an open PR is polled every five minutes, with backoff on failure, while startup/index changes trigger scans (`libs/backend/task-end-hook/src/lib/close-out/task-pr-reconciler.service.ts:31-33,48-56,64-75,131-155`). The Electron process and an applicable workspace folder must be open for these timers and listeners; disposal clears them (`apps/ptah-electron/src/activation/task-end-hook.activation.ts:63-72`; `libs/backend/task-end-hook/src/lib/close-out/task-pr-reconciler.service.ts:100-105`).

On `merged`, the reconciler calls `detector.setCarrierStatus(task.mainRoot, task.taskId, 'done')`, then starts close-out (`libs/backend/task-end-hook/src/lib/close-out/task-pr-reconciler.service.ts:77-97`). `setCarrierStatus` joins that root with `.ptah/specs/<id>/task.md`, verifies the real path, replaces the single frontmatter `status:` line, and calls `fs.writeFile`; it has no git commit step (`libs/backend/task-end-hook/src/lib/trigger/task-end-transition-detector.ts:171-190`). Thus the root is the **scanned workspace folder**, normally the main checkout when main is open, but a worktree if that is the registered folder. The parameter name `mainRoot` does not itself resolve or enforce main. The detector's separate main-root resolver belongs to journal observation (`libs/backend/task-end-hook/src/lib/trigger/task-end-transition-detector.ts:435-469`).

## Why merged tasks can remain stale

| Candidate | Finding |
|---|---|
| Owning session must be live | **Refuted as a strict requirement.** The scan uses persisted session organization links, not a live session, and runs at startup (`task-end-hook.activation.ts:94-120,141-142`). **Confirmed dependency:** a link with both branch and worktree path must exist (`:108-112`); no such link means no lookup. |
| Carrier looked up in worktree while merged copy is on main | **Conditional.** The scan and write use the same registered `root` (`task-end-hook.activation.ts:94-95,113-120`; `task-end-transition-detector.ts:171-189`). Opening main reads/writes main; opening only a worktree reads/writes the worktree. There is no automatic main checkout substitution in this status path. |
| Merge by another actor unseen | **Refuted if polling is active and `gh` succeeds.** Status is queried from GitHub by branch, independent of merge actor (`task-pr-reconciler.service.ts:107-125,131-155`). If the host is closed, there is no poll; startup can catch up only if the task and session branch link remain visible (`task-end-hook.activation.ts:94-120,141-142`). |
| Detector stops after worktree removal | **Partly confirmed.** Removing a worktree that is the registered workspace root removes that scan source; the reconciler also lives only until host disposal (`task-end-hook.activation.ts:66-72,94-95,141-142`). A removed *linked* worktree path alone is not checked for existence by the scan (`:108-120`), and PR lookup uses mainRoot plus branch (`task-pr-reconciler.service.ts:111`). |
| `gh`/GitHub auth absent | **Confirmed possible cause, not proven per task.** Failed/invalid/timed-out lookup returns `unknown`; `unknown` only watches `in_review` tasks, while `in_progress` gets no retry timer (`task-pr-reconciler.service.ts:55-57,107-127`). The audit states GitHub CLI lacked authentication (`task-status-audit.md:3`); the historical failure of each of the 40 cannot be attributed individually from code alone. |
| `in_review` required | **Refuted for a successful lookup:** scan includes `in_progress`; merged branch writes `done` unless cancelled (`task-end-hook.activation.ts:98-99`; `task-pr-reconciler.service.ts:77-85`). **Confirmed retry gap:** an `unknown` lookup watches only `in_review` (`:55-57`), so the one `in_progress` task may be missed after a transient auth failure until another scan. |
| PR linking depends on branch name/body | **Branch: confirmed. Body: refuted in this path.** A session organization entry supplies `branch`, `gh` searches by head branch, and the port checks exact head and base `main` (`task-end-hook.activation.ts:108-116`; `github-pr-status.reader.ts:453-460`; `task-end-hook-composition.ts:458-466`). No PR body is read here. |

The common structural cause is that merge discovery is conditional on host uptime, active workspace root, retained session organization link, and a working `gh` lookup. The audit's 40 stale statuses are consistent with these gaps, but the audit does not identify which gate failed for each task (`task-status-audit.md:3-5`).

## Board and durable derived status

`TaskScannerService` reads and parses carriers with `parseTaskFile` (`libs/backend/task-specs/src/lib/task-scanner.service.ts:256-258`); that parser reads YAML `status` and excludes invalid status (`libs/backend/task-specs/src/lib/task-frontmatter.ts:259-276`). `TaskIndexService` rebuilds its SQLite index from the scanner, and its documented write invariant says index rows come from parsed files (`libs/backend/task-specs/src/lib/task-index.service.ts:17-20,805-815`). `tasks:list` returns `index.list(root)` directly (`libs/backend/rpc-handlers/src/lib/handlers/tasks-rpc.handlers.ts:631-645`); the Tasks UI renders `task.status` (`libs/frontend/tasks-ui/src/lib/components/board/task-list.component.ts:681`). A derived `done` should therefore be injected in the host's task read/list projection **after** carrier parsing and before the RPC response, consistently for detail and filters, not written into the index's source-of-truth row. Persist the verified merged PR identity in host SQLite, keyed by repository and task ID; `ITaskCloseOutStore.getCloseOutForTask(repoId, taskId)` already exposes a close-out record with PR identity (`libs/backend/task-end-hook/src/lib/persistence/task-end-store.interface.ts:145-169`), implemented by `SqliteTaskEndStore` (`libs/backend/task-end-hook/src/lib/persistence/sqlite-task-end.store.ts:138,208`). The journal's `journalObservation` records carrier status, so it cannot by itself prove a remote merge when the carrier is stale (`task-end-store.interface.ts:183-195`). A dedicated verified-merge marker or completed close-out identity is safer than inferring done from a journaled `done`.

## Carrier compatibility and recommendation

Other carrier consumers include `TaskWriterService` (`libs/backend/task-specs/src/lib/task-writer.service.ts:793,836,901`), `TaskDoctorService` (`libs/backend/task-specs/src/lib/task-doctor.service.ts:760`), `TaskIndexService` single-file reparse (`libs/backend/task-specs/src/lib/task-index.service.ts:417-426`), and the task-end disposal reader (`libs/backend/task-end-hook/src/lib/dispose/task-spec.reader.ts:42-57`); all use `parseTaskFile`. The detector's writer independently requires exactly one plain `status:` line in YAML frontmatter (`task-end-transition-detector.ts:180-189`). Changing that line's format or semantics would break these readers and the status updater.

**Smallest design:** keep the carrier format and current parser; make a successful merged-PR lookup persist a verified marker in the host SQLite store, then overlay `done` in the host task list/detail projection. Include `in_progress` in unknown-lookup retries, and scan main checkout tasks independently of worktree lifetime and live sessions by retaining a durable task-to-PR branch/number link. Keep the existing `gh` poll as a refresh path and surface lookup failures. **Rejected alternative:** continue writing `status: done` into main `task.md` and auto-commit it. That creates post-merge tracked-file churn and still misses tasks when discovery is gated or `gh` fails; it also changes repository history for a display-state update.
