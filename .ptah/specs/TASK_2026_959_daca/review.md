# Review findings

- **Medium — overlay disappears for explicit worktree reads.** `libs/backend/task-end-hook/src/lib/di/register.ts:58-62` resolves merged IDs only through `detector.cachedRepoId(root)`. That cache is populated for roots processed by the detector; an otherwise valid `worktreePath` supplied to MCP task list/get/check can be a registered worktree the detector has never processed (`libs/backend/vscode-lm-tools/src/lib/code-execution/namespace-builders/tasks-namespace.builder.ts:713-743`). For that root the overlay returns an empty set, so its merged task remains `in_progress`/`in_review` in all three MCP reads. Resolve the repository identity for each requested root, or maintain a stable mapping for registered worktrees.

- **Medium — manual close-out does not refresh the Tasks board.** The overlay is notified only when the reconciler inserts a new row (`libs/backend/task-end-hook/src/lib/close-out/task-pr-reconciler.service.ts:76-81`). The manual close-out path also inserts a row through `TaskCloseOutService.start` (`libs/backend/task-end-hook/src/lib/close-out/task-close-out.service.ts:61-67`), but emits no index change. A board already open with an `in_review` task can therefore keep displaying that status after a merged PR is recorded manually, until some unrelated index event or refresh. Notify the index whenever a close-out identity is first persisted, regardless of caller.

## Checks

`TaskIndexService.list/getDetail` project the overlay before returning status; Tasks RPC and MCP list/get/check use those methods. The PR reconciler no longer writes `task.md`; a closed-unmerged result does not create a close-out row. The merged notification queues at most one extra scan because an existing close-out row suppresses another notification. Lookup failures from a scan are counted and logged once after that scan.
