# Skills appearing in the main checkout

## Answer

**Unintended cross-workspace propagation; moderate confidence for this incident.** Ptah deliberately has a machine-wide skill store and can fan its skills into a workspace, but the current `skillsSh:install` contract defaults to **workspace** scope (`libs/backend/rpc-handlers/src/lib/handlers/skills-sh-rpc.schema.ts:52-64`). The source explicitly calls unselected global skills reaching other workspaces a leak (`libs/backend/harness-sync/src/lib/state/skill-sync-gate.ts:39-47`). The observed copies fit a release-instance reconciliation of shared global skills, but code alone cannot prove the exact trigger or release version.

## Write path and roots

1. The RPC handler takes its active folder from `IWorkspaceProvider.getWorkspaceRoot()` (`libs/backend/rpc-handlers/src/lib/handlers/skills-sh-rpc.handlers.ts:400-419,1045-1055`). It chooses `{ scope: 'workspace', workspaceRoot }` by default, or `{ scope: 'global' }` only when requested. Separately, `HarnessSkillInstallService.installSkills` calls `sourceRoots.install` **without** a location, so harness apply uses the service's global default (`libs/backend/rpc-handlers/src/lib/harness/io/harness-skill-install.service.ts:90-95`; `libs/backend/rpc-handlers/src/lib/skills-sh/skills-sh-source-root.service.ts:282-285`). The incident's exact entry point is unknown.
2. `stageSkillsInstall` runs the skills CLI with the scratch directory as cwd (`libs/backend/rpc-handlers/src/lib/utils/skills-sh-cli.ts:216-240`). The service then moves staged slugs into a source root (`libs/backend/rpc-handlers/src/lib/skills-sh/skills-sh-source-root.service.ts:298-329`). Workspace scope resolves to **that workspace's** `.ptah/plugins/<rootId>`; global scope resolves to `<home>/.ptah/plugins/<rootId>` (`:222-250`). Thus a normal current workspace install in the dev app should not directly write this repository.
3. On install, the RPC calls propagation for its own normalized harness root (`libs/backend/rpc-handlers/src/lib/handlers/skills-sh-rpc.handlers.ts:431-433,658-667,1049-1055`). Propagation refreshes the user layer and reconciles that root (`libs/backend/harness-sync/src/lib/propagation/harness-propagation.service.ts:125-155`). A later release-instance pass over `<repo>` can independently read the same global root: Electron includes global skills.sh plugins in `harnessPluginRoots` (`apps/ptah-electron/src/activation/plugin-activation.ts:345-369`), and the mirror copies their skill directories into `<home>/.ptah/user/skills/<slug>` (`libs/backend/agent-generation/src/lib/services/user-layer/user-layer-mirror.service.ts:2091-2102,2131-2133`; `libs/backend/agent-generation/src/lib/services/user-layer/user-layer-fs-ops.ts:48-49`). The plugin loader also discovers global skills.sh roots (`libs/backend/agent-sdk/src/lib/helpers/plugin-loader.service.ts:1692-1699`). This is a shared-store route, not evidence of a dev process choosing `<repo>` as its active workspace.
4. The release reconciler resolves **its caller's** workspace root, source state and selection (`libs/backend/harness-sync/src/lib/reconciler/harness-reconciler.service.ts:379-403`). The manifest includes user-layer and overlay skills only if that workspace's selection permits them (`libs/backend/harness-sync/src/lib/manifest/harness-manifest.builder.ts:500-540,543-564`). Claude plans `.claude/skills/<slug>` and copies to `join(workspaceRoot, relPath)` (`libs/backend/harness-sync/src/lib/targets/claude-target.ts:79,204-245,491-495`). Codex plans `.agents/skills/<slug>` and copies it under the same workspace root (`libs/backend/harness-sync/src/lib/targets/rival-targets.ts:110-123`; `libs/backend/harness-sync/src/lib/targets/workspace-target.ts:418-429,1040-1047,1124`). The two target writes may occur in separate passes, consistent with the timestamps.

## Isolation, git visibility, and correction

- Dev Electron changes `userData` to `Ptah Dev` and settings to `<home>/.ptah-dev` (`apps/ptah-electron/src/main.ts:69-75`), **but** the skill source service and content download resolve `<home>/.ptah/plugins` (`libs/backend/rpc-handlers/src/lib/skills-sh/skills-sh-source-root.service.ts:217-229`; `libs/backend/platform-core/src/content-download.service.ts:97-100`), while the user-layer mirror uses `<home>/.ptah/user` (`libs/backend/agent-generation/src/lib/services/user-layer/user-layer-fs-ops.ts:48-49`). Those paths are shared across dev and release. `PTAH_SETTINGS_DIR` affects settings resolution (`libs/backend/platform-core/src/file-settings-manager.ts:68-78`), not these paths.
- Current skill sync state is per workspace: an absent mode derives `selected` from already owned manifest slugs, or an empty list (`libs/backend/harness-sync/src/lib/state/skill-sync-gate.ts:35-52,105-122`); explicit `all` permits every eligible global skill (`:209-227`). The historical broad fan-out or an explicit `all` setting explains the copies; a new workspace on current code should not receive them. Harness apply's implicit global install is a separate scope defect if that path was used: pass `{ scope: 'workspace', workspaceRoot }` to `install` and reject absent workspace; pin with a service spec asserting the source-root call and a second-workspace reconciliation spec asserting no copies. The current RPC default and selection gate already implement the corresponding fix for ordinary marketplace installs.
- Git shows the Claude copies because `.gitignore` explicitly re-includes `.claude/skills/**` for project-owned skills (`.gitignore:198-210`); `skills-lock.json` is ignored (`:213`). `.agents/skills` remains ignored by the broad `skills/` rule (`:199`). To hide only these user-installed copies while keeping project skills tracked, add the three exact `.claude/skills/<slug>/` exclusions **after** the re-inclusion, as the existing `stitch-loop` example does (`:245`). A blanket `.claude/skills/` ignore would also hide project-owned skills. Harness gitignore maintenance will not add a blanket rule when a deeper re-inclusion exists (`libs/backend/harness-sync/src/lib/gitignore/gitignore-writer.ts:312-322`).

## Unsettled from code

- Which UI/RPC action installed the three skills, its requested scope, and whether the release app ran the current source version or an older fan-out implementation.
- `<repo>`'s actual `.ptah` skill-selection state and harness manifests at the write time; without those, one cannot distinguish explicit `all`, previously owned slugs, and an older ungated release pass. No root `skills-lock.json` does not settle this because the modern source-root install does not require one.
