# Session handoff routing investigation

## 1. Current implementation

There are two related handoffs. A **chat session handoff** is implemented in `libs/backend/cli-agent-runtime/src/lib/session-children/session-handoff.service.ts`. A **child session succession** is implemented in `session-spawner.service.ts` and `session-child.registry.ts` in the same directory. They use different ID relationships.

For a chat handoff, `SessionHandoffService.guardAndStart` allocates a successor **tab ID** before starting the host session (around lines 380–430). `adoptWork` (567–600) immediately calls `AgentProcessManager.adoptLanes([predecessor tab ID, predecessor SDK ID], successor tab ID)` and reparents each live child, plus each terminal child with a `heldCompletion`, to the successor tab ID. `reparent` clears `parentSdkSessionId` so an old SDK ID cannot remain the recorded owner. `settleAdoption` (610–645) keeps those transfers after successful start or restores them after a failed or timed-out start. This early move allows a lane or child to finish during startup without sending its signal to the retiring session. The spawner stores held completions on child records and `takeHeldCompletions` (1337–1360) drains them by matching the *current* parent IDs. Thus already held child completions move with the child record; no separate report queue is copied. Lane signals follow the lane adoption/settlement logic.

The handoff acknowledgement is `SessionHandoffService.acknowledgeOnce` (215–240), exposed by `session-handoff-ack.tool.ts`. It calls `SessionHandoffAckStore.findByPredecessor`; a miss produces `handoff record missing`. It authorizes the caller against the recorded successor tab or SDK ID before closing the predecessor. The store (`session-handoff-ack.store.ts`) persists both predecessor and successor tab/SDK IDs, handoff path, workspace, and close state under `ptah.handoffAcknowledgements`. It serializes operations, validates records with Zod, and retains at most 200 completed records. This is an acknowledgement record, not currently a general request router.

After successful start, `guardAndStart` records that acknowledgement edge (around 425–455). The successor SDK ID can arrive later through `onSessionIdResolved` (797–820); the store is patched when it does. `SessionHandoffChainStore` separately persists SDK-ID-to-SDK-ID edges in workspace state (`ptah.handoffChain`, cap 256). Its `read` API returns the connected component root-first, not a direct latest-successor lookup. The chain only receives a link once both real SDK IDs are available. `SessionMetadataStore` and `SqliteSessionRecordRepository` are session metadata persistence: the SQLite repository's `get(sessionId)` is an exact primary-key lookup. Neither is used by `SessionSpawnerService` to route these calls.

For child succession, `SessionChildRegistry` stores records by child tab ID with a separate SDK-ID index. `succeed` (454–496) leaves the predecessor as terminal with `succeededBy` and creates a successor with `succeeds`; `resolveLatest` (527–541) follows up to 64 links and guards against cycles. `SessionSpawnerService.resolveOwned` (about 1920–1970) first fetches the requested child and checks its recorded parent against the caller tab and SDK IDs; only **after ownership passes** does it follow `succeededBy`. `send`, `read`, and explicit `status` use this helper. `stop` requires `followHandoff: true` before targeting the successor. The no-ID `status` path (1051–1075) directly lists `registry.childrenOf([caller, sdkIdOf(caller)])` and pending children. The MCP status tool is a wrapper over this spawner result; the `not-a-child-of-caller` refusal comes from `resolveOwned`.

## 2. Gap

An explicit **old child ID** is already followed to its latest child successor for `send`, `read`, and `status`, provided the caller still owns the predecessor. The missing route is an **old parent/caller session ID** after `ptah_session_handoff`. `adoptWork` changes each child and lane owner to the successor tab ID, but `SessionSpawnerService.status`, `resolveOwned`, `takeHeldCompletions`, pending lookup, and related ownership checks only expand a caller to its own tab/SDK pair. They do not consult the chat handoff acknowledgement or chain. Consequently a status/list call from the old ID sees no adopted children, an explicit child lookup can return `not-a-child-of-caller`, and held completions are drained only for the new owner. The acknowledgement record proves the relationship but is only queried by the ack flow. The SDK chain supports lineage display but has no request-resolution API, cannot cover a successor whose SDK ID is still pending, and cannot map tab IDs by itself.

This distinction matters: changing `SessionChildRegistry.resolveLatest` alone would not fix parent routing, because it follows *child* `succeededBy` links. Nor should ownership checks be removed: a foreign caller must still receive `not-a-child-of-caller`.

The child registry is host-memory state and prunes ended records, so child aliases have a host-lifetime limit. The acknowledgement and chain stores have different retention and scope. A durable old-parent routing guarantee after restart would need an explicit retention/scope decision; the current live child/held-completion state itself is not restored by the SQLite session-record repository.

## 3. Where the fix should go

* `session-handoff.service.ts`: publish a predecessor tab/SDK → successor tab alias only for a **kept** start, using the IDs already captured for adoption; discard it on rollback. Continue updating the alias when the successor SDK ID resolves. Keep ack authorization independent.
* A small shared resolver/store in `session-children` (or a carefully extended `SessionHandoffAckStore` plus a synchronous in-memory index): resolve either tab or SDK ID through successive chat handoffs, with a hop bound/cycle guard. The existing ack record is the durable mapping source if restart-time resolution is required, but its current async read API cannot be dropped directly into synchronous `status`.
* `session-spawner.service.ts`: apply that resolver to the **caller** before `resolveOwned`, `ownedPending`, no-ID `status`, `takeHeldCompletions`, clear/list operations, and other ownership-sensitive paths. Keep the requested child ID's existing `resolveLatest` behavior and stop's explicit follow opt-in. Keep refusal behavior for unrelated callers.
* `session-child.registry.ts`: likely no new child succession algorithm is needed; its `reparent`, `childrenOf`, and `resolveLatest` already model the required child transfer and child-ID forwarding. Change it only if the shared alias lives there, which would mix parent chat handoffs with child succession.
* Tests: extend `session-handoff.service.spec.ts`, `session-spawner.service.spec.ts`, and, if the resolver/store changes, its focused spec. Cover the MCP wrapper only if its result shape or async contract changes.

## 4. Proposed approach and verification

1. Introduce a typed session-ID resolver shared by handoff and spawner. Record both predecessor IDs as aliases of the successor tab ID **after** the start is kept. Resolution should support multi-hop A→B→C, both tab and SDK spellings, a maximum hop count, cycle detection, and no mapping for failed/late starts. A later SDK binding can add the successor SDK spelling. Keep workspace scope if backed by the persisted ack store.
2. Normalize the caller ID at the spawner entry/ownership boundary, then use the resolved tab ID and its current SDK ID for owner matching and pending/held-completion enumeration. This preserves strict child ownership while allowing the authorized predecessor identity to reach adopted work. Ensure all entry points that call `takeHeldCompletions` use the same normalization, so a completion is delivered once. Do not rewrite child ownership back to the predecessor.
3. Keep `succeededBy` resolution for requested child IDs in `resolveOwned`, and preserve the special `stop` opt-in. Explicitly define whether a historical status query should show the predecessor or successor; current explicit status follows the successor, while the unfiltered list enumerates children of the caller and can include terminal history.
4. Test a kept handoff with live child, starting child, terminal child holding a completion, and active lane; query using both old tab and SDK IDs and verify the successor owns and drains each exactly once. Test a second handoff hop, unknown/foreign callers, failed/timed-out start rollback, and successor SDK ID arriving after startup. Test child-ID forwarding and stop semantics separately so the two routing layers stay distinct.

Verification for an implementation should use focused Jest specs, TypeScript `tsc` for the changed project, and ESLint for changed files. No implementation was made in this investigation; verification here was source inspection and cross-checking existing succession/handoff specs. No `nx`, build, or workspace-wide command was run.
