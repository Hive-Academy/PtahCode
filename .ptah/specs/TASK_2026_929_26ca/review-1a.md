# Review batch 1a: button family (branch feat/ui-button-family)

Read-only review. No build, test, serve or git state change was run. Everything below is from source, `git diff HEAD`, installed `node_modules` sources and CSS. Nothing was rendered. Where a finding needs a render, it says so.
Ptah tools (`ptah_*`) were not called; native `rg`, `git show` and file reads were the fallback. No skill was loaded: this is a review, not UI authoring.

## Verdict

CHANGES REQUIRED: zero pixel holds, but the icon button misses the `type="button"` default and the tooltip fails WCAG 1.4.13 dismissal and can hide behind top-layer dialogs.

## Findings

1. **major** `libs/frontend/ui/src/lib/button/icon-button.directive.ts:22-24` vs `button.directive.ts:28-36`. The icon button constructor only calls `blockBusyActivation`. It does not default `type="button"`. A `<button ptahIconButton label="x">` inside a `<form>` is a submit button. The two directives promise the same host behavior and the context says the logic is shared (`button-host.ts`), but this part was copied into one directive only. Fix: move the default into `button-host.ts` (for example `defaultButtonType()` next to `blockBusyActivation`) and call it from both constructors. Add a spec (`<button ptahIconButton label="x">` has `type` `button`, explicit `type="submit"` is kept).

2. **major** `libs/frontend/ui/src/lib/button/tooltip.directive.ts:15-21` (WCAG 1.4.13 Content on Hover or Focus).
   - Dismissible: `(keydown.escape)` is bound on the host element, so Escape closes the tooltip only while the host has keyboard focus. A tooltip opened by pointer hover cannot be dismissed with Escape. Fix: subscribe to `overlayRef.keydownEvents()` (CDK dispatches body keydown to attached overlays) or add a document-level Escape listener while open; hide on Escape and call `preventDefault` plus `stopPropagation` only when a tooltip was actually open, so Escape does not also close a surrounding dialog.
   - Hoverable: `(pointerleave)` on the host hides at once (line 17), so the pointer can never travel onto the panel. A focus-only tooltip fails nothing here, a hover tooltip does. Fix: on `pointerleave` start a short grace timer (about 100 ms) that `pointerenter` on the panel (or the host) cancels; drop `pointer-events-none` (see 4) so the panel can hold the hover.
   - Persistent: passes (stays until pointer leave, blur or Escape, no timeout).
   If the team accepts hover-only tooltips as a documented 1.4.13 exception, record that in `context.md`; today the code is not conformant.

3. **major (needs a render to confirm)** `libs/frontend/ui/src/lib/button/tooltip.directive.ts:59-62`. The overlay is created in the CDK overlay container (a `body` child, `z-index: 1000` from `apps/ptah-extension-webview/src/styles.css:10` -> `@angular/cdk/overlay-prebuilt.css:9-11`). A `z-index` cannot beat the browser top layer. The lib already knows this: `libs/frontend/ui/src/lib/native/drawer/native-drawer.component.ts:69,130` uses `popover="manual"`, `libs/frontend/ui/src/lib/native/modal/native-modal.component.ts:7` uses `<dialog>` with `showModal()`, and `apps/ptah-electron-e2e/src/specs/git/hunk-revert-top-layer.spec.ts` documents the same class of bug. An icon button inside a native modal or drawer (the typical close or action button) would show a tooltip that is painted under the dialog. CDK 22.2.6 supports `usePopover` (`node_modules/@angular/cdk/types/_overlay-module-chunk.d.ts:297`, `withPopoverLocation` at :619). Fix: `this.overlay.create({ usePopover: true, ... })` and `position.withPopoverLocation('inline')` (or `'global'`); add a spec asserting the pane is a popover. Verify in a Playwright or Electron run with an icon button in `ptah-native-modal`.

4. **minor** `libs/frontend/ui/src/lib/button/tooltip-panel.component.ts:12` (`pointer-events-none` on the component host). The CDK pane wrapping it has `pointer-events: auto` (`@angular/cdk/overlay-prebuilt.css:23-25`), and the pane is exactly as large as the panel plus its `my-ptah-label` margin. So the class does not make the tooltip click-through; the pane still takes the pointer and covers neighbouring controls. Fix: pass `panelClass: 'pointer-events-none'` in `overlay.create` (only if finding 2 keeps the tooltip non-hoverable), otherwise remove the class and own the hover behavior from finding 2.

5. **minor** `libs/frontend/ui/src/lib/button/tooltip.directive.ts:69-77` (double announcement). The icon button sets `aria-label` = `label` and the tooltip adds `aria-describedby` pointing at a panel with the same text, so a screen reader announces the name twice. Fix: when the host `aria-label` (or text content) trims to the same string as the tooltip text, do not add `aria-describedby`. Keep `aria-describedby` for a plain `[ptahTooltip]` that adds information. The merge logic itself is sound (`aria-describedby` tokens split, own id appended on show, own id removed on hide, attribute removed when empty, lines 69-90). One edge: a host `[attr.aria-describedby]` binding that re-renders while the tooltip is open overwrites the appended id.

6. **minor** `libs/frontend/ui/src/lib/button/tooltip.directive.ts:66-67`. `text` is pushed to the panel once at show time. If `label` changes while open (Copy -> Copied is the usual case) `aria-label` updates and the tooltip stays stale; if it becomes empty the panel stays open. Fix: keep the `ComponentRef`, and in the constructor `effect(() => ref?.setInput('text', this.ptahTooltip()))` (hide on empty). Spec it.

7. **minor** `libs/frontend/ui/src/lib/button/tooltip.directive.ts:16-19`. Interaction details:
   - `(focus)` calls `show()` for any focus, including the focus a mouse click gives. The tooltip then appears immediately after each click and stays until blur or pointer leave, on top of whatever the click opened. Use keyboard-modality focus only (`host.matches(':focus-visible')`; jsdom support must be checked, otherwise track the last input modality).
   - Focus vs pointer: a focused control loses its tooltip when the pointer merely crosses it (`pointerleave` -> `hide()`). For a keyboard user with a stray mouse this is acceptable but not good; better: remember what opened it and let `pointerleave` close only a pointer-opened tooltip, or keep it open while `document.activeElement === host` and focus-visible.
   - Touch: `pointerenter` also fires for touch. A press longer than 250 ms flashes a tooltip that `pointerleave` removes on lift. Ignore `event.pointerType === 'touch'` in `scheduleShow`. Electron is first, so low priority.
   - Repeated show is safe: `if (this.overlayRef ...) return` (line 41), the timer is cleared in `show` and `scheduleShow` (lines 36, 40).
   - Leak check passes: `destroyRef.onDestroy(() => this.hide())` (line 33) clears the timer and disposes the overlay. The `ComponentRef` dies with `dispose()`.

8. **minor** `libs/frontend/ui/src/lib/button/index.ts:1-4`, `button-host.ts:2-4`. The public inputs are typed `ButtonVariant` and `ButtonSize`, but `button-host.ts` is not exported from `index.ts` (correctly, it also holds helpers). Consumers cannot type a wrapper `input<ButtonVariant>()` from `@ptah-extension/ui`. Fix: move the two type aliases to `button.types.ts` and add `export * from './button.types'` to `button/index.ts`. Also consider the unprefixed names against the `Ptah*` convention. `PtahTooltipPanelComponent` is exported publicly (`index.ts:4`) although only the directive creates it; drop the export unless a consumer needs it. `scheduleShow`, `show`, `hide` are public only to be called from host bindings; `protected` is enough.

9. **minor** Specs (see section "Specs" below for the list). The main gap: no spec fails on a zero-pixel regression, because class checks only use `classList.contains`.

10. **minor** `libs/frontend/ui/src/lib/button/button.directive.ts:17`, `icon-button.directive.ts:12`. `host: buttonHost()` and `{ ...buttonHost(true), ... }` are function calls in a decorator. The Angular AOT compiler only evaluates a function whose body is a single `return` (default parameters are supported: `@angular/compiler-cli/bundles/chunk-GY2QRHJA.js:2853`), and `buttonHost` currently fits. Jest runs JIT, so the passed tests do not prove the AOT build. This is the only `host: fn()` in the repo. Fix: add a comment on `buttonHost` ("single `return` of an object literal, required by the AOT static evaluator, no local statements") and let the batch gate include one AOT compile of the webview app (not run here by instruction).

11. **minor** Smaller points:
    - `libs/frontend/ui/src/lib/button/tooltip.directive.ts:37`: raw `250` delay; name it (`const SHOW_DELAY_MS = 250`) near the id counter.
    - `libs/frontend/ui/src/lib/button/button-host.ts:34`: the busy block is bound to `click` only. For `a[ptahButton]`, `auxclick` (middle click) is not blocked and opens the link. Add `auxclick` to the blocked set (the same listener, a second `addEventListener`/remove).

### 2. Behavior
- Static `type="submit"`: Angular writes template attributes at element creation, before the directive constructor, so `hasAttribute('type')` is true and the type is kept (`button.directive.spec.ts:59-67` asserts it). With bound `[attr.type]="x()"` or `[type]="x()"` the binding runs after the constructor and overwrites the `button` default; safe except a null/undefined value (finding 11).
- Existing callers in a `<form>` with no explicit type: none. The two submit buttons (`review-finding-card.component.ts:49,52`) are explicit `type="submit"`. The default only affects future code.
- Busy click blocking: capture listener on the host, `preventDefault` + `stopImmediatePropagation`, removed on destroy (`button-host.ts:29-35`). Angular `(click)` handlers on the same element do not run. For an anchor, Enter on a focused link raises a synthetic `click`, which the capture listener cancels, so keyboard navigation is blocked as well as mouse and Ctrl+click (middle click is the exception, finding 11). The busy button keeps focus (not `disabled`).
- `aria-disabled="true"` on `a[href]`: valid (supported on the link role) and matches the button treatment. `aria-busy` is set too.

### 3. Icon button + tooltip composition
- Angular rule (runtime check in `node_modules/@angular/core/fesm2022/_debug_node-chunk.mjs:10886-10897`, error NG0312): for `hostDirectives` with `inputs: ['ptahTooltip: label']` the host-directive input is exposed under the alias `label`. The only name check is within that host directive: it throws if the alias equals a different public input of the same host directive (`PtahTooltipDirective` has only `ptahTooltip`, so `label` is free) or if the source name does not exist. A host-directive alias that equals an input of the host (`PtahIconButtonDirective.label`) is not a collision: Angular assigns a template binding to every directive on the element that exposes that public name, so both `label` inputs receive the value.
- Static `label="x"` is set on both inputs at creation; `[label]="x()"` is set on both on each change. The spec covers the static case only (`icon-button.directive.spec.ts:7,16,20-22`); the bound case is not covered (finding 9). `input.required` on both is satisfied by the single `label` binding. `[ptahTooltip]` is never matched by selector on the icon button because host directives are not selector-matched, but writing a separate `ptahTooltip` on an icon button would add a second copy (duplicate-directive error); the lib should not allow it and nothing does.

Other app stacking contexts use z-index 30 to 40 (`styles.css:3251-3276`), so a normal (non-top-layer) tooltip is above them. Top layer is finding 3.
