# Research report

## Question

For C2–C4, FA2 and Handoff item 2, which lanes expose the model and effort they actually use, which accept a per-spawn effort, and what does each discovery source expose or cache? Scope is the checked-out Electron-first lane paths, including shared host code. Timings below are configured limits or cache ages. No live CLI or latency measurements were run.

## Findings

1. **Current outcome and spawn boundary.** All rows use `info.model ?? 'lane-default'` in Runtime `cli-agents/lane-completion-outcome.ts:62`. C4 has no effort column. The common manager resolves spawn effort before handing it to an adapter (Runtime `cli-agents/agent-process-manager.service.ts:1405,1567`). The precedence walks request, settings, inherited chat, role default and chat fallback. Blank/unsupported values let precedence continue. Cursor and OpenCode have no effort mapper. Codex, Copilot and Grok map minimal to low and max to xhigh. Antigravity forwards its own scale to its profile, and Pi keeps its separate thinking scale. An attempt, a mapped value sent to the CLI, and the CLI-reported current/effective value are distinct evidence. Runtime `cli-agents/lane-spawn-policy.ts:310–418,422–497`.

2. **Claude and Ptah CLI share SDK evidence, with different effort gates.** The init segment displays the SDK's selected session model. An assistant frame identifies a model used on that message. The result is cumulative and can include auxiliary or subagent calls. The stream loop differences per-model totals and emits a single usage model only when one model has a delta. Init is evidence of session selection and assistant output is direct turn evidence. For system Claude, the explicit-model effort check requires a positive native metadata entry. Without an explicit model it can offer any of its five spawn values to the SDK. The live-turn `applyFlagSettings` path maps max to xhigh, separately from spawn. For Ptah CLI, the SDK call is also used through compatible gateways. A returned alias may establish the SDK-visible model while leaving the downstream model unresolved. This applies regardless of whether local tier or a raw override chose the requested model. SDK native catalog ordinary reads share cached or pending results and can restore persisted entries up to 30 days old. The 1 h age bound applies to the separate live-only memory read. The 5 min API cache is separate from ordinary native catalog reads. Runtime `ptah-cli/helpers/ptah-cli-stream-loop.service.ts:514–527,854–869,943–995`, `claude/claude-sdk-lane-runner.ts:344–346,542–594`. Adapters `claude-cli.adapter.ts:572–615`. SDK `helpers/sdk-model-service.ts:244–259,328,865–895,1111–1138`.

3. **Codex has session-level wire evidence for both fields.** The checked-in protocol defines a model and nullable `reasoningEffort` on both `ThreadStartResponse` and `ThreadResumeResponse`. The native enum is broader than Ptah's lane allowlist. `CodexContext` consumes returned model at thread binding, and consumes thread settings updates. Its turn-start code can also seed the translator from its own outgoing `params.model`. Usage evidence draws from that translator, so a model string on a usage segment alone does not prove which source won. The same context serializes effort into outgoing requests and exposes local settings to the lane catalog. The session response or settings event can establish server-reported effort when present. Turn-level effective effort remains unproven by the current lane usage events. Native `model/list` preserves per-model supported/default efforts internally, while the lane helper computes a union for its effort picker. Codex runtime `protocol/codex-app-server-protocol.schema.json:18585,24513–24616,25255–25331`, `codex-context.ts:340–366,539–544,1023–1056,1468–1475`, `codex-event-translator.ts:373–381`. Adapters `codex/codex-lane-events.ts:222–247`, `codex/codex-app-server-lane-models.ts:37–43`.

4. **ACP manages current session settings with provenance caveats.** Grok's recorded `session/new` reply includes `models.currentModelId` and reasoning metadata. AgY's session model reply is parsed via the same code. The runner reads advertised config after setup, successful writes and `config_option_update`, and validates effort after model selection because that can change the available options. Its `sessionModel()` usage fallback prefers acknowledged/requested model over advertised `currentValue`, and does not consult the marked current model in `advertisedModels`. A successful binding confirms acceptance of the configured ID. A returned current model or native model-bearing usage is stronger evidence of resolution. Grok's parsed `response_completed` contributes token counts only. Antigravity's legacy-ID reconciliation picks a currently listed ID before sending it. Neither heuristic nor model suffix gives independent evidence of a downstream model call. ACP `__fixtures__/grok-p3-set-model-unknown.ndjson:13`, `acp-session-helpers.ts:178–191`, `acp-session-runtime.ts:600–603,1010–1099,1317–1319,1648,1818–1825`, `profiles/grok-acp-profile.ts:89–111`. Adapters `antigravity-cli.adapter.ts:152–191`.

5. **Cursor, OpenCode and Pi need provenance at the point of observation.** Cursor has a direct SDK result model even if usage is absent, but its structured usage emission depends on counters and initializes to `cursor/unknown`. OpenCode promotes a runtime model only on paired provider/model fields and otherwise leaves its request-initialized value. Pi uses a runtime assistant ID when valid token usage accompanies it and otherwise leaves its initial requested value. Pi already requests state, and upstream RPC includes model and thinking-level state. Current Pi source can report available thinking levels for the active model through RPC, while Ptah's text parser does not read those capabilities. Current OpenCode docs describe model selection using a model-specific `#variant` and an error for unknown variants. That is separate from the Ptah adapter's generic effort input. Adapters `cursor-cli.adapter.ts:510–547`, `opencode-cli.adapter.ts:963,1166–1179`, `pi-cli.adapter.ts:520–526,563–585,786–791`. [Pi RPC server source](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/modes/rpc/rpc-mode.ts) · [Pi RPC client source](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/modes/rpc/rpc-client.ts) · [OpenCode model variants](https://opencode.ai/docs/models/)

6. **Copilot has model evidence, with a version-sensitive effort interface.** Its parser emits the model from the CLI session event and from assistant usage. Mixed usage is explicitly marked `copilot/multi-model`, and missing model becomes `copilot/unknown`. The installed-binary adapter in this tree emits `--effort`. Current vendor docs advertise `--reasoning-effort` and a broader model-specific scale including none, minimal and max. They establish upstream capabilities, with the repository defining the scale and flag Ptah currently attempts. Installed version acceptance of the flag and individual model levels is unverified. Adapters `copilot-sdk.adapter.ts:60,378–385,528–550,671–674,825–855`. [GitHub Copilot CLI configuration reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference)

7. **A discovery deadline and a source cache solve different problems.** System routing constructs ID/provenance entries from the CLI listing service, which first waits on detection and then tries additional Codex and Copilot sources. The routing gather race in C2 is 2 s and can lose to sources with longer internal budgets. Outer routing lacks a durable system catalog snapshot. Source caches still apply as shown in the matrix. Antigravity's 10 min ID cache is for spawn reconciliation and a listing call still probes. Ptah CLI shares only pending discovery at the routing adapter boundary. The provider service separately caches successful model lists and can read persisted per-credential data. None of those paths gets per-model effort support through the routing contract, even where richer upstream data exists. RPC `cli-model-list.service.ts:53–101`, `lane-model-listing.adapter.ts:128–162,236–250,294–340`. Auth `provider-models.service.ts:482–493,550–585`. See C2 for `routing-constants.ts:169` and `pipeline/gather.ts:501–537`.

## Decision supported

- **Claude and Ptah CLI providers** can promise the requested model on every row and an SDK-reported model where the relevant stream contains an attributable ID. Keep unresolved for absent evidence, opaque provider aliases when identifying the downstream model, or ambiguous multi-model usage. Spawn effort is request/config evidence. Applied effort remains unknown.
- **Codex** can promise app-server-reported session model and, when present, native session-reported effort. That capability exists on the wire. Current lane completion does not retain it and outgoing turn overrides can affect attribution. Without an applicable native observation, keep the requested model and mark resolution unknown.
- **Grok and Antigravity** can promise the ACP-reported session model where the agent supplies current model state. Both can return current config information where advertised. Current usage fallback alone does not establish resolution for a bound model. Keep the request and unresolved status when native model state is absent or only the requested value survived the adapter. Keep effective effort unknown when the agent supplies no usable current effort. AGY's effort-suffixed model IDs should be treated as vendor IDs with their own provenance.
- **Copilot and Cursor** can promise a resolved model when a direct native model report is present and attributable. Keep unresolved when it is missing or model attribution is ambiguous. Copilot can record requested effort. Cursor has no per-spawn effort transport and neither lane reports effective effort through the current integration.
- **OpenCode and Pi** can promise observed model where the corresponding native model fields survive parsing. Both require request-plus-unresolved fallback for runs that only carry adapter-seeded model telemetry. OpenCode has no effort input through the adapter. Pi can record requested thinking level, and current upstream RPC can report session thinking state, which Ptah currently discards.

There is no lane-wide basis to declare every run of a listed adapter unresolved. The unresolved-only cases are runs where direct evidence is missing, ambiguous, or insufficient for the identity being scored. In particular, compatible Ptah CLI gateways can stay unresolved at the downstream-provider level even with a valid SDK-visible model ID. None of the current outcome rows records the provenance needed to distinguish these cases.

## Unknowns

- Actual cold/warm latency distributions and installed binary version behavior remain unmeasured. The smallest follow-up is to time only model discovery with representative versions and cold/warm state, and separately replay existing captures for attribution. No vendor CLI was launched for this report.
- On current supported installations, validate Copilot's legacy flag and Pi's version-specific state payload. For ACP, validate availability and meaning of effort `currentValue` after binding, especially on resumed sessions or model-suffixed Antigravity IDs. A no-inference session state capture would settle availability.
- For supported Ptah CLI gateways, which upstream aliases are canonical and which are rewritten is provider-specific. A sanitized SDK init/assistant/result capture paired with provider-side attribution can settle a particular provider/model combination.
- Ptah symbol search had an empty index. Source searches used native `rg` and targeted line reads, alongside Ptah AST analysis. Skill discovery found the orchestration skill, and the workspace copy supplied the research-phase guidance. Ptah web search lacked a configured provider key, so vendor questions used the native web tool and primary vendor sources.
