# Follow-up queue: reason-less refusal investigation

## Summary

- **CONFIRMED:** The exact notice has two frontend callers: an unsuccessful `chat:continue` submission and a `failed` state push with an absent/blank reason (`follow-up-queue.service.ts:195-197,401-440,481-490`).
- **CONFIRMED:** Backend `chat:continue` and Electron IPC preserve error text, but the frontend discards it (`chat-session.service.ts:1983-2011`; `ipc-bridge.ts:584-603`; `follow-up-queue.service.ts:416-420,440`).
- **POSSIBLE, most probable for the reported active turn:** a submission rejection or timeout during backend admission, misreported as an unexplained queue failure. No runtime trace identifies which rejection occurred.
- A failed push without a reason is contractually possible, but the inspected Claude/Codex queue failure emitters provide reasons.

## Code paths

1. **Frontend admission and RPC.** `enqueue()` captures the tab's then-current `claudeSessionId`, creates a client ID, and pumps immediately (`libs/frontend/chat/src/lib/services/chat-store/follow-up-queue.service.ts:129-163,366-388`). `submit()` passes the captured tab/session to `MessageSenderService.submitQueuedFollowUp()` (`:401-414`), which calls `chat:continue` with `queueIntent: 'next-turn'`, client ID and Electron `ptahUiFence` (`libs/frontend/chat/src/lib/services/message-sender.service.ts:785-815`). The method map is `libs/shared/src/lib/types/rpc.types.ts:1118`; parameters/result and optional queue state/error are `libs/shared/src/lib/types/rpc/rpc-chat.types.ts:168-243`. `ChatRpcHandlers` parses params then calls `ChatSessionService.continueSession()` (`libs/backend/rpc-handlers/src/lib/handlers/chat-rpc.handlers.ts:297-303`).
2. **Every unsuccessful submission becomes the exact reason-less notice. CONFIRMED.** `submit()` accepts only `result.success && data?.success !== false && data?.cancelled !== true`; all other replies and caught exceptions keep `outcome='failed'`, then call `fail(clientMessageId)` without a reason (`follow-up-queue.service.ts:405-421,425-443`). This includes backend `{success:false,error,errorCode}` (tab ownership mismatch, invalid params, account/auth refusal, resume failure, SDK error, follow-up ID conflict), `{cancelled:true}` after Stop, transport rejection, and renderer RPC timeout. These are code paths, not evidence they occurred in this incident. The mismatch check throws `SESSION_NOT_FOUND` when a live registration or prior binding belongs to another tab (`libs/backend/rpc-handlers/src/lib/chat/follow-up/chat-follow-up-queue.service.ts:109-119,278-290`); a test exercises it (`chat-session.follow-up-queue.spec.ts:324-332`). The backend also rejects a slash command, guards Stop generation, binds then calls the SDK and can catch its failure (`chat-session.service.ts:1723-1745,1930-1953,1983-2011`).
3. **Backend admission while a turn runs.** The intended path is specifically allowed while busy (`chat-session.service.ts:1723-1729,1893-1895`): `sendMessageToSession(...queueIntent)` and `settleAccepted()` return queued or admitted (`:1934-1982`). The Claude pump pushes to `messageQueue` without `require-idle` (`libs/backend/agent-sdk/src/lib/helpers/session-lifecycle/session-stream-pump.service.ts:378-400,443-472`), and waits while `turnInFlight` before claiming the next item (`:203-255,269-289`). Thus a normal active turn's busy state alone is **not** a proven refusal. The `busy` check at `:394-397,451-456,517-521` applies to `require-idle` requests, not this queued request. Codex likewise enters the queue path for `queueIntent` without `requireIdle` (`libs/backend/agent-sdk/src/lib/codex-app-server/codex-chat-adapter.ts:798-831`); its `requireIdle` busy/blocked check at `:799-804` is not the queued path.
4. **Turn/session races. POSSIBLE while user sees work.** `continueSession()` awaits account gate, folder resolution, MCP registration and `autoResumeIfInactive()` *before* binding/SDK send (`chat-session.service.ts:1744-1767,1813-1828,1930-1942`). The original turn can end, restart, compact, or change its live record during those awaits. The Claude pump explicitly rejects a removed/replaced/aborted session after asynchronous message construction (`session-stream-pump.service.ts:430-449`); a missing registry record rejects at `:384-392`. Its queued item can also fail if record identity changes or the session is removed (`:64-75,203-214`). A missing attached broadcast stream leads `autoResumeIfInactive()` to interrupt a registered record and resume (`chat-session.service.ts:2523-2549,2593-2627`), so a visually ongoing subagent/permission/compaction phase with no main stream **could** enter that path; the repository does not prove that it happened. Stop generation cancellation is explicit (`:1930-1933`), but requires Stop and is less consistent with the user's account.
5. **Failed state push. CONFIRMED as a frontend branch; not established as an emitted reason-less failure.** Adapter state flows through `ChatFollowUpQueueService.onStateChange()` to `chat:queued-message-state`, preserving an optional reason (`libs/backend/rpc-handlers/src/lib/chat/follow-up/chat-follow-up-queue.service.ts:235-267`); renderer parser retains nonblank text and omits blank/missing text (`libs/frontend/chat/src/lib/services/chat-store/queued-follow-up-event.ts:25-47`); `handleStateEvent()` calls `fail(id,event.reason)` (`follow-up-queue.service.ts:166-198`). Claude record-removal/token-mismatch failure emits `reason: 'Session ended'` (`session-stream-pump.service.ts:64-75,203-214`); Codex queue closure/delivery failure emits a reason (`libs/backend/agent-sdk/src/lib/codex-app-server/codex-chat-peer-queue.ts:168,226-228`). A future adapter or malformed `failed` push omitting/blanking reason would produce this notice.
6. **Electron transport and timeout.** Preload sends `rpc` to `IpcBridge`; it guards sender/child-window permissions, calls `rpcHandler.handleMessage`, then forwards `success,data,error,errorCode` to the renderer (`apps/ptah-electron/src/ipc/ipc-bridge.ts:525-603`). A rejected sender gets no reply (`:533-535`); a disallowed child method gets an error reply (`:567-576`); a destroyed sender gets none (`:590-595`); an exception gets an error reply (`:609-633`). `ClaudeRpcService` resolves `chat:continue` timeout to a failed result with `RPC timeout: chat:continue`, not an exception (`libs/frontend/core/src/lib/services/claude-rpc.service.ts:23-34,145-200`). Its configured admission timeout is 90s + 30s (`libs/shared/src/lib/types/rpc/rpc-chat.types.ts:38-53`). A late successful backend send after timeout is **POSSIBLE**; the frontend will have restored a draft, so retries need ID reconciliation.

## Most probable root cause

**POSSIBLE:** an error or timeout from `chat:continue` while its pre-send admission work races the still-running session, followed by the frontend's unconditional, reason-free `fail()` call. This is more consistent with the exact no-parentheses text than a normal queue `failed` push, because the inspected SDK emitters attach reasons. The precise backend condition (session replacement, ownership mismatch, account/resume failure, IPC timeout, or another SDK exception) remains **unconfirmed without a correlated RPC result/log**. A permission prompt or subagent turn alone is not proven to reject queued input; a main-stream/record transition during one is the plausible mechanism.

## Where the reason is lost

The backend return includes `error`/`errorCode` (`chat-session.service.ts:1983-2011`), Electron forwards them (`ipc-bridge.ts:596-603`), and `ClaudeRpcService` retains them in `RpcResult` (`claude-rpc.service.ts:188-202`). `FollowUpQueueService.submit()` checks only booleans, never `result.error`, `result.errorCode`, `data.error`, `data.errorCode` or `data.cancelled` (`follow-up-queue.service.ts:405-420`), then calls `fail(clientMessageId)` (`:439-440`). The separate push path loses only absent/blank reason at the event producer/parser (`queued-follow-up-event.ts:38-47`). The provided spec covers a **reasoned** failed push, not the reason-less submission (`follow-up-queue.service.spec.ts:280-296`).

## Proposed fix

- In `FollowUpQueueService.submit()`, classify `RpcResult` failure, `ChatContinueResult` failure/cancellation and caught exception. Use a fixed safe user-facing reason per typed code (session changed, stopped, authentication needed, connection timed out); log the raw error and correlation context via injected `LoggingService`. Do not interpolate arbitrary backend/SDK error text into the UI. Pass the safe reason to `fail()` and keep the exact captured tab/session/client ID in logs. Use the existing typed RPC result; parse any new IPC or event boundary fields with Zod rather than casts.
- For transient timeout/unknown transport outcome, reconcile `chat:queued-list` and receipt state before restoring to composer, or add a minimal status lookup keyed by session/client ID. Otherwise a late backend acceptance can both run the message and invite a duplicate retry. Keep the original client ID for idempotent retry where supported. In backend admission, recheck session ownership/live identity immediately before `bind()`/SDK send after awaits, and return a stable typed refusal code when changed.
- Keep the fix in shared chat code and Electron bridge only if transport evidence calls for it; no host-specific imports in neutral libraries. Preserve queue admission during a live turn. No source edits were made in this investigation.
