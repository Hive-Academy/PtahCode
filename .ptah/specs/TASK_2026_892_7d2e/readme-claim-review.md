## Findings

### 1. SCREENSHOTS.md:40-41 — the claim "never copies `workspace-storage`" is false

- **Wrong text:** "Secrets are never copied. In particular, it never copies `secrets.json`,
  `secrets.enc*`, `master-key-ref.json`, `config.json`, or `workspace-storage` from the
  source profile."
- **Evidence:** `apps/ptah-electron-e2e/src/docs-screenshots/_harness/docs-profile.ts:36-43`
  copies `workspace-storage/<base64url workspace path>` from the dev profile when
  `devSessionWorkspace` is set. `docs-fixtures.ts:63-66` sets it when the
  `useDevSessionStorage` option is true. `chat.shot.ts:39-47` sets that option when
  `PTAH_DOCS_SESSION_WORKSPACE` is set. It then opens that real workspace, not the
  sample repo. The file allowlist is empty (`docs-profile.ts:27-35`), so the
  other named files are never copied.
- **Replacement:** see finding 3. That replacement includes this fix.

### 2. SCREENSHOTS.md:37-40 — the run is not "isolated", and the harness does not "seed synthetic state"

- **Wrong text:** "**An isolated dev-profile copy with synthetic state.** … The harness
  creates a temporary profile and seeds synthetic state in a throwaway sample repo."
- **Evidence:**
  - No profile files are copied by default (`docs-profile.ts:27-35`, empty allowlist).
    The temporary `userData` folder gets only `global-state.json` with the workspace
    folder list (`docs-profile.ts:44-49`). It is an empty profile, not a copy.
  - The launched app still reads the developer's home `~/.ptah` at run time. The
    launcher overrides only `PTAH_DB_PATH`, not `HOME` or `USERPROFILE`
    (`apps/ptah-electron-e2e/src/support/electron-launcher.ts:57-64,109-117`; there is
    no `HOME` override in the launcher or the harness). The Electron settings layer
    reads `~/.ptah` for the settings file, the secrets store and the master key
    (`libs/backend/platform-electron/src/settings/electron-settings-registration.ts:60-79`,
    `libs/backend/platform-electron/src/implementations/electron-workspace-provider.ts:15,57`).
    Other `~/.ptah` reads include `apps/ptah-electron/src/di/phase-2-libraries.ts:383-433`.
  - `~/.ptah` is refused only as a *copy source* (`docs-profile.ts:15-17`).
  - The sample repo holds git fixture files (`docs-repo.ts:136-150`). It holds no app state.
- **Effect:** the run never *copies* secrets into the profile. But the app reads the
  production settings and secrets during the capture. Thus provider, account or
  setting values from `~/.ptah` can appear in a screenshot. This also conflicts with
  D8 ("Production `~/.ptah` stays excluded"). The coordinator must decide on a
  harness fix, for example a `HOME`/`USERPROFILE` override to a temporary folder in
  `launchPtah`. That fix is out of scope for this text review. Until a fix lands,
  the per-asset privacy inspection (D8) is the only control.
- **Replacement:** see finding 3.

### 3. SCREENSHOTS.md:37-44 — replacement text for both bullets

- **Wrong text:** lines 37-44 (both new bullets). Line 42-44 also says "capture against
  synthetic data" for all captures. But the saved-session shot uses a real workspace
  when `PTAH_DOCS_SESSION_WORKSPACE` is set, and only a regex guards it against private
  text (`chat.shot.ts:40`).
- **Exact replacement** (for the current harness; update it again if the other lane
  changes `docs-profile.ts`, `docs-fixtures.ts` or `electron-launcher.ts`):

```markdown
- **An empty temporary profile.** Each run creates a temporary Electron `userData` folder
  and writes only the workspace list into it. By default, no file is copied from the
  development profile (`%APPDATA%\Ptah Dev`, or the path in `PTAH_DOCS_SOURCE_PROFILE`).
  The harness refuses `~/.ptah` as a copy source. The SQLite database is a temporary file
  (`PTAH_DB_PATH`).
- **The home `~/.ptah` folder is not isolated.** The launcher does not override `HOME`, so
  the app still reads settings, the secrets store and the master key from `~/.ptah` while
  it captures. Examine every image and video for keys, names, emails and paths before you
  commit it.
- **A throwaway sample repo for captures.** The default workspace is `SAMPLE_REPO`, which the
  fixture creates and deletes. The app may rewrite `.codex/agents/*.toml` in an opened
  workspace, and Source Control actions can stage files, so git shots never use a
  developer's repository.
- **Saved development sessions (optional).** When `PTAH_DOCS_SESSION_WORKSPACE` is set,
  `chat.shot.ts` opens that workspace and copies its `workspace-storage` folder from the
  development profile. That shot uses real session data. It skips the capture if the page
  shows text that looks private.
```

  If the coordinator adds a `HOME` override first, replace the second bullet with:
  "The launcher points `HOME` at a temporary folder, so the app does not read `~/.ptah`."

- **Note on the last bullet:** confirm the skip behavior in the final `chat.shot.ts`
  before you keep the sentence "It skips the capture …". The test title at
  `chat.shot.ts:49` ("if private text is absent") and the regex at line 40 support it.
  I did not read the rest of the test body.

### 4. README.md:118 — "Open a session from the rail" does not describe how the inspector opens

- **Wrong text:** "Open a session from the rail to inspect its stats, requests, agents, and
  linked sessions."
- **Evidence:** the inspector is docked at the right edge of the focus area for the
  *focused* session. It is compact by default, and you expand it
  (`apps/ptah-docs/src/content/docs/canvas/session-inspector.md:8-16`;
  `libs/frontend/canvas/src/lib/canvas-rail/canvas-inspector-dock.component.ts:125-144`).
  The sections are Orchestrator requests, session stats, agents, plan limits and lanes,
  task, and git. Linked sessions show only when the inspector is expanded
  (`libs/frontend/chat/src/lib/components/organisms/session-inspector/session-inspector.component.ts:55-66,215-223`).
- **Replacement:** "- **[Session details](https://docs.ptah.live/canvas/session-inspector/).**
  Expand the inspector beside the focused session to see its requests, stats, agents,
  plan limits, task, git changes, and linked sessions."
