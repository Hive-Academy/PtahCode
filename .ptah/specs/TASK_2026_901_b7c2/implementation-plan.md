## Architecture decision

**Chosen:** review-core emits lifecycle progress through a new interface in review-contracts. review-github implements GitHub Check Run and commit-status writes and read-side check discovery, plus thread-resolution reads. Electron composes the port, the existing publication guard, a named cron handler, and startup recovery. The review-core must not import cron-scheduler or review-github; adapters depend inward on contracts. Reuse the existing review queue/discovery and the task-900 renderer. Rejected: putting GitHub fetches directly in the orchestrator (would reverse the dependency and duplicate transport policy). Rejected: a second polling worker (cron already handles sleep/catch-up). Existing `review-publication.service.ts:4` core → GitHub helper dependency should have been removed by task 900.

## Component specifications

### Status contract and lifecycle coordinator

- **Responsibility:** map attempts to queued, in_progress, and completed statuses and progress summaries.
- **Contract:** attempt/state and stage records (`review-repository.interface.ts:5-43`), queue claims (`review-queue.service.ts:71-85`), and typed GitHub target (`github-review-publication.adapter.ts:22-43`). Define `IReviewStatusPort` and Zod schemas for status payloads in review-contracts; allow one persisted external status/check ID per attempt and head. Call the port at enqueue, claim, each completed lens, and final release. A skipped/dry-run or publication-blocked attempt must not claim a successful public review.
- **Conclusion:** failure for a completed review with Critical or Major accepted findings or fatal review failure; neutral for only Minor/Nitpick, partial, cancelled, or no actionable findings; success only for a complete review with no actionable findings. Record the mapping in one pure function with focused tests; do not infer success from publication success alone.
- **Failure:** GitHub write failure must not lose the local attempt or block lease release; persist sync-pending with retry time and a sanitized error. Retry idempotently by stored check ID/attempt marker. Throttle progress writes by stage transition and dedupe unchanged text. On missing token, keep local work and report status unavailable.
- **Verification seam:** coordinator specs for transitions, severity mapping, retries, stale-head supersession, and restart idempotency.
- **Files:** CREATE `libs/backend/review-contracts/src/lib/review-status.port.ts`, `libs/backend/review-core/src/lib/status/review-status-coordinator.service.ts`, `libs/backend/review-core/src/lib/status/review-status-coordinator.service.spec.ts`; MODIFY `libs/backend/review-contracts/src/index.ts`, `libs/backend/review-core/src/lib/review-orchestrator.service.ts`, `libs/backend/review-core/src/lib/stages/lens-stage.runner.ts`, `libs/backend/review-core/src/di/tokens.ts`, `libs/backend/review-core/src/di/registration.ts`, `libs/backend/review-core/src/lib/persistence/review-repository.interface.ts`, `libs/backend/review-core/src/lib/persistence/sqlite-review.repository.ts`; CREATE a forward-only SQLite migration under `libs/backend/persistence-sqlite/src/lib/migrations/` for external IDs, owner identity, sync state and retry time.

### GitHub status and credential adapter

- **Responsibility:** authenticate by App installation token when configured, create/update/list own Check Runs, and fall back to a commit status for a personal token.
- **Contract:** new review-contracts port; existing review-github `FETCH` and typed errors (`github-review.adapter.ts:93-139`); existing personal token key (`review-github/src/di/tokens.ts:9`). Add an installation-token provider interface at the host/platform boundary, implemented in Electron from configured App ID, installation ID and private key held in secret storage. Validate settings with Zod and mint a short-lived installation token on demand; never store or log the JWT, private key or token in persistent review rows. If no App credentials, use commit statuses with context `PtahCode Review` and pending/success/failure/error states, mapping neutral to success with a descriptive `description` because commit statuses lack neutral. Never attempt Checks with a PAT. 
- **Permissions:** PtahCode App installation must have `checks:write` to create/update checks, `statuses:write` for commit statuses when used, and `pull_requests:read` for PR discovery, review comments and thread reads; publication of comments also requires `pull_requests:write` (and issue-comment permission where the current walkthrough route requires it). Check actual permission headers or a targeted capability request at startup: 401 means invalid credential, 403 without rate-limit headers or 404 on a protected endpoint means missing permission/installation access. Distinguish this from 403/429 rate limit using `retry-after`, `x-ratelimit-remaining`, and reset headers as current adapter does (`github-review.adapter.ts:120-136`). Never silently use PAT after an App permission denial; surface the missing permission and mark sync pending.
- **Failure:** 15-second timeout per call, Zod-parse every JSON response, bounded response bodies, bounded output summary (<65,536 characters using task-900 renderer), backoff only for idempotent GET/PATCH and status PUT; reconcile uncertain check POST by querying own checks/attempt marker before retry. On rate limit, persist next retry time; no hot loop. On stale PR head, finish old check neutral/cancelled with reason and do not write a success to the new head.
- **Verification seam:** mocked-fetch adapter specs for token mode, PAT fallback, permission detection, 401, 403/429, 5xx, timeout, malformed JSON, POST ambiguity, and body bound.
- **Files:** CREATE `libs/backend/review-github/src/lib/github-review-status.adapter.ts`, `libs/backend/review-github/src/lib/github-review-status.adapter.spec.ts`, `libs/backend/review-github/src/lib/github-app-token.provider.ts`; MODIFY `libs/backend/review-github/src/di/tokens.ts`, `libs/backend/review-github/src/di/registration.ts`, `libs/backend/review-github/src/index.ts`.

### Progress comment and thread reconciliation

- **Responsibility:** update the same summary comment with “Reviewing… X/Y lenses”, then render final run summary; read actual resolved-thread state into findings.
- **Contract:** walkthrough marker/upsert (`github-review-publication.adapter.ts:11-13,145-164`), finding markers (`:165-190`), thread model (`github-review.port.ts:28-40`), and existing hard-coded false (`github-review.adapter.ts:220-227`). Extend the GitHub read port with a paginated GraphQL review-thread query keyed by PR node ID and comment IDs; Zod-validate pageInfo, isResolved and comment identity. Map only own finding markers to local finding IDs. A human resolution changes local finding state through a repository method with idempotent transition history; reopening maps back to unresolved. Do not infer resolution from missing comments or GitHub REST comment state.
- **Failure:** progress-comment patch is best effort and keeps the final publication outbox intact; it must pass the task-900 65,536-character body budget. GraphQL error, partial page, unknown marker, or permission denial leaves current finding state unchanged and records sync-pending. Avoid modifying a comment belonging to another identity.
- **Verification seam:** comment adapter spec for monotone progress, final replacement and exact markers; thread mapper/repository spec for resolved, reopened, missing, pagination and repeated poll.
- **Files:** MODIFY `libs/backend/review-github/src/lib/github-review-publication.adapter.ts`, `libs/backend/review-github/src/lib/github-review-publication.adapter.spec.ts`, `libs/backend/review-github/src/lib/github-review.adapter.ts`, `libs/backend/review-github/src/lib/github-review.adapter.spec.ts`, `libs/backend/review-contracts/src/lib/github-review.port.ts`, `libs/backend/review-core/src/lib/persistence/sqlite-review.repository.ts`, `libs/backend/review-core/src/lib/persistence/review-repository.interface.ts`.

### Electron schedule and startup recovery

- **Responsibility:** register one deterministic review-sync job, bind its named handler, and reconcile stale in_progress checks after restart.
- **Contract:** `ReviewOrchestratorService.discoveryHandler()` (`review-orchestrator.service.ts:79-82`), `startupPoll()` and `reconcileStartup()` (`:85-91`), scheduler handler registry (`cron-scheduler/src/lib/types.ts:123-146`) and catch-up (`cron-scheduler.ts:101-142`). The handler performs discovery/enqueue plus thread sync, returns promptly, and does not run review lanes inline. Create or upsert a stable system job (for example `@ptah/review-sync`) with catch-up `last` so sleep performs one reconciliation, then let the existing detached worker drain the queue. On startup, correlate persisted active attempts/check IDs and current PR heads; resume a lease-requeued attempt when recoverable, otherwise complete its own in_progress check neutral/cancelled with a reason. Never cancel another machine's check: ownership is persisted machine identity plus attempt ID and verified against the remote check marker.
- **Failure:** scheduler unavailable does not block application startup; log with Logger and retain a retryable pending state. Sleep/wake, overlapping cron slots, and duplicate process starts are protected by deterministic job ID, queue dedupe, lease ownership, and per-attempt status ID.
- **Verification seam:** Electron composition spec with actual registrations, scheduler handler spec, startup recovery spec for stale/current heads and foreign checks.
- **Files:** CREATE `apps/ptah-electron/src/services/review/review-sync-schedule.service.ts`, `apps/ptah-electron/src/services/review/review-sync-schedule.service.spec.ts`; MODIFY `apps/ptah-electron/src/di/phase-2-libraries.ts`, `apps/ptah-electron/src/activation/wire-runtime.ts`, `apps/ptah-electron/src/di/container.smoke.spec.ts`, `apps/ptah-electron/src/di/expected-resolvable.ts`, `apps/ptah-electron/src/di/surface-composition.spec.ts`; update `rpc-surface.spec.ts` only if a new RPC method is introduced (none required here).

## Integration architecture

Enabled repository settings → scheduler named handler → existing discovery/queue → detached review worker → status coordinator → GitHub status adapter and progress comment → final publication → completed Check Run or commit status. Scheduler also queries GitHub thread resolution and updates local finding rows. Startup first reconciles expired local leases and remote in_progress checks, then schedules normal polling. Local SQLite owns attempt/check correlation, sync retry and machine ownership; GitHub owns check state and thread resolution. Validate GitHub JSON, App/settings inputs and all returned GraphQL pages with Zod. Use parameterized SQLite queries. The required Check Run can be documented after deployment; branch-protection changes are outward-facing and remain a separate user decision.
