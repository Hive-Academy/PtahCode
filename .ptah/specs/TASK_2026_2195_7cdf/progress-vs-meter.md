# Raw `<progress>` versus `ptah-meter`

Source census: the 13 rendered `<progress>` openings in `libs/` and `apps/` (`rg -n '<progress'`, excluding `node_modules`), checked against `libs/frontend/ui/src/lib/charts/meter.component.ts` and `chart.types.ts`. Paths below are relative to the repository root.

`ptah-meter` requires `value`, `max`, and `label`. It has `xs` (`h-1` track), `sm` (`h-1.5`), and `md` (`h-2`); `neutral`, `accent`, `info`, `ok`, `warn`, `err`, `gold`, `primary`, and `auto` tones; and `showValue`, `hideLabel`, `valueText`, `ariaLabelledby`, `barRole`, and `indeterminate` inputs. A determinate bar defaults to `role="meter"`, so task completion needs `barRole="progressbar"`. Indeterminate mode is already a progressbar without `aria-valuenow`, with pulse or sweep animation and reduced-motion handling. Hidden labels remain available to assistive technology. The component renders its own label/value row, which can be visually hidden with `hideLabel` and `showValue="false"` when the surrounding UI already supplies text.

**Recommendation:** Reuse the existing meter for the 12 compatible sites, setting `barRole="progressbar"` on determinate task progress and meaningful `label` text at every site. Keep the dashboard's native progress until a `native-progress-track` appearance is deliberately added and visually checked. No separate progress owner is justified by semantics alone: this meter already has an accessible progressbar and true indeterminate mode, and the repository already uses both for workspace indexing.
