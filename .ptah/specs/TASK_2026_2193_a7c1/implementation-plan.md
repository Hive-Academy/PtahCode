## Target flow and decisions

1. Analyze completes → **Review skills** (`/onboarding/analyze/skills`). Load a structured stack summary tied to the completed analysis run and active workspace. For each detected item, show its type and evidence and the recommended skills.sh results. Include manual search, deselection, and an empty result per item.
2. Review → existing preview RPC → consent modal. Script-bearing skills need explicit approval by skill and content hash; installation uses `wizard:install-skills-with-consent`, workspace scope. No implicit install. Zero selections can skip to Project guidance. Partial install reports installed and failed items and stays retryable.
3. Skills → Project guidance → Done. Done shows installed/selected/skipped skill outcome and useful next actions, not agent run state. Revisiting saved analysis recomputes recommendations against its validated summary; it does not require an agent-generation run.

### Decisions

- **Structured source:** Generate a small machine-readable `stack-summary` section as part of the existing project-profile/architecture-assessment phase output, parse it once on the backend with a strict Zod schema, and expose it as optional structured response data. Alternative: parse arbitrary prose in Angular; rejected because headings and wording are model-authored and cannot support stable matching. Existing completed analyses lacking it get a backend-only bounded legacy extraction from their phase markdown, marked `legacy`, with no fabricated evidence; a failed extraction yields an empty summary and manual search. This is reversible by rerunning analysis. The summary contains `kind`, `name`, `evidence` and source phase for each item, deduped by normalized name and kind. Do not add a new LLM call or edit verified phase files after hashing.
- **Reuse boundary:** Generalize `SkillRecommendationService` input from dependency strings to typed evidence terms; `package.json` dependencies remain an additional high-confidence source. Retain `SkillSelectionService`, `SkillConsentService`, `ProjectGuidanceService`, skills.sh API, and install RPC. Alternative: new Analyze-only recommender/install service; rejected because it would duplicate search, scoring, and consent rules. Existing team-builder `wizard:recommend-skills` stays compatible; add an analysis-run variant/parameter, validated server-side, rather than trusting caller-authored stack terms.
- **UI ownership:** Rename/extract team-builder skill review, consent, and signal state into flow-neutral `stack-skill-*` units in the same onboarding lib; TeamBuilderStartPage and AnalyzeSkillsPage consume them. Keep team-builder launch/owner-decision behavior local to its page. Alternative: copy the components; rejected because consent and result presentation would drift. If review's guidance controls cannot be cleanly optional, keep a small team-builder wrapper around the shared skill list rather than introducing broad configuration.
- **Old URLs:** Redirect `/analyze/agents` and `/analyze/generate` to `/analyze/skills`, preserving `tab` query parameter, until restored tabs/bookmarks migrate. Delete the agent page implementations and recommendation list after route references are gone. `setup-agent-generation` may remain only as a legacy tab identity if the shared router requires it; it must never invoke deleted PR #1333 backend methods.
- **Project skill creation:** A registry miss for a framework/pattern shows “Create a project skill” as an optional action. This needs a reviewed draft, explicit user action, and `harness:create-skill`; the RPC takes content directly and must not be called with unreviewed model output. If the UI/draft synthesis is larger than the core flow, defer its implementation to the optional third batch below, but retain the offer and manual search in the core page. Decision remains open on whether automatic drafting is authorized; see Clarifications Needed.

## Component specifications

### Analysis data and recommendation (backend)

- **Boundary:** `setup-rpc.handlers.ts` obtains the active workspace and a completed analysis run through existing storage; the caller supplies an analysis identifier, not arbitrary markdown/path. Reuse the storage path checks and completed-run check. Validate the summary before use and bound term count/length, catalog calls and response size. Include source item and evidence in each recommendation; group unmatched framework/pattern terms separately. Search failures are visible as per-item unavailable, not a false “no skill exists.” No adequate match means no exact technology/pattern token match under the existing ranking rule, not merely a network failure.
- **RPC:** Extend shared `WizardRecommendSkillsParams` with a discriminated source (`{ source:'analysis', runId }` versus existing `{ analysis }`) or add `wizard:recommend-analysis-skills` if the current schema cannot safely discriminate. Zod: `source: z.literal('analysis')`, bounded nonempty run ID, no client workspace path/stack terms; response includes `skills`, `detectedItems`, `unmatchedItems`, `searchFailures`, `summarySource`. Extend `MultiPhaseAnalysisResponse` with optional `stackSummary` for live/saved analysis and its Zod validation. Keep existing preview/install schemas and contract unchanged. Register method/prefix and surface guards only if new method is chosen; `wizard:` is already allowed.
- **Failure:** malformed/missing legacy summary returns an explicit extraction warning and empty terms, with manual search enabled. A changed workspace/run must reject or reload; duplicate registry hits dedupe by `source/skillId`. External search has the current bounded concurrency and existing timeout path must be checked; add an explicit timeout if absent.
- **Seams:** schema tests for malformed summaries and stale/cross-workspace run ID; service tests for each evidence category, dedupe/ranking, unmatched items, partial catalog failure; handler tests for active-root binding and consent path reuse.

### Shared skill review and Analyze step (frontend)

- **Boundary:** page-scoped signal store owns selected IDs, search results, previews, approved IDs, installation outcome, and request revision. `AnalysisStepStore` owns only analysis selection/loading. Reset skills state when workspace or analysis run changes; reject late RPC responses. UI receives typed inputs, emits actions, and uses `ClaudeRpcService` through the page/store. - **Flow:** `AnalyzeWorkspacePage` continues to skills; `AnalyzeSkillsPage` retrieves saved or live completed run, displays detected item evidence and matched skills using shared review UI, then handles preview/consent/install and navigates to guidance. Show an explicit skip and registry error state. `AnalyzeDonePage` reads skill outcome from durable install state or rechecks installed skills; do not claim a prior install from an ephemeral signal after reload. Keep existing guidance panel and link behavior, but remove agent-run panels and actions.
- **Seams:** component tests for recommendation/empty/error/partial install, consent gating, skip, workspace switch, and saved analysis. Router tests cover old URL redirects with tab query and new route classification. Existing team-builder tests must still pass after extraction.

Use its existing Zod boundary and workspace path checks. No unattended write, no generated script execution. Surface creation failure inline and keep the draft. If this cannot be completed in the feature batch, expose the offer as disabled with a clear future-work link only if product accepts that partial behavior.
