## 1. Present child-session rule, end to end

1. **PROVEN — tool input:** `SessionStartArgsSchema` accepts task, branch, optional label, deliverables, model, effort, and `phase`; it is strict (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/session-tool-args.schema.ts:45-72`). The handler parses then calls `session.start(parsed.data)` (`session-tool-handlers.ts:679`, same directory). Tool guidance explicitly recommends small/low for coordination/Git/CI and strong for unknown causes/security/design (`session-tools.ts:86-89`, same directory).
2. **PROVEN — initial values and explicit model:** The spawner trims the task (`libs/backend/cli-agent-runtime/src/lib/session-children/session-spawner.service.ts:474`), initializes effort from the request and sources to pin/default, then validates an explicit model before provisioning. An invalid explicit model refuses the start (`same file:654-683`). A pin is authoritative subject to provider admission; it is not silently replaced by ranking.
3. **PROVEN — router wiring:** `registerLaneRoutingServices` constructs `ChildSettingRouterService` (`libs/backend/lane-routing/src/lib/di/register.ts:64-70`). Chat DI aliases that service to the runtime's child-router token (`libs/backend/rpc-handlers/src/lib/chat/di.ts:142-145`). Lookup is lazy because registration may follow spawner construction; missing/failed lookup returns null (`session-spawner.service.ts:2928-2950`). Electron registers lane routing at `apps/ptah-electron/src/di/phase-2-libraries.ts:401`; CLI composition does likewise at `libs/backend/cli-engine/src/lib/container.ts:900`.
4. **PROVEN — exact ranking inputs:** If either setting is absent, the spawner obtains models (only when model is absent), then passes `brief: label-or-branch + newline + task`, model ID strings, validated explicit model if any, and explicit effort if any (`session-spawner.service.ts:686-700`). The router's Zod input truncates the brief to its first 8,000 characters (`libs/backend/lane-routing/src/lib/child-session/child-setting-router.service.ts:17-22`). Both regex fallback and optional decision request see that truncated brief. A label can trigger a rule; decisive task text after 8,000 characters cannot.
5. **PROVEN — fallback ordering:** Deduplicate model strings; split lowercased IDs on hyphens, underscores, dots, slashes, colons and digits. Tokens opus/pro/large/strong mean strength 2; haiku/mini/nano/flash/small/lite mean 0; everything else means 1. Sort strength ascending, then `localeCompare` ascending (`child-setting-rule.ts:10-34`). This is name heuristics, not measured capability, generation, price or context capacity.
6. **PROVEN — fallback choice:** Strong regex wins over small regex. Strong selects the LAST sorted ID and effort high; small selects the FIRST and effort low. A selected ID has modelSource ranking; absent ID has modelSource default; matched effort always has effortSource ranking. Unmatched brief returns neither field and both sources default (`child-setting-rule.ts:35-46`). Empty catalog can therefore yield low effort with a host-default model.
7. **PROVEN — pins and optional refinement:** The service overlays explicit fields individually, labeling them pin; with both pinned it returns immediately (`child-setting-router.service.ts:40-59`). Otherwise it offers ALL admitted model IDs and ALL five efforts, including low, to an optional decision model, using numbered labels (`same file:60-83`). It sends only the brief as request (`same file:103-109`). Valid answers independently replace fallback fields and mark source model (`same file:116-149`). There is no capability/effort floor after refinement.
8. **PROVEN — ranking survives refinement failure:** Unset/blocked decision caller returns fallback (`same file:94-101`); invalid labels preserve fallback (`same file:119-149`); the request deadline and exception path return fallback (`same file:85-91,158-167`). Existing timeout tests explicitly use 3,000 ms (`child-setting-router.service.spec.ts:73-85`). Thus `(ranking)` can mean deterministic fallback after no configured decision model, blocked/failed/late decision, or invalid answer for that field; it does not identify which reason occurred.
9. **PROVEN — final admission:** A ranked model is admitted again. If accepted, resolved model/source are recorded; if refused, model stays unset/default while routed effort survives. Routing exceptions are logged and the start continues (`session-spawner.service.ts:701-723`). Model, effort and source labels enter the child record (`same file:800-809`).
10. **PROVEN — host defaults:** `ChildChatSessionHostAdapter` forwards selected settings to chat startup (`libs/backend/rpc-handlers/src/lib/chat/session/child-chat-session-host.adapter.ts:115-124`). Child startup forwards only present options (`chat-session.service.ts:1552-1564`, same directory). Launch chooses option model, otherwise stored selectedModel, otherwise literal `default` (`same file:1790-1796`), and passes optional effort onward (`same file:1809`). **NOT PROVEN:** A universal effective effort for the unset case; no low/high default can be inferred from the ranking's omission alone.
11. **PROVEN — structured phase ignored for routing:** `phase.kind` is accepted by schema and available on request, persisted at `session-spawner.service.ts:823-826`, and forwarded to execution at `same file:885`. But the routing call at `same file:695-700` omits it, and the route port has no phase field (`libs/backend/cli-agent-runtime/src/lib/session-children/child-setting-router.port.ts:10-17`). **NOT PROVEN:** Whether either reported caller actually supplied phase.
12. **PROVEN — other inputs absent:** Deliverables are stored (`session-spawner.service.ts:631`) but not supplied to the router. Lane outcomes, taskKind, shape/weight, plan/usage limits, monetary cost, generation metadata, workspace token count and context window are absent from the route port and implementation (`child-setting-router.port.ts:10-17`; `child-setting-router.service.ts:17-22,40-83`). Provider/account selection can restrict the catalog, but that is different from ranking against remaining plan quota.

### Why Haiku 4.5 and low can result

- **PROVEN, conditional reconstruction:** If the first 8,000 characters contain a small-work match and no strong-work match, and the admitted list sorts Haiku 4.5 first, the fallback selects Haiku 4.5 + low. `Coordinate CI and git changes` is explicitly expected to select Haiku + low by `libs/backend/lane-routing/src/lib/child-session/child-setting-rule.spec.ts:6-13`.
- **PROVEN:** “Investigate a defect,” “root cause,” “implement pricing,” “review code,” “plan,” and “design” are not themselves strong regex terms. Mentioning Git instructions anywhere can make otherwise serious work small; there is no positive requirement that it be coordination-only (`child-setting-rule.ts:35-39`). Design is mentioned in tool guidance but absent from the strong regex.
- **PROVEN:** Multiple Haiku generations share strength 0; alphabetical ordering can select `claude-haiku-4-5-20251001` before `claude-haiku-5-5`. Dates and version numbers are not compared as generations. For strongest work the reverse alphabetical endpoint is also not a reliable capability comparison (`child-setting-rule.ts:10-40`).
- **NOT PROVEN:** Which of these conditions held for each reported start, whether Haiku 5.5 was offered, or why refinement fell back. Capture original start arguments, admitted catalog snapshot, and per-field fallback reason before claiming a full incident replay. A status with both fields `(ranking)` is consistent with the deterministic path, not proof of a particular timeout or quota event.

## 4. Prioritized fix plan

### P0 — explicit work intent and mandatory floors

**Files:** `libs/backend/lane-routing/src/lib/child-session/child-setting-rule.ts`, `child-setting-router.service.ts`; `libs/backend/cli-agent-runtime/src/lib/session-children/child-setting-router.port.ts`, `session-spawner.service.ts`; `libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/session-tool-args.schema.ts`, `session-tools.ts`; request contract in `session-spawner.port.ts`.

**Present:** Whole-brief regex can downgrade code work; unknown work delegates to arbitrary stored defaults; refinement can choose low again.

**Proposed:** Add optional explicit `workIntent` with code/investigation/review/plan/design/security/architecture and coordination-only variants (`git-only`, `ci-watch`, `status-only`). Pass existing phase.kind separately. Do not expand the widely consumed PHASE_KINDS enum just to describe Git/status. Resolve intent in this order:

1. Existing phase and declared write scope are safety constraints: implement/tests/code edits/review/plan/research/design cannot be downgraded by a conflicting coordination-only flag. Treat batch/completion/docs conservatively unless demonstrably status-only.
2. Explicit workIntent supplies specificity absent from phase (root-cause investigation/security versus routine code work). Coordination-only must expressly exclude code edits, investigation, review, planning and design; CI repair and Git conflict resolution are code work, not CI watch/Git-only.
3. Without an explicit signal, classify unknown as balanced/high. Text may escalate risk to strongest/high; it must never authorize small/low. Label, branch and boilerplate Git instructions must not downgrade anything.

Code implementation, tests, defect investigation and code review have minimum balanced/current Sonnet-class + high. Root-cause, security, architecture and design get the most capable admitted tier + at least high; planning has at least balanced/high (architecture planning gets strongest). Only positively declared coordination-only work can rank small/low. Enforce the floor before offering refinement options AND after interpreting refinement, before admission. Unknown/new model families require capability metadata, not a presumed balanced name.

**Tests:** Extend `child-setting-rule.spec.ts` and `child-setting-router.service.spec.ts`: implementation/investigation/review/plan/design with incidental “coordinate”, “git commit” and CI instructions; root-cause spelling; unknown/empty briefs; explicit coordination-only; conflicting phase/intent; classification before 8k truncation; malicious/invalid/late refinement and valid low answers cannot bypass floors. Add spawner integration tests proving phase/intent reaches router and unknown tasks start balanced/high. Test model-only, effort-only and both pins: each supplied field wins, including explicit low/Haiku; missing fields still obey floors. Preserve explicit admission refusal.
