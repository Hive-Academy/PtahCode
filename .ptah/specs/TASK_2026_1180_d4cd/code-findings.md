## Codex false AT LIMIT

**Verified:** Codex parses every `rateLimitsByLimitId` bucket and fields including `rateLimitReachedType`, `spendControlReached` and credits (`libs/backend/codex-runtime/src/lib/codex-account-usage-client.ts:133-180,188-225`). The reader maps all buckets into windows, with distinct keys for non-Codex buckets (`libs/backend/auth-providers/src/lib/quota/readers/codex-plan-usage.reader.ts:122-131,172-213`). It adds exhaustion only if `usedPercent >= 100` **and** `rateLimitReachedType` is present (`:180-181,208-211`). The reached flag on a 7% weekly window alone does not make it exhausted. Credits are mapped to allowances, not directly to window exhaustion (`:142-164`).

The ledger merges the reading with retained evidence (`libs/backend/auth-providers/src/lib/quota/plan-usage.service.ts:445-455,476-501`). `carryExhaustion` retains an earlier hit unless `readingClears` accepts the new value (`libs/backend/auth-providers/src/lib/quota/plan-limit-ledger.rules.ts:104-114,151-182`); the classifier checks active evidence before percentage (`libs/shared/src/lib/utils/plan-limits/lane-state.ts:326-349`). **Hypothesis (c), retained ledger evidence, is the supported code-path cause.** Commit `d91f6b2a8`, dated 2026-11-10, explicitly fixed clearing a table-reported hit on a newer read; its rule comment names “7% used, limit reached” (`plan-limit-ledger.rules.ts:151-159`). The observation's exact time and full bucket set were not provided, so a separate exhausted bucket, hypothesis (b), cannot be excluded historically. Hypothesis (a) alone does not explain the current mapper.

**Cause supported by code (inference for the historical observation):** hypothesis (c), previously recorded exhaustion survives a fresh 7% provider reading. `toWindow` only sets new exhaustion when `usedPercent >= 100` and `rateLimitReachedType` is present (`libs/backend/auth-providers/src/lib/quota/readers/codex-plan-usage.reader.ts:180-181,208-211`). Hence a fresh 7% reading alone cannot produce `LIMIT REACHED`. The ledger merges its held evidence into the read (`libs/backend/auth-providers/src/lib/quota/plan-usage.service.ts:451-452,486-499`), and `carryExhaustion` retains a prior hit unless `readingClears` accepts the newer window (`libs/backend/auth-providers/src/lib/quota/plan-limit-ledger.rules.ts:104-114`). For a known reset, a provider-table hit clears only if the new window does not `namesGate`; that function treats `reachedType` or `spendControlReached` as a gate even at 7% (`plan-limit-ledger.rules.ts:151-182`). An error-derived 429 with a known reset also survives by design (`:175-177`). The dashboard independently displays used percentage and calls `classifyWindow` for state (`libs/frontend/dashboard/src/lib/components/provider-account-card/plan-tile-view.model.ts:354-374`), so 7% and LIMIT REACHED can coexist.

Hypothesis (a) alone is **not** the direct mapper cause: the flag is copied to `reachedType` but exhaustion is gated by `atLimit` (`codex-plan-usage.reader.ts:192-210`). It can indirectly preserve a ledger hit. Hypothesis (b) remains a possible additional limit, because all native IDs become buckets and non-`codex` buckets receive distinct keys (`libs/backend/codex-runtime/src/lib/codex-account-usage-client.ts:203-223`; `codex-plan-usage.reader.ts:122-131,187-191`); the exact *Weekly* label on the observed row gives no proof that such a second bucket caused that row. The historical ledger contents and full raw snapshot were not supplied, so the exact prior hit/source cannot be verified. Forced spawn working is consistent with a false gate but does not identify its origin (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/agent-spawn-limit-gate.ts:38-68`).

Git history has `d91f6b2a8` on 2026-11-10, “clear a table-reported limit on a newer read”; its rule is now at `plan-limit-ledger.rules.ts:151-182`. The 2026-11-11 fallback commits added source chains but do not prove the historical contradiction fixed. A provider `reachedType` still prevents this clearing.

## Codex/grok lookup timeout

`LaneLimitLookupService.lookupRow` races the read against a per-lane deadline and returns timeout on expiry (`libs/backend/cli-agent-runtime/src/lib/cli-agents/limits/lane-limit-lookup.service.ts:174-213`). Default is 3,000 ms; Codex, Antigravity and Kimi get 12,000 ms (`libs/shared/src/lib/utils/plan-limits/evidence-precedence.ts:16-39`). Codex's sequential app-server then rollout chain allows 50,000 ms (`libs/backend/auth-providers/src/lib/quota/readers/codex-plan-usage.reader.ts:46-47,68-104`). The primary read starts a child, requests rate limits, and closes it before returning (`libs/backend/codex-runtime/src/lib/codex-account-usage-client.ts:434-471`); the alternate service path performs initialize, account, rate limits, and optional activity RPCs in order (`libs/backend/auth-providers/src/lib/providers/codex/codex-account-usage.service.ts:485-565`). **Inference:** a cold read can exceed the 12-second outer deadline before the fallback runs. The 30-second owner cache and in-flight joining already exist (`plan-usage.service.ts:87-90,198-225`); this is a cold-miss/deadline mismatch, not simply absent caching.

Grok uses this same outer lookup but separate account/session readers (`plan-usage.service.ts:185-190,347-368`). It is absent from the slow-provider set, so normally has 3 seconds (`evidence-precedence.ts:26-39`). That explains the same timeout text but does not identify which Grok stage is slow. The spawn path also asks for limits (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/protocol-dispatcher.ts:306,1189`); an MCP-call timeout beyond the classified lane timeout needs transport tracing.

`limitLookupDeadlineMs` gives Codex 12,000 ms and Grok the normal 3,000 ms (`libs/shared/src/lib/utils/plan-limits/evidence-precedence.ts:17-39`); `lookupRow` races each row against that timer (`libs/backend/cli-agent-runtime/src/lib/cli-agents/limits/lane-limit-lookup.service.ts:173-209`). Codex's reader instead allows 50,000 ms across sequential App Server then rollout sources (`libs/backend/auth-providers/src/lib/quota/readers/codex-plan-usage.reader.ts:47,71-102`). A cold App Server is spawned, then `initialize`, `account/read`, and `account/rateLimits/read` are awaited in order (`libs/backend/auth-providers/src/lib/providers/codex/codex-account-usage.service.ts:479-530`); request timeout is 10,000 ms each (`:41,683-688`). Thus a cold read can overrun 12 s before rollout is tried. Grok has a 5,000 ms billing HTTP timeout (`libs/backend/auth-providers/src/lib/quota/readers/grok-account-plan-usage.reader.ts:122-127`), so it can overrun its independent 3 s lane deadline; it does **not** share Codex's App Server cause. Actual wall-time stage logs were not supplied, so these are verified budget mismatches and inferred explanations of today's timeouts.

## Antigravity no windows / reader failed

The ordered sources are OAuth, local RPC, then CLI if fallback is allowed (`libs/backend/auth-providers/src/lib/quota/readers/antigravity-plan-usage.reader.ts:88-138`). OAuth has a 3-second stage budget; local RPC returns unavailable if it finds no valid model quota (`:98-114,193-223`). The CLI runs `antigravity -p /usage` in the remaining 11-second chain budget (`:116-138`; `libs/backend/auth-providers/src/lib/quota/readers/antigravity-cli-usage.adapter.ts:110-134`). Its parser requires all lines to be valid tab-separated rows and rejects duplicates/malformed output (`antigravity-cli-usage.adapter.ts:152-180`). The chain accepts only an available, established, nonempty window set (`libs/backend/auth-providers/src/lib/quota/readers/usage-source-chain.ts:23-29,64-92`). The displayed “no windows reported [CLI command]” may also reflect no windows **applicable to the selected model**, because both local and CLI windows carry model scope (`antigravity-plan-usage.reader.ts:389-410`; `antigravity-cli-usage.adapter.ts:195-203`); raw output and route model are needed to distinguish.

The old “[PlanUsage] reader failed” log is emitted when the whole reader throws (`plan-usage.service.ts:387-395`), whereas the current source chain catches individual source errors (`usage-source-chain.ts:77-80`). Commits `3a36902e0` (2026-11-10) and `aed6e5d1d`/`cd2876373` (November 11) added and hardened CLI fallback; they address some missing coverage but do not prove a live readable source.

The reader orders OAuth API (3 s), provisional local RPC (3 s), then CLI command (up to 8 s) under an 11 s chain budget (`libs/backend/auth-providers/src/lib/quota/readers/antigravity-plan-usage.reader.ts:48-51,88-138`; `antigravity-cli-usage.adapter.ts:24,110-126`). Local RPC requires one discovered server (`antigravity-plan-usage.reader.ts:241-257`), a Zod-valid response and a matching owner, then ignores model entries with missing `quotaInfo.remainingFraction`; no qualifying entries returns unavailable (`:160-223`). OAuth/local failures fall through. CLI is skipped unless `allowCliFallback` is true, and uses `agy -p /usage` (`:116-135`; `antigravity-cli-usage.adapter.ts:120-125`). Its parser accepts only bounded tab-separated rows with a five-hour or weekly label, percent, and ISO UTC reset; one malformed line or duplicate key rejects all rows (`antigravity-cli-usage.adapter.ts:32-49,152-210`). This is a concrete route to the observed no-windows result; the exact rejected output was not supplied. The earlier `reader failed` log comes only from an exception reaching `PlanUsageService`, which maps it to `service-unavailable` (`libs/backend/auth-providers/src/lib/quota/plan-usage.service.ts:387-395`); the historical exception is unknown. The 2026-11-10 CLI reader commit `3a36902e0` and 2026-11-11 chain commits `aed6e5d1d`/`cd2876373` changed the old reader path, so today's symptom is distinct.

## Existing port

`UsageSource` has id, label and `read(PlanUsageReadRequest)`; success carries source/readAt/reading and failure a reason (`libs/backend/auth-providers/src/lib/quota/readers/plan-usage-reader.types.ts:58-105`). The chain visits sources sequentially under one deadline and returns the first proven nonempty set with source and read time (`usage-source-chain.ts:31-66`); otherwise it returns unavailable/no-source with a reason (`:72-92`). `runFallbackUsage` keys cache and single-flight by source/owner/executable/version/account fingerprint, limits concurrency, backs off failures and kills timed-out processes (`fallback-usage.runner.ts:17-45,49-69,78-125`). `PlanUsageService` carries source/readAt to the snapshot (`plan-usage.service.ts:398-409,481-509`); formatter shows source and age (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/agent-limit.formatter.ts:319-336`). The provider-to-reader registry is still a plain record, not a universal source registration (`plan-usage.service.ts:177-190`).

`UsageSource` has `{id,label,read(request)}` and returns `{ok,source,readAt,reading}` or typed failure; `PlanUsageReadRequest` carries owner target, abort signal, and `allowCliFallback` (`libs/backend/auth-providers/src/lib/quota/readers/plan-usage-reader.types.ts:58-105`). `readUsageSourceChain` runs sources in order under one deadline and accepts the first available, established, nonempty window set; it attaches winning source and original read time (`usage-source-chain.ts:9-10,23-29,31-92`). `PlanUsageService` fills missing labels/times, caches, records ledger evidence, and exposes `source`/`readAt` on the snapshot (`plan-usage.service.ts:398-409,481-499`). Formatter maps labels and displays snapshot age (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/agent-limit.formatter.ts:320`; `libs/frontend/dashboard/src/lib/components/provider-account-card/plan-tile-view.model.ts:55-61`). `runFallbackUsage` bounds process lifetime to 8 s, caches by source/owner/executable/account fingerprint, limits concurrency, and kills on timeout (`fallback-usage.runner.ts:80-101,122-162,194-216`; `fallback-usage.constants.ts:1`). It is a reusable CLI fallback contract, but each provider still needs a strict parser and owner verification.

## Per-model dimension

Antigravity local RPC and CLI put model identity in `PlanLimitWindow.modelScope` (`antigravity-plan-usage.reader.ts:389-410`; `antigravity-cli-usage.adapter.ts:195-203`). Ledger identity includes window key and scope; owner evidence is scoped too (`plan-limit-ledger.rules.ts:34-60`; `plan-limit-ledger.service.ts:231-240`). `applicableLimits(snapshot,row.modelScope)` narrows windows/evidence and marks unresolved model scopes unknown (`libs/shared/src/lib/utils/plan-limits/lane-state.ts:127-154`; `libs/backend/cli-agent-runtime/src/lib/cli-agents/limits/lane-limit-lookup.service.ts:306-315`). Formatter and spawn gate consume the generic state (`agent-limit.formatter.ts:215-248,319-370`; `libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/agent-spawn-limit-gate.ts:47`). The dashboard classifies its own window view (`libs/frontend/dashboard/src/lib/components/provider-account-card/plan-tile-view.model.ts:360-373`). The selected model must reach `row.modelScope`; an unresolved scope must remain unknown.

Much of the dimension already exists: `PlanLimitWindow.modelScope` and `OwnerLimitEvidence.modelScope` (`libs/shared/src/lib/types/plan-limit.types.ts:69-100`), ledger allowance identity includes scope (`libs/backend/auth-providers/src/lib/quota/plan-limit-ledger.rules.ts:41-60`), classifier filters applicable windows and marks unresolved model unknown (`libs/shared/src/lib/utils/plan-limits/lane-state.ts:84-105,144-153`), lookup row has `modelScope` (`libs/backend/cli-agent-runtime/src/lib/cli-agents/limits/lane-limit-lookup.service.ts:69-97`). Antigravity CLI rows already set the group as scope (`antigravity-cli-usage.adapter.ts:195-210`); local RPC creates model windows (`antigravity-plan-usage.reader.ts:192-215`). The missing link is reliable normalization from requested Antigravity model/alias into `LaneLimitLookupRow.modelScope`, including the spawn target (`libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/agent-spawn-limit-gate.ts:76-80`). Formatter and gate should consume the same resolved state (`agent-limit.formatter.ts`; `agent-spawn-limit-gate.ts:38-51`), with no provider branch. Model-specific 429 evidence must carry scope from the lane failure path (`libs/backend/cli-agent-runtime/src/lib/cli-agents/limits/lane-limit-classifier.ts:92-101`; ledger service `:230-245`); otherwise an owner-wide hit can incorrectly block every model.

## Decisions

- Attribute the 7% mismatch primarily to retained evidence addressed by `d91f6b2a8`; retain separate-bucket regression. Evidence: `plan-limit-ledger.rules.ts:151-182`, `codex-plan-usage.reader.ts:180-211`. Reversible: yes.
- Preserve unknown for unreadable/unverified sources. Evidence: `usage-source-chain.ts:23-29,85-92`. Reversible: yes.
- Reuse the existing chain, fallback runner and model-scope classifier. Evidence: `plan-usage-reader.types.ts:95-105`, `fallback-usage.runner.ts:78-125`, `lane-state.ts:127-154`. Reversible: yes.

- Treat the historical Codex explanation as an inference, not a proven runtime reconstruction. The available code eliminates fresh 7% exhaustion as a direct mapper outcome and supports carried ledger exhaustion; this is reversible when raw historical evidence appears.
- Keep API-key Claude outside subscription plan windows; `planOwnerRead` explicitly returns `unsupported-auth`. A separate verified billing source would be a new capability, not a reinterpretation of the subscription reader.
- Reuse the existing source-chain and fallback runner contracts instead of adding CLI branches to formatter or spawn gate; both already consume the shared classified state.
