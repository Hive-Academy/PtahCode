# Stuck remote session fix rereview

**Verdict: REVISE — 7/10.** The new serialization fixes the demonstrated two-attach stale-head race, the normal borrowed-drive path preserves its nonce, and `session:status` reads the engine's own turn-state registry. Two lock/state edge cases remain, plus an unbounded wait introduced by serialization.

## Remaining findings

1. **High — A racing foreign refresh can be released by this attach** (`libs/backend/worker-runtime/src/lib/transcript.ts:143-157,170-192`). The initial `held()` check and `acquire()` are separate. `KernelSessionDriverLock.acquire()` is re-entrant for *any* held entry and also returns another caller's pending acquisition. If another in-process refresh enters between those calls, `acquire()` returns its nonce. The post-acquire check recognizes only `purpose === 'drive'`, so this attach calls `release()` on the foreign refresh nonce, potentially closing its lock while its history read is in progress. The stated fail-closed rule for a foreign refresh therefore holds only when it was present at the first check. After acquisition, distinguish an entry this refresh acquired from an existing/pending refresh; never release a nonce whose ownership cannot be established. Add a deferred-acquire race test with the foreign refresh entering between the checks.

2. **Medium — A failed turn can still own background tasks yet list as idle** (`libs/backend/worker-host/src/lib/commands/remote-sessions.ts:359-361`). `SessionTurnStateRegistry.settleTurn()` chooses `failed` before it considers `backgroundTasks`, but retains the tasks in the state (`libs/backend/agent-sdk/src/lib/helpers/session-turn-state.registry.ts:359-376`). The new predicate checks only phase and `isStreaming`, so `failed` with nonempty `backgroundTasks` loses the running chip despite the comment's promise to reject background work. Require no pending background tasks (and consider pending cron work according to the intended idle definition); add a failed-state test with nonempty tasks.

3. **Medium — A hung history read now blocks every later attach for that session** (`libs/backend/worker-runtime/src/lib/transcript.ts:116-127,185-185`). `refreshSerial()` correctly stores a never-rejecting predecessor, so a *rejected* refresh does not poison the chain. But `HistoryReader.readForResume()` has no timeout or cancellation at this boundary. If one read never settles, all subsequent attaches wait behind it indefinitely, even if they could otherwise return a snapshot or a later refresh. Provide a bounded/cancellable refresh or a safe recovery path, and cover an indefinitely pending read.

## Checks and scope

- `session:status` is the engine state read in `session-rpc.handlers.ts:1673-1717`: it obtains `SessionTurnStateRegistry.get()`, derives `isStreaming` from `generating`, and returns no turn state on caught errors. `InProcessRpc.call()` also converts thrown, malformed, and refused responses to `ok: false`; `idleEngineSession()` then keeps the lock classified as running. The new schema validates the fields used by the predicate.
- `sessions.list` makes one in-process `session:status` call per attributable session with a locally held drive lock and no worker-driver turn. Calls are parallel across rows. This adds linear local RPC work; no network round trip is involved. Failure remains conservative, and the evidence reviewed does not establish a separate cost defect.
- The two-attach deferred-read test exercises the stale-head fix. The new specs do not cover the foreign-refresh acquisition race, a failed state with background tasks, or a hung read.
- Scoped verification passed: `TMPDIR=/home/amun/.cache/ptah-phase-e-tmp npm run verify -- -p @ptah-extension/worker-host,@ptah-extension/worker-runtime` (four lint/typecheck tasks and two test tasks, all Nx cache hits). No build or workspace-wide checks were run.
- The cross-process ownership limitation from the first review is documented in `future-enhancements.md`; this remains an explicit future handoff decision, not an additional finding against this change.
