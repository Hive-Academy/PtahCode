# Stuck remote session fix review

**Verdict: REVISE — 6/10.** The reported lock lifecycle and original list bug are real, but the attach change introduces a stale replay race and the list classification does not establish that this process's lock is idle.

## Findings

1. **High — Concurrent attaches can replay stale history** (`libs/backend/worker-runtime/src/lib/transcript.ts:89-92`). `held()` includes a `refresh` acquisition. If attach A acquires that lock and pauses in `readForResume()`, attach B sees `heldHere`, skips the refresh, and returns the old log before A appends its new baseline. The prior code re-entered the lock (itself unsafe), but this change makes stale replay an intended path. Distinguish a drive lock from a refresh lock and serialize or await in-process refreshes for the same session. Do not release a borrowed nonce. Add a deferred-read, two-attach test that proves B cannot return the old head.

2. **Medium — A locally held lock is not proof of an idle engine record** (`libs/backend/worker-host/src/lib/commands/remote-sessions.ts:332-335,368-379`). `driver.running()` tracks only turns admitted through this `SessionDriver`; `deps.lock.held()` tracks the entire engine process. Once `tabsBySession` contains an ID, a later turn started through any other in-process chat path can hold the lock while `driver.running()` is false. The list then reports `idle` and drops its driver chip. The current worker server routes remote starts through this driver, so this depends on another in-process caller sharing its engine, but the helper's claim is broader than its evidence. Check engine turn/record activity through an authoritative source, or restrict the exception to a known idle record with a reliable lifecycle signal. Cover an attributable session driven through another path.

3. **Medium — An idle record still blocks other processes** (`libs/backend/rpc-handlers/src/lib/chat/session/session-driver-lock-coordinator.ts:282-297,345-360`; `libs/backend/worker-host/src/lib/commands/remote-sessions.ts:332-335`). The coordinator owns the lock until its record is removed, independent of turn completion. The new list label makes the worker session appear idle, but the Electron parent or another client still cannot acquire its drive lock. This is pre-existing lock retention, not a regression from these lines, and may be intentional session ownership. If `idle` is meant to imply that another client can continue the session, the lifecycle or protocol must explicitly support handoff/release; relabeling alone does not fix that behavior. Document the intended ownership semantics and test cross-process continuation.

## Evidence and test assessment

- **Root cause confirmed.** The coordinator adds a record to `owner.records` on session ID binding and releases only after record removal (`session-driver-lock-coordinator.ts:282-297,345-360`). The kernel `holder()` reports its own process's entry (`kernel-session-driver-lock.ts:275-284`). Previously, `sessions.list` mapped that holder to `running` after `SessionDriver.end()` removed the turn (`session-driver.ts:370-382`). A failed turn can therefore leave a visible idle engine record with a running chip.
- **`running` versus `driving` is used sensibly for the remote path.** `running()` includes admitted and orphan turns; `driving()` includes registered turns only (`session-driver.ts:172-185`). A known admission does not enter the new idle branch. A list call racing a future turn can become outdated after it returns, as any snapshot can; the synchronous idle mapping does not itself add an await window. The separate same-process-path case remains.
- **The old release did drop the engine lock.** `KernelSessionDriverLock.acquire()` returns the existing entry's nonce on an in-process acquire (`kernel-session-driver-lock.ts:81-89`), and `release()` closes the matching entry (`:224-248`). Skipping acquire/release for a held *drive* lock avoids that failure. The current `heldHere` check also matches `refresh`, `releasing`, and `stranded` entries; it must narrow the case.
- **The new happy-path tests fail against the old implementations by inspection.** The list test expects `idle` after `session:turnFailed`, whereas the old mapping uses the mocked holder and returns `running`. The attach test expects no acquire/release, whereas the old code calls both. The other-process list test is a useful unchanged-behavior check. The attach mock does not model actual kernel release or concurrent refresh, and its history never changes; it cannot establish replay correctness. No automated checks were run in this read-only review.

## Concrete changes requested

1. In `Transcript.attach`, treat a held drive lock as borrowed ownership, but refresh history without releasing that nonce when it may have changed. For a held refresh lock, await the in-process refresh and replay its result. Fail closed or retry for non-`held` states.
2. Make the list exception depend on authoritative engine idleness, or constrain and document the host's single admission path so another in-process turn cannot be hidden.
3. Add the concurrent attach and other-path turn cases to the specs. Decide and document whether an idle worker session is transferable to another process; if so, implement a safe lock handoff.
