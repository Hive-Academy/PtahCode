2. **What happens when inputs are weird?**
   - `intake.platform === 'other'` (`profile === null`): `bundled` is `[]`, `requiredBundled` is `[]`, `profileSkillSlugs` is `[]`, `saveWorkspacePluginConfig` and `reconcileHarness` are not called, and `buildNewProjectSeedPrompt` falls back to generic discovery/bounded-context wording when `ddd-architecture` is not in `availableSkillIds`.
   - `intake.platform === 'python'` (`PYTHON_PROFILE`, `requiredPlugins: []`): `profile` is non-null, so `requiredBundled` becomes `['ptah-core']`, `profileSkillSlugs` is `['python-workspace-initializer', 'python-workspace-architect', 'ddd-architecture']`, `ptah-core` is enabled, `ddd-architecture` is allowlisted and reconciled into `{ws}/.claude/skills/ddd-architecture`, and the missing external Python plugins are still reported in `missingExternalPlugins`.
   - `workspaceRoot === undefined`: `allowlistProfileSkills` warns and returns `false` when `profileSkillSlugs.length > 0`, which sets `allowlistReady = false` and forces `availableSkillIds = []` so the prompt never names unsynced skills.

3. **What happens when dependencies fail?**
   - If `this.skillSyncGate.keepSelected` returns `false` or throws (`harness-rpc.handlers.ts:868-887`), `allowlistProfileSkills` logs a warning with `errorSource: 'HarnessRpcHandlers.allowlistProfileSkills'` and returns `false`. `availableSkillIds` is forced to `[]` (`:963-966`).
   - If `this.reconcileHarness('harness:start-new-project')` returns `false` (`:319-344, 957-960`), `reconcileSucceeded` is `false` and `availableSkillIds` is forced to `[]`.
   - If `this.skillSyncGate.resolve(workspaceRoot)` throws inside `resolveAvailableSkillIds` (`:819-844`), it catches, logs a warning with `errorSource: 'HarnessRpcHandlers.resolveAvailableSkillIds'`, and returns `[]`.

4. **Is shared state safe?**
   **Yes.** `saveWorkspacePluginConfig` (`libs/backend/agent-sdk/src/lib/helpers/plugin-loader.service.ts:1374-1427`) preserves omitted fields (`disabledPluginIds`, `disabledAgentIds`, `enabledSkillIds`). `SkillSyncGate.keepSelected` (`libs/backend/harness-sync/src/lib/state/skill-sync-gate.ts:193-207`) is idempotent, preserves `skillSyncMode: 'all'` when already set, and merges/deduplicates/sorts slugs when in `'selected'` mode while preserving `skillSelectionAt`.

## Numbered Findings

### Minor Findings

1. **`[minor]` `libs/backend/rpc-handlers/src/lib/harness/workspace/harness-workspace-context.service.ts:349-368` & `libs/backend/rpc-handlers/src/lib/handlers/harness-rpc.handlers.ts:921-922` — Workspace-only plugin/skill reads can drift from `PluginConfigSourceResolver` when a plugin or skill is disabled in the global capability layer**
   - **Evidence**: In `registerStartNewProject`, `const config = this.pluginLoader.getWorkspacePluginConfig()` (`harness-rpc.handlers.ts:921`) and `this.workspaceContext.discoverAvailableSkills()` (`harness-workspace-context.service.ts:350-351`, which calls `this.pluginLoader.resolveCurrentPluginPaths()` and `this.pluginLoader.getDisabledSkillIds()`) read only the **workspace** layer. By contrast, during `reconcileHarness`, `PluginConfigSourceResolver.resolveEffective(workspaceRoot)` (`libs/backend/harness-sync/src/lib/sources/plugin-config-source-resolver.ts:207-230`) calls `this.loader.getEffectivePluginConfig(workspaceRoot)`, which merges the global capability layer (`ICapabilityGlobalLayer`) with the workspace layer. If a user globally disabled `ptah-core` or `ddd-architecture` without a workspace-level override, `HarnessReconcilerService` will omit that skill from `{ws}/.claude/skills/`, while `discoverAvailableSkills()` will still treat it as active and `resolveAvailableSkillIds` will include it in `seedPrompt`.
   - **Concrete correction**: In `HarnessWorkspaceContextService.discoverAvailableSkills()` (or `HarnessRpcHandlers.resolveAvailableSkillIds`), intersect discovered skills with `this.pluginLoader.getEffectivePluginConfig(workspaceRoot)` when available so globally-disabled plugins/skills are excluded from `availableSkillIds` just as they are excluded during reconcile.

2. **`[minor]` `libs/backend/rpc-handlers/src/lib/handlers/harness-rpc.handlers.spec.ts:344-358` — `HarnessRpcHandlers` unit suite uses an in-memory `SkillSyncGate` fake rather than a real `SkillSyncGate` instance**
   - **Evidence**: `buildSuite()` (`harness-rpc.handlers.spec.ts:344-358`) stubs `skillSyncGate` with an in-memory `allowedSlugs = new Set<string>()` where `keepSelected` mutates the set and `resolve` returns `{ mode: syncMode, slugs: [...allowedSlugs], derived: false }`. While `libs/backend/harness-sync/src/lib/state/skill-sync-gate.spec.ts:168-210` tests the real `SkillSyncGate.keepSelected` against disk, `harness-rpc.handlers.spec.ts` does not exercise the real `SkillSyncGate` slug-validation (`isSafeSlug`) and `HarnessStateStore` persistence during `harness:start-new-project`.
   - **Concrete correction**: Wire a real `new SkillSyncGate(new ManagedManifestStore(), new HarnessStateStore())` pointed at a temp workspace directory in at least one `harness:start-new-project` spec case in `harness-rpc.handlers.spec.ts`.
