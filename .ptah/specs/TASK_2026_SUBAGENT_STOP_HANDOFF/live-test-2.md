## Findings and root-cause hypotheses

1. **The safety stop did not fire after 28 denied Reads.** `libs/backend/agent-sdk/src/lib/helpers/compaction/subagent-notes-gate.ts:62-65` increments denials and flags `stop` at three. `subagent-budget-monitor.ts:755-765` starts `stopWarnedAgent` when that flag is true, while `:772-789` only calls `stop` if it finds a live session state whose `warnedAgentId` matches. The observed denials plus absence of a safety-stop log or record suggest that lookup returned without a matching state, or the stop was deferred without recovery. This is a hypothesis, not a proven internal branch; targeted instrumentation should log the selected state and any early return.
2. **Normal exits did not persist the required handoff.** The `SubagentStop` hook calls `finishWarnedAgent` at `libs/backend/agent-sdk/src/lib/helpers/compaction/subagent-budget-hooks.ts:47-48`. `subagent-budget-monitor.ts:829-855` can return before preparing a handoff if its notes gate or matching session state is missing; `:1718-1735` is the record write path. No new-run `SubagentHandoffRecords ... saved` line appeared for these three tool calls, despite `SubagentStop` and notes gate denials. A lost or mismatched monitored state is a plausible common cause. The notes redaction path at `subagent-budget-monitor.ts:888` also depends on a prepared normal handoff, consistent with the unredacted notes observed.
3. **S1 duplicate remains unresolved by this live run.** Round 3 warned that `PostToolUseFailure` may return the full handoff again. These three original Agent calls exited normally; none generated an Agent `PostToolUseFailure` event. Ordinary tool results and UI continuation demonstrate useful subagent output, but they do not prove exactly-once delivery of the Ptah host handoff. A controlled forced-stop case remains necessary to exercise S1.
