# SDK subagent budget stop: evidence and recommendation

Decision served: choose a stop and handoff mechanism that makes the **first** parent continuation identify Ptah's budget, continue unfinished work without another human turn, and leave usable notes. Options are the current `stopTask` plus streamed handoff, hook based repair, and a cooperative, interrupt free subagent exit. This report recommends an experiment order, not an architectural decision.

## Answer 1: parent sequence and failure mode

**Foreground:** `stopTask` interrupts the in-flight Agent tool call. The parent first receives the exact interrupted tool result above. Ptah's notice/handoff is prepared and queued after the SDK stop result. The first parent reply can finish on the interruption interpretation before the separate handoff is read; the cited foreground run did so. The handoff can be consumed on a later turn, as that run's later record read shows. The source comment claiming a foreground notice “rides on its own tool result” (`subagent-budget-monitor.ts:1578-1581`) is an intention; the observed transcript has a standalone queued handoff after the interrupted result. **Background:** the launch result is earlier; at stop the SDK task notification saying “stopped by user” precedes the Ptah user handoff. The example parent ultimately continued without a human message. The observed failure is therefore nondeterministic first-turn attribution and delivery timing; “NEVER continues” is not universal across the supplied traces. The user-origin handoff is a new prompt, not a guaranteed amendment to the same tool result (`subagent-message-dispatcher.ts:212-229`).

## Answer 2: hooks and same-turn repair

`PostToolUseFailure` input has `tool_name`, `tool_use_id`, `error`, and optional `is_interrupt`; its only hook-specific output is `additionalContext` (`sdk.d.ts:2747-2764`). A **foreground** interrupted Agent result is eligible in principle, but no supplied hook trace proves that event fired for `stopTask`; instrument it. It cannot replace the tool result text. `TaskCompleted` is a separate task-management hook with `task_id`, `task_subject`, etc., **no status field** (`sdk.d.ts:10210-10220`); it must not be assumed to fire for a background Agent notification or distinguish `stopped` by itself. `SubagentStop` has `agent_id`, transcript path and last assistant message (`:10145-10165`); its `additionalContext` is explicitly delivered **to the subagent** to let it continue (`:10168-10173`), so it is not a same-turn parent override. `PreToolUse` can deny with `permissionDecision:'deny'`, `permissionDecisionReason`, and `additionalContext` (`:2849-2863`), but this governs a subagent's next tool, not the already-returned parent Task result. Hook outputs therefore offer a possible adjacent context signal, not a verified same-turn replacement of the SDK canned interruption/notification. The installed wrapper is not enough to verify CLI injection ordering for each hook; a small live hook probe is required before relying on it.

Cleaner candidate: at near budget, instruct the subagent to write notes and finish with a budget handoff as its **normal final message**, while `PreToolUse` gates further work. This avoids `stopTask`'s user-interruption wording if the model cooperates. A denial by itself may merely loop or end with a failed tool; it does **not** guarantee normal completion. Keep `stopTask` as a bounded safety fallback. Validate in a live run that a normal Task result contains the Ptah handoff in the same parent turn.

## Answer 3: notes enforcement and fallback

`BaseHookInput.agent_id` is present only inside subagents (`sdk.d.ts:184-190`), so a `PreToolUse` hook can key its gate by agent ID. After the 85% notice, permit the exact canonical notes-path `Write` (and a narrowly scoped parent-directory creation operation if required); deny other tool calls with a reason naming the path. Match path inside the workspace with existing root-validation helpers, parse tool input, and require the exact agent identity and budget state. Bound denials per agent (for example three), then trigger the safety stop; also bound elapsed time because a model can issue no more tools. Never permit arbitrary shell writes under the guise of notes. The reason is model visible by hook contract, but Haiku compliance is unproven. This is a proposed design, not a verified behavior.

The host already has a bounded progress snapshot: last assistant text, targeted file paths, recent tool calls/outcomes and an optional transcript path (`subagent-budget-monitor.ts:1052-1082,1476-1482`; `subagent-handoff-message.ts:125-141`). It redacts assignments/flags/labels before a handoff (`subagent-budget-monitor.ts:226-305,1482-1497`) and redacts an existing notes file after stop (`:1400-1403`). If notes are absent, write a **host-generated** notes file from that snapshot plus original task and the stopped transcript pointer, mark its provenance and uncertainty, cap lengths, redact secrets before writing, and atomically persist it before publishing the handoff. Do not copy raw transcript JSONL wholesale: it can contain tool inputs/results, secrets, and user material. If the workspace/path is unavailable, report that explicitly; “always exists” cannot be promised without a writable workspace.

## Answer 4: ranked options, files, proof

1. **Cooperative normal exit with bounded gate and safety stop** (preferred experiment): model writes notes and final budget handoff; host supplies missing notes; parent receives a normal Agent result. Best same-turn semantics, but requires proving the model exits after a bounded deny. Keep fallback stop for a noncooperative model.
2. **Current `stopTask` plus synchronous parent context**: attach Ptah notice through a verified `PostToolUseFailure` path for foreground and a background task-notification consumer for background, then retain the queued handoff as durable backup. Smaller change, but hook delivery and same-turn ordering are unproven; SDK canned text remains prominent.
3. **Current stop and streamed user handoff only**: least implementation change; supplied traces show the first reply can misattribute the stop and a 10-second acceptance timeout can occur.

Minimal likely files: `libs/backend/agent-sdk/src/lib/helpers/compaction/subagent-budget-monitor.ts`, `subagent-handoff-message.ts`, the handoff-file helper in that directory, `libs/backend/agent-sdk/src/lib/helpers/subagent-message-dispatcher.ts`, `sdk-query-options-builder.ts`, and the existing focused specs for monitor, dispatcher, and query options. Add a small dedicated notes-gate helper/spec if option 1 is chosen; avoid growing the builder. Inspect `session-query-executor.service.ts` only if the live turn/render trace confirms a delivery issue there.

Unit proof: a foreground interrupted result, background notification, delayed `streamInput` read and timeout each preserve exactly one durable handoff; gate scopes by `agent_id`, permits only valid notes write, bounds denials, and safety-stops on timeout; missing notes create a redacted host fallback before handoff. Live proof on installed SDK: log hook event order and outputs for one foreground and one background budget stop; capture exact parent JSONL lines; assert the **first** parent reply names Ptah's budget, a fresh Agent or equivalent continuation occurs with no human message, and notes exist with usable progress. Include a noncooperative Haiku case and a writable-workspace failure case. No build, process, or live test was run for this read-only research.

## Recommendation

Prototype option 1 behind the current safety stop, with host-written fallback notes. First run an instrumented hook/turn-order probe to settle whether `PostToolUseFailure` receives the foreground interrupt and whether the normal-exit result stays in the parent turn. Ship only after both foreground and background live checks pass the first-reply, autonomous-continuation, and notes assertions.

## Decisions

- Treat the 10-second “not read” warning as delayed acceptance, not confirmed loss: transcript `5be...jsonl:79-91` shows later continuation. Reversible if a correlated trace shows a dropped handoff.
- Do not rely on `TaskCompleted` status for background Agent stops: its declared input lacks status (`sdk.d.ts:10210-10220`). Reversible if a runtime-specific extension is instrumented and documented.

## Open risks

- The embedded CLI's exact hook injection and stop-state branches are not visible from `sdk.mjs`; the hook claims above are type-contract conclusions and proposed tests, not observed hook firings.
- Parent continuation may occur in JSONL after the UI has already rendered a misleading answer; the first visible reply and transcript must both be checked.
- A forced notes write can fail due to model noncompliance, permission/path errors, or a tool-free loop. The host fallback must be durable and must clearly label inferred progress.
