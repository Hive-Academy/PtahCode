# Code Logic Review - TASK_2026_POST_STOP_READ_DENIAL

Verdict: **REVISE** (small; the diff is safe, but the report overstates what is proven and one cheap hardening is missing).

## Findings

1. **Moderate** - `libs/backend/agent-sdk/src/lib/helpers/session-lifecycle/session-query-executor.service.ts:304`. The classifier only feeds a log field (`cause`); nothing branches on it (grep of `'denied'` in compaction/ and the executor). The fix is therefore diagnostic only and correct as such. Regex has the `i` flag, so case is fine; it runs after the `interrupt|stopped by user` test, and the SDK string contains neither "interrupt" nor "stopped by user", so ordering is fine. Gap: the apostrophe is the ASCII `'`; a typographic `'` (U+2019) variant would fall to `other`. Use `/the user doesn.t want to take this action/i` (drop the "right now" tail too). Also the spec line ~1753 is not prettier-wrapped (long inline array), lint may flag it.

2. **Moderate** - report.md "Root cause" is honest but incomplete. SDK `sdk.mjs:56` holds a sentinel list (`LL`) in which the denial string sits next to *other* synthetic texts: "[Tool call skipped: the turn ended to deliver the message that follows before this call ran. Nothing refused it]" and "[Tool call skipped: the turn was stopped before this call ran, by the check whose denial is on another call in this batch. Nothing refused this call]". The CLI therefore already has a distinct text for "turn ended to deliver a pushed message". The denial string is the CLI's canned text for a permission deny with `interrupt: true` (comment at `sdk-permission-handler.ts:1149-1152` says so explicitly, TASK_2026_247) or for a user-rejected prompt. This points the live check at: which tool_results in the failing batch got the "skipped/turn ended" sentinel vs the canned denial, and whether the parent's Read/Glob were in the same assistant batch as the stopped Task/other denied call. Not proven either way; the report's "no Ptah action can prevent it" is an inference.

3. **Moderate** - Ptah deny paths that can emit that string, checked: `sdk-permission-handler.ts:1110-1115` (no response, `interrupt: true`, logs "aborted" warn), `:1185-1187` (hard deny, `interrupt: true`, logs "hard denied"), `:539` (SendMessage budget refusal, `interrupt: false`, custom message), `:776-855` (unattended policy, `interrupt: false`, custom text), PreToolUse hook `sdk-query-options-builder.ts:1315-1334` (matcher is `SendMessage` only, custom reason, fails open). None applies to Read/Glob without a log line, and the report's grep ("Permission decision") only covered one of those log strings. Residual: the two `interrupt: true` paths log under different strings ("aborted"/"hard denied"); the report should confirm those are also absent in the post-stop windows (log lines 19611-19631, 24557-24586). If absent, Ptah's canUseTool is exonerated.

4. **Moderate** - Handoff push is a plausible trigger, not excluded. `subagent-message-dispatcher.ts:190-258` pushes `shouldQuery: true` user turn via `streamInput`, not `interrupt()`; `stopTask` (`:291`) is task-scoped. The CLI's own "turn ended to deliver the message" sentinel shows a pushed user turn can end a turn and skip pending calls in the CLI; the report's note that the push precedes the failing calls (1 ms in round 5) supports this ordering. The parent `abortSignalAborted=false` and `pendingPermissionRequests=0` readings exclude Ptah's abort/pending-request paths, which is good evidence against shared AbortController and rejected-pending-permission hypotheses (SDK `stop_task` does not touch parent permission state on Ptah's side).

5. **Minor / cheap Ptah-side option** - Rather than change stop semantics, add to the handoff text (subagent-handoff-message) a line: "If your next Read/Glob returns 'The user doesn't want to take this action', nothing refused it: re-run the call." Evidence: the CLI's own sentinels say exactly this ("Nothing refused it; re-run it if still needed"), and the canned denial string tells the model to STOP, which is the reported harmful behaviour. Optionally, in the executor tap (`:290-306`), log the batch siblings' results (tool names + first 80 chars) to make the live trace conclusive. No Ptah code path found that needs a behavioural fix.

## Answers

1. Evidence sound as far as it goes (verified: no abort, no pending permission, no PreToolUse deny for non-SendMessage); conclusion "SDK-generated, cause unproven" is acceptable; "no Ptah fix possible" is too strong (see 5).
2. Regex correct for the ASCII string; add apostrophe-insensitive match.
3. Recommend the handoff-text hint (5) plus the sibling-result logging; keep the classifier change.

## Round 1 re-review

Verdict: **REVISE** (one wording fix; everything else resolved).

- F1 resolved: classifier now `the user doesn.t want to take this action` (handles ' and U+2019, case-insensitive, after the interrupt check); both apostrophes are in the spec. Long-line formatting was reflowed in the spec.

- **New R1-1 (Moderate)** `subagent-handoff-message.ts:122-125`. The hint asserts "nothing refused that call; re-run it". That is false for a genuine refusal: `sdk-permission-handler.ts:1185-1187` (hard deny, `interrupt: true`) and `:1110-1115` (aborted, `interrupt: true`) make the CLI substitute this same canned string (comment at `:1149-1152`), so a real user "Deny" on a Read/Glob prompt is indistinguishable by text and the parent is told to override it. Impact is bounded (hint is scoped to "right after this handoff", Read/Glob only, and a re-run re-enters canUseTool, so the user is prompted again and a real deny just recurs), but an unbounded retry or a model that retries after a true user refusal is a regression of the TASK_2026_247 intent. Fix: hedge and bound, e.g. "If a Read or Glob right after this handoff fails with "The user doesn't want to take this action right now" and you did not see a permission prompt the user declined, nothing refused it: retry it once. If it fails again, stop and report to the user."
- Test at `subagent-budget-monitor.spec.ts:1564` asserts the exact old sentence; update with the wording change.
