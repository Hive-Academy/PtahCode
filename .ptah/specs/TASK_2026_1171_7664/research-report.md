# Phase B root-cause research

Question: which code paths explain the five observed failures, and which changes preserve authenticated caller identity? This is a source review, not a reproduction of the other workspace. Citations below are repository-relative `file:line`; observations are from `context.md:11-18`. No tests or builds were run.

## A. Codex main tab: `unattributed-caller`

**Verified path.** `chat-session.service.ts:925-954,1748-1783` builds `mcpServersOverride` from Smithery, OAuth, and the `chat:start` caller's map; the caller map wins. It does **not** read `.mcp.json` or `~/.codex/config.toml` here. `codex-chat-host-ports.ts:306-338` chooses `tabId` before the thread/session ID. It builds `/session/{routingId}/workspace/{cwd}` (`codex-chat-host-ports.ts:374-390`; `codex-ptah-mcp.ts:41-53`), then applies user entries after it with `Map.set` (`codex-chat-host-ports.ts:392`). The privileged session token is issued only if that built-in entry survives (`codex-chat-host-ports.ts:394-421`). A caller-supplied `ptah` entry can therefore replace both the scoped URL and its token. This contradicts the nearby “Claude parity” comment: Claude's `mergeMcpOverride` restores the built-in `ptah` after spreading the override (`sdk-query-options-builder.ts:2316-2327`). The persistent file-writer URL is `/workspace/{root}` with no session segment (`ptah-mcp-slots.ts:241-266`), but the code inspected does not establish that file entry reaches `mcpServersOverride`.

The HTTP handler extracts `sessionId` from the URL, authenticates before dispatch, and replaces any body caller fields with URL-derived values (`http-server.handler.ts:414-469,510-533`). The credential registry checks token length, lookup, and exact URL binding (`mcp-caller-token-registry.ts:346-369`; `mcp-caller-auth.types.ts:105-148`). Thus a token bound to `/session/{tab}` cannot authorize a bare `/workspace` URL. A separately issued workspace token can authorize that URL but carries no session identity. The dispatcher passes `_callerSessionId` to `ptah_session_start` (`protocol-dispatcher.ts:2531`), and `guardStart` refuses absent, malformed, or inactive IDs (`session-spawner.service.ts:332-355`). `SessionId.safeParse` accepts UUID v4/v7 strings (`branded.types.ts:39-43,74-75,111`), not arbitrary tab strings. Even a UUID-shaped tab ID is insufficient after open: native sessions are stored by thread ID while `isSessionActive` checks `sessions`/`opening` keys (`codex-chat-adapter.ts:343-350,606`; `codex-chat-session-controls.ts:61-69`); `RoutingAgentAdapter` delegates to the owning adapter (`routing-agent-adapter.ts:200-204`). Native adapter already offers a trusted tab-to-live-thread resolver (`codex-chat-adapter.ts:210-227`).

**Verdict: CONFIRMED mechanism; LIKELY observed cause.** An override of `ptah` or a tab ID unresolved to a live native thread produces this refusal. The other workspace's actual override and URL were not captured, so the exact trigger is unproven. Global Codex `mcp_servers.ptah` can be loaded by Codex, but the per-thread named override is designed to replace the same-name global entry (`codex-mcp-config.ts:148-171`). If the built-in entry is omitted, a global entry may remain; source alone does not show which entry Codex connected to in the observed tab.

**Minimal fix.** Reserve `ptah` for the host in `codex-chat-host-ports.ts`, matching Claude's merge, and do not silently substitute a caller-supplied URL. Resolve the transport-authenticated tab ID to its unique live native thread ID at the session-child boundary through `codex-chat-adapter.ts`/`routing-agent-adapter.ts` and `session-spawner.service.ts`; keep the token bound to the original URL. Never accept a body-supplied parent ID. Add `codex-chat-host-ports.spec.ts` (`user ptah override cannot replace host URL or credential`) and `session-spawner.service.spec.ts` (`authenticated Codex tab routes to live thread; closed/ambiguous tab is refused`).

## B. Codex lane MCP handshake timeout

**Verified path.** Spawn gets an MCP port and issues a lane token for Codex (`agent-process-manager.service.ts:573-606,1039-1054`). The native Codex lane profile attaches `ptah` only for a valid port **and** token, using `/agent/{agentId}` and an auth reference (`codex-lane-profile.ts:128-139,161-175`). `codex-app-server-lane.adapter.ts:317-345` passes port, agent ID, token, and profile onward. `codex-lane-thread-config.ts:107-149,151-164` requires the secret and emits one `mcp_servers` table with bearer authorization; `codex-mcp-config.ts:175-201` selects this lane config in place of dotted per-server chat config. The older CLI config builder also emits a whole table **before** dotted `mcp_servers.ptah` entries (`codex-lane-config.builder.ts:131-152`). Therefore the hypothesized table/dotted collision is **RULED OUT by construction** on these paths. The HTTP handler records attachment only after an authenticated, successful `initialize` or `tools/list`, with a valid agent ID and socket local port (`http-server.handler.ts:414-469,537-550`). The process manager warns when the probe has not seen `(agentId,port)` by the adapter timeout or the 15-second fallback; it clears a warning after a late attachment (`agent-process-manager.service.ts:1454-1485`; `mcp-attachment-probe.port.ts:18`).

**Ranked causes (inferences, not observed transport logs):** (1) Codex did not perform `initialize`/`tools/list` before the 15-second probe window, especially if MCP startup is lazy. This is directly compatible with an otherwise running lane. (2) Connection/auth failure from wrong port, missing token, or URL/token mismatch: the server rejects it before observer recording (`http-server.handler.ts:414-469`; `mcp-caller-token-registry.ts:346-369`). Missing token is visibly warned and omits the server (`codex-lane-profile.ts:128-139`), so it should be distinguishable from a true handshake timeout. (3) A transport request reaches the server but initialization fails, the ID fails the observer regex, or the local port differs (`http-server.handler.ts:537-550`). (4) Codex MCP startup timing or a `startup_timeout` in external/global configuration; no lane `startup_timeout` is emitted (`codex-lane-thread-config.ts:118-164`), so its effect needs a captured Codex event. (5) Tool timeout is unlikely: `tool_timeout_sec` covers calls after attachment (`codex-lane-thread-config.ts:139-147`). (6) Dotted/table collision is ruled out as above. The warning itself proves only **no observed successful handshake**, not why.

**Minimal fix.** Add bounded, secret-free connection diagnostics (connection attempt, auth result category, initialization result, observer key, elapsed time) around `http-server.handler.ts`, `mcp-attachment-observer.ts`, and `agent-process-manager.service.ts`; align the probe deadline with the native adapter's actual startup lifecycle if it is shorter than Codex initialization. Preserve the bound `/agent/{id}` token. Add `codex-lane-activation.spec.ts` (`native lane initializes with bound token and matching observer key`) and `agent-process-manager.service.spec.ts` (`late attachment clears timeout; valid authenticated handshake prevents warning`), using their existing lane/probe mocks. A real Codex trace is still needed to pick a timing versus connection fix.

## C. Reports missing at the parent

**Verified path.** `ptah_agent_report` requires transport caller identity and chooses lane agent ID or child session ID (`protocol-dispatcher.ts:1617-1641`). A lane report uses the parent recorded at spawn; if none, it refuses (`agent-report-router.service.ts:314-343`). It enqueues to the durable parent store and drains, or sends directly when no drainer is present (`agent-report-router.service.ts:423-450`). The drainer requires `SessionId.safeParse(parentSessionId)` and `adapter.isSessionActive(id)` before delivery (`parent-delivery-drainer.service.ts:196-215`). Spawn stores the transport-derived parent (`protocol-dispatcher.ts:1273-1275,1333-1356`); `agent-namespace.builder.ts:364-380` discards body-supplied parent identity during MCP requests. Its `resolveSessionId` uses the Claude lifecycle record or returns the original tab ID (`ptah-api-builder.service.ts:769-778`), while native Codex holds sessions under thread IDs (`codex-chat-adapter.ts:606`). `resolveParentSessionId` backfills some lanes after resolution (`agent-process-manager.service.ts:2271-2304`), but this is not proof that a native tab's lane is backfilled on this path. Consequently a Codex parent stored as tab ID can remain pending or fail the active-session check. If A removes caller identity, the lane is explicitly ownerless and push reports cannot arrive (`agent-namespace.builder.ts:373-380`; `protocol-dispatcher.ts:1419-1421`). A Claude plan lane being unable to call the report tool is a separate tool-exposure issue; zero reports follows without invoking the router. A Codex lane with B cannot invoke it either.

Child-session reports select the first parseable recorded parent and require it active; they refuse instead of falling through to a later ID (`agent-report-router.service.ts:560-595`), then call `sendMessageToSession` (`:618-625`). The same first-owner rule applies to child completion (`lane-completion-notifier.service.ts:920-959`).

**Verdict: CONFIRMED ownerless behavior; LIKELY Codex tab routing defect; CONFIRMED tool-unavailability explanation for the observed zero reports.** Exact parent IDs and delivery-store states were not captured. **Minimal fix:** resolve authenticated Codex tab to unique live thread at `ptah-api-builder.service.ts`/`agent-namespace.builder.ts` before persisting parent; retain pending records while resolution is legitimately in flight in `parent-delivery-drainer.service.ts`. Avoid rerouting to unrelated sessions. Add `agent-namespace.builder.spec.ts` (`native tab resolves to thread parent; absent caller remains ownerless`), `parent-delivery-drainer.service.spec.ts` (`Codex thread receives stored report`), and `agent-report-router.service.spec.ts` (`child report reaches recorded live parent; dead parent refuses`).

## D. Late completion notices and success verdicts

**Verified path.** Completion is keyed by `agentId:completedAt`; a stored entry or in-memory `signalledKeys` suppresses duplicate signaling of the *same transition* (`lane-completion-notifier.service.ts:391-429`). `signalOnce` builds the signal, checks live parent, and may coalesce a held final report (`:445-475`); stored pending notices can later drain/replay (`:802-856`). No read-consumption operation appears on the `ptah_agent_read`/`status` dispatcher path (`protocol-dispatcher.ts:1427-1450`) or in the signal key logic. Reading a result therefore does **not** mean its eventual push notice is consumed. This explains a late notice after read without requiring duplicate completion signaling. A restarted/resumed lane with a new `completedAt` has a different key by design.

Verdict logic explicitly ignores `_reportsDelivered` (`lane-completion-notifier.service.ts:1130-1150`). A completed lane with no declared deliverables yields `unverified`; declared missing/empty/stale files yield `no-deliverable`; fresh declared files yield `delivered` even when MCP never attached or reports failed. Exit code zero is not by itself a `delivered` verdict, but it can coexist with `unverified` and with delivery despite missing MCP/report capability. The observed `no-deliverable` is correct for missing declared files.

**Verdict: CONFIRMED read/push race and verdict limitations.** **Minimal fix:** record a terminal read acknowledgment keyed to the same lane transition in `agent-process-manager.service.ts` or the parent-delivery store, and consult it in `lane-completion-notifier.service.ts` before enqueue/replay. Define whether `status` merely polls or also acknowledges; prefer `read`/`wait` acknowledging a complete result. Keep file verification independent of process exit, and surface MCP/report failure separately from artifact verdict. Add `lane-completion-notifier.service.spec.ts` (`read before delayed completion suppresses push; different terminal transition still pushes`) and `protocol-dispatcher.spec.ts` (`read/wait acknowledge exact completion key; status semantics explicit`).

## E. Parent permission when caller is unattributed

**Verified path.** `_callerSessionId` from the HTTP URL goes through `ptah_agent_spawn` into `parentSessionId` (`protocol-dispatcher.ts:1273-1275,1333-1356`). `agent-namespace.builder.ts:364-372` uses that transport ID, resolves a session, and asks `getParentLevel` only when it exists. `ptah-api-builder.service.ts:769-784` wires the Claude lifecycle lookup and `parentLanePermission`; the latter returns `plan` if an ID is provided but no trusted live level is found (`parent-lane-permission.ts:6-17`). Native Codex's `getPermissionLevel` only accepts a session/thread UUID and looks up the thread map (`codex-chat-adapter.ts:201-207`), while the MCP URL favors tab ID (`codex-chat-host-ports.ts:328-334`). Thus a tab ID not found in Claude lifecycle and not itself a native thread ID resolves to parent `plan`. If `_callerSessionId` is **undefined**, the namespace passes `parentLevel: undefined`, not the explicit fail-closed `plan`; the lane policy resolver determines the remaining default (`agent-namespace.builder.ts:369-372`; `cli-lane-policy-resolver.ts:74-96`).

**Verdict: CONFIRMED for an unresolved Codex tab ID; RULED OUT as a direct `plan` return for a wholly absent caller ID.** The observed read-only lane can be explained by the former, or by independent policy mapping owned by Phase A. **Minimal fix:** resolve the authenticated tab to a unique live native thread before permission lookup in `ptah-api-builder.service.ts`/`parent-lane-permission.ts`; do not accept a requested permission as proof of parent authority. Add `parent-lane-permission.spec.ts` (`live native tab gets live level; unknown tab remains plan`) and `agent-namespace.builder.spec.ts` (`unattributed MCP spawn cannot inherit elevated level`).

## Findings for Phase A (permission mapping)

The caller-attribution defect can cap a valid native Codex parent to `plan` before Phase A's mapping runs. Fix parent lookup first or in parallel; then inspect the resulting policy. `parentLanePermission.ts:13-17` accepts `plan`, `auto-edit`, `yolo` and returns `undefined` for other live levels such as `ask`; `cli-lane-policy-resolver.ts:74-96` applies the parent-plan cap. That behavior is a Phase A decision, not a Phase B permission change.

## Unsupported combinations / limitations

- A persistent workspace/home `ptah` MCP entry has no live session identity (`ptah-mcp-slots.ts:241-266`); session-child and parent-push tools require one. A workspace credential must not be promoted into a session credential (`mcp-caller-auth.types.ts:124-140`).
- A lane without bound token or valid port starts without attached Ptah tools (`codex-lane-profile.ts:128-139`). Direct reports cannot be expected from that lane.
- A non-UUID tab ID cannot pass `SessionId.safeParse`; a UUID-shaped tab still requires live native resolution (`branded.types.ts:39-43,74-75`; `codex-chat-session-controls.ts:61-69`).
- No observed HTTP request, Codex config snapshot, or attachment event from the other workspace was supplied. B's transport root cause and A's actual override source remain open. The repository establishes plausible mechanisms, not those missing runtime facts.

## Decisions

No product decision was taken. The recommended fix keeps caller identity transport-authenticated and resolves it through trusted live host state; it is reversible. The alternative of trusting a body or argument parent ID would defeat the URL/token binding (`http-server.handler.ts:510-533`; `mcp-caller-auth.types.ts:105-148`).
