# Startup main loop stall investigation

Scope: Electron MAIN startup on 2026-11-10 UTC. Log citations below refer to `Ptah Electron-2026-11-10.log` and `ptah-hang.log` in `%APPDATA%\Ptah\logs`. Times and line numbers only; no database opened. The release log does not contain a stack sample, so a temporal match is not proof of a particular synchronous call.

## Q1

**Answer.** The current source takes the pre-migration backup in an Electron utility process, using the better-sqlite3 online `db.backup` API there. MAIN awaits a promise returned by the worker runner; there is no synchronous IPC or `Atomics.wait` on that path. `Atomics.wait`, sync flush/stat, and backup validation run in the worker. The 17 s lag ending alongside backup completion is therefore not evidence that `db.backup` ran on MAIN. MAIN can still stall during synchronous migration SQL and SQLite auto-checkpoint before the post-migration WAL worker starts.

1. `apps/ptah-electron/src/activation/boot-heavy-services.ts:215-226` — “`await bootThothRuntime`”; persistence gate settles only after `openAndMigrate` resolves. `libs/backend/thoth-runtime/src/lib/boot-thoth-runtime.ts:213-215` — “`await refs.sqliteConnection.openAndMigrate()`”.

Correlation alone cannot assign its MAIN blockage to the worker's copy.

## Q2

**Answer.** The trigger depends only on any missing schema version, not migration size. A pending one-table migration therefore demands a full database image. Retention is count based: one pre-migration, seven daily, two reset copies, approximately up to ten database-sized copies (about 16.4 GB at 1.64 GB each) before filesystem overhead and staging. There is no age or byte cap for published backups; stale staging has an age sweep. Rotation scans and deletes asynchronously on MAIN, although filename sorting is synchronous JavaScript.

1. `libs/backend/persistence-sqlite/src/lib/migration-runner.ts:78-96` — reads applied versions, computes “`pending = sorted.filter(...)`”, and backs up when `pending.length > 0`; no SQL complexity or database-size guard.
2. `libs/backend/persistence-sqlite/src/lib/migrations/0074_review_status_sync.ts:3-17` — migration 74 creates one table and one index; `libs/backend/persistence-sqlite/src/lib/migration-runner.ts:267-286` — migration SQL and commit execute synchronously after backup.
3. `libs/backend/persistence-sqlite/src/lib/backup.service.ts:169-172` — `KEEP_BY_KIND` is pre-migration 1, daily 7, reset 2. `:295-309` — daily files go to `backups`, other kinds beside the DB.
4. `libs/backend/persistence-sqlite/src/lib/migration-runner.ts:103-108` — successful pre-migration backup is rotated immediately. `libs/backend/persistence-sqlite/src/lib/backup.service.ts:702-750` — `fs.promises.readdir`, in-memory sort, then awaited `fs.promises.unlink` for surplus files; no `readdirSync` or sync deletion in the current rotation method.
5. `libs/backend/persistence-sqlite/src/lib/backup.service.ts:720-734` — staging artifacts older than two worker budgets are swept separately; this is not an age limit for published backups.

1. Add monotonic start/end spans around `applyAll` bookkeeping, `backup()` dispatch/await, migration SQL, and auto-checkpoint state in `sqlite-connection.service.ts`, `migration-runner.ts`, and `backup.service.ts`; include MAIN event-loop delay and worker duration without paths/secrets.
2. Add spans around state-storage worker start, receipt delivery, and session-store gate in `apps/ptah-electron/src/di/phase-1-infra.ts` and its state-storage service; capture a MAIN stack sample when watchdog reports >5 s lag.
3. Move any confirmed expensive startup SQLite statement and filesystem archive scan off MAIN, preserving migration ordering, in `migration-runner.ts` and `skill-pipeline-archive.ts`.
4. **USER-RESERVED:** Decide whether to alter the unconditional full pre-migration backup policy in `migration-runner.ts`/`backup.service.ts`; skipping or changing it reduces rollback protection.
5. **USER-RESERVED:** Decide any age/byte-cap pruning or deletion of existing backups in `backup.service.ts`; this deletes recovery data. Any change to `VACUUM` policy in `migrations/0009_auto_vacuum.ts` is also reserved.

## Decisions

- No source or database file was changed, and no app/test/build was run. Only this deliverable was written.
- Treat worker backup duration and MAIN event-loop lag as separate measurements. Exact cause of first 8 s and earlier two gaps remains unproved without stack/timing evidence.
