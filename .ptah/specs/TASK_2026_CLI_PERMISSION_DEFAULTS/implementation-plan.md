## Decisions

1. **One persisted lane-default map.** Use `agentOrchestration.cliLaneDefaults` keyed by `CliType` (`ptah-cli` applies to every provider instance) with optional `{permission, network}`. The shared Zod schema uses existing mode enums and strict object keys. Omitted entries derive a built-in choice from the manifest: yolo+allow, else highest supported mode with a supported network, else `undefined` policy (native adapter default). No unsupported value is synthesized. This meets the default-auto intent where the adapter can prove full auto. Alternative: persist a copy of every default; that makes capability changes and migrations stale. Reversible: remove the map after migrating entries back to legacy keys.
2. **Legacy values migrate on read, with new writes canonical.** For Codex, if no canonical Codex entry exists, map existing `codexSandboxMode`: read-only→plan/deny; workspace-write-no-network→auto-edit/deny; workspace-write-network→auto-edit/allow; danger-full-access→yolo/allow. Preserve existing value in storage and keep legacy RPC field readable/writable for older clients; a legacy write updates canonical Codex entry, and a canonical write projects the corresponding legacy value. Do not make the two keys independent sources at spawn. The two settings must be updated in a serialized write path or rolled back on failure. For Copilot, `copilotAutoApprove=false` has no equivalent manifest mode (`ask` is unsupported at `copilot-sdk.adapter.ts:251`), so keep the bridge flag as a separate compatibility setting and apply it only where bridge permission hooks are used; do not pretend false means `plan`. Existing saved false remains effective for those hooks. Canonical lane policy governs spawn argv. Alternative: silently map false to plan/auto-edit; that changes existing approvals. Reversible: legacy fields remain readable.
3. **Precedence and cap.** Resolve each field independently: explicit `ptah_agent_spawn` arg > saved per-CLI default > built-in manifest-derived default. A provided field is never silently ignored. Validate the combined pair against the selected adapter's manifest before process creation; reject invalid pair with `UNSUPPORTED_LANE_POLICY`, including a default made invalid by a newly detected adapter version. A parent chat in `plan` caps the child at `plan`; if the adapter cannot enforce plan, refuse spawn rather than widen it. For other chat levels, keep the established lane-specific policy behavior; this allows an ordinary `ask` chat to spawn its requested autonomous lane. A plan cap also forces Codex network deny; for adapters whose plan manifest only permits allow, plan limits file mutation but cannot promise network isolation, so disclose that in UI/docs. This is a planned behavior change; verify actual parent-level propagation at the tool entry before implementation. Reversible: central resolver can be removed.
4. **UI edits defaults, capabilities still describe support.** Keep manifest detail rows; put selected values in dedicated permission/network selects for each CLI row. For unsupported/unverified cells show “Unavailable” with manifest reason. The network select is limited by both `manifest.networkModes` and `permissionModes[selected].networkModes`. Confirm yolo/full access, show the existing Codex warning language, and save only after confirmation. Alternative: turn capability badges themselves into controls; that blurs support versus user preference.
