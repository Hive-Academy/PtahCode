## Confirmed bugs and risks

1. **BUG â€” MCP approval hangs after a visible answer.** Repro: an Electron MCP `approval_prompt` arrives; click Allow on its generic card. The producer waits on `PermissionPromptService` ([approval-prompt.handler.ts:63](../../../libs/backend/vscode-lm-tools/src/lib/code-execution/mcp-core/approval-prompt.handler.ts#L63)), while the card posts `SDK_PERMISSION_RESPONSE` ([permission-handler.service.ts:433](../../../libs/frontend/chat-streaming/src/lib/permission-handler.service.ts#L433)). Electron's switch only tries Codex and SDK for that message ([ipc-bridge.ts:650](../../../apps/ptah-electron/src/ipc/ipc-bridge.ts#L650)); the MCP resolver is wired for `MCP_PERMISSION_RESPONSE` in the VS Code path ([webview-message-handler.service.ts:319](../../../libs/backend/vscode-core/src/services/webview-message-handler.service.ts#L319)). The pending MCP promise has no timeout ([permission-prompt.service.ts:128](../../../libs/backend/vscode-lm-tools/src/lib/permission/permission-prompt.service.ts#L128)). **Fix:** carry a producer type with the card and route MCP replies through an Electron MCP response handler; reject or settle on window loss.
2. **BUG â€” Copilot can wait forever after a lost prompt.** Repro: trigger a Copilot permission while the main window is absent, reloading, or closed. The bridge sets `timeoutAt: 0` and promises an indefinite wait ([copilot-permission-bridge.ts:217](../../../libs/backend/cli-agent-runtime/src/lib/cli-agents/cli-adapters/copilot-permission-bridge.ts#L217)); forwarding only logs a rejected broadcast ([agent-events.ts:561](../../../libs/backend/cli-agent-runtime/src/lib/wiring/agent-events.ts#L561)). There is no delivery result fed back to `resolvePermission`. **Fix:** make forwarding acknowledge an active renderer and deny on non-delivery; add a finite timer cleared on reply and cleanup.
3. **RISK â€” unresolved chat ownership exposes prompts on the active unrelated tab.** Repro: two chat sessions run concurrently; a request lacks a valid tab binding after resume or a session ID rotation. `routePermissionPrompt` returns an empty target list ([stream-router.service.ts:429](../../../libs/frontend/chat-routing/src/lib/stream-router.service.ts#L429)); the permission store's session predicate always returns true ([permission-handler.service.ts:187](../../../libs/frontend/chat-streaming/src/lib/permission-handler.service.ts#L187)), and the fallback card is shown when no targets remain ([permission-handler.service.ts:293](../../../libs/frontend/chat-streaming/src/lib/permission-handler.service.ts#L293)). The analogous question route documents global fallback ([stream-router.service.ts:497](../../../libs/frontend/chat-routing/src/lib/stream-router.service.ts#L497)). IDs still direct an answer to the right backend pending call, but the wrong visible session can approve it. **Fix:** require a verified owner binding for interaction; show unresolved requests in a clearly global attention surface with owner context, or deny with a finite timeout.
4. **RISK â€” lane permission ownership is indirect and can drift on resume.** The SDK lane payload drops parent session/tab IDs and keeps only `agentId` ([sdk-permission-handler.ts:352](../../../libs/backend/agent-sdk/src/lib/sdk-permission-handler.ts#L352)); renderer display relies on a separate spawn record's `parentSessionId` ([agent-monitor-panel.component.ts:723](../../../libs/frontend/chat/src/lib/components/organisms/agent-monitor-panel.component.ts#L723)). Repro: permission arrives before spawn/reparent replay, or a resumed lane is associated with a stale parent record; it buffers by agent ID, with no owner in the request to validate against the record ([agent-monitor.store.ts:1871](../../../libs/frontend/chat-streaming/src/lib/agent-monitor.store.ts#L1871)). **Fix:** include immutable parent session and lane generation in each request, validate against live lane registry before rendering and answering, and rehydrate pending prompts on resume.
5. **RISK â€” replies can disappear while UI reports completion.** Both the agent monitor panel and responder remove a prompt immediately after `postMessage` ([agent-monitor-panel.component.ts:1232](../../../libs/frontend/chat/src/lib/components/organisms/agent-monitor-panel.component.ts#L1232), [agent-permission-responder.ts:38](../../../libs/frontend/chat/src/lib/services/agent-permission-responder.ts#L38)). The RPC handler sets `handled = true` merely because an SDK handler is registered, even when the ID is unknown; the SDK handler then logs and ignores it ([agent-rpc.handlers.ts:1402](../../../libs/backend/rpc-handlers/src/lib/handlers/agent-rpc.handlers.ts#L1402), [sdk-permission-handler.ts:1124](../../../libs/backend/agent-sdk/src/lib/sdk-permission-handler.ts#L1124)). Repro: answer a stale/expired prompt after timeout or reload. **Fix:** return a consumed boolean from each pending registry, acknowledge only actual consumption, and clear the UI after positive acknowledgement or explicit expiry.
6. **RISK â€” `always_allow` can approve sibling sessions' pending tools.** The SDK handler iterates all pending request contexts and resolves every matching tool name without session/tab matching ([sdk-permission-handler.ts:1157](../../../libs/backend/agent-sdk/src/lib/sdk-permission-handler.ts#L1157)). Repro: two parallel sessions ask to run the same tool with different inputs; choose Always in one. Both unblock. **Fix:** scope the rule and sibling resolution to the intended session/workspace and tool-input policy, and make that scope explicit in the UI.
7. **RISK â€” a CLI request can be classified as unbounded chat before its agent ID is attached.** `classifyPermissionRoute` gives any UUID session/tab an unbounded wait before considering `cliAgentId` ([sdk-permission-handler.ts:883](../../../libs/backend/agent-sdk/src/lib/sdk-permission-handler.ts#L883)); the lane's resolver is attached after spawn ([ptah-cli-registry.ts:989](../../../libs/backend/cli-agent-runtime/src/lib/ptah-cli/ptah-cli-registry.ts#L989)). Repro: a tool prompt fires between SDK startup and `setAgentId` with a valid parent UUID; it goes to the chat card, potentially in another active tab, with `timeoutAt: 0` ([sdk-permission-handler.ts:931](../../../libs/backend/agent-sdk/src/lib/sdk-permission-handler.ts#L931)). **Fix:** establish lane identity before query starts, or queue prompts until the lane record is attached; prioritize explicit lane route in timeout classification.
8. **RISK â€” native Codex chat can outlive its prompt's deadline.** The presentation starts a timer only for `!routable` requests ([codex-chat-approval-presentation.ts:138](../../../libs/backend/rpc-handlers/src/lib/chat/codex-host/codex-chat-approval-presentation.ts#L138), [codex-chat-approval-presentation.ts:163](../../../libs/backend/rpc-handlers/src/lib/chat/codex-host/codex-chat-approval-presentation.ts#L163)). Repro: a valid tab owns a request, then is closed or renderer reloads before answering. The card's timeout effect may no longer run; backend pending presentation has no local timer. **Fix:** run a backend deadline for all pending approvals, tied to `expiresAt` or a configured maximum, and decline on timeout/window loss.
9. **RISK â€” ACP permission policy can select a persistent grant without user interaction.** When `allow_once` is absent and auto-approve is on, `decideAcpPermission` selects `allow_always` ([acp-permission-policy.ts:91](../../../libs/backend/cli-agent-runtime/src/lib/cli-agents/cli-adapters/acp/acp-permission-policy.ts#L91)). Repro: ACP process offers only a persistent allow. No Electron permission card appears. **Fix:** require explicit policy opt-in for persistent grants or reject/cancel that offer.

## Five logic questions

1. **Silent failure:** MCP and Copilot pending calls can remain blocked after UI delivery or response failure (findings 1â€“2); monitor replies are cleared before acknowledgement (finding 5).
2. **User action:** switching to an unrelated tab, then accepting an unresolved global fallback prompt can approve another session's call (finding 3).
3. **Input:** a missing owner ID in an MCP request or pre-attachment lane request causes global or wrong-surface routing (findings 1, 4, 7).
4. **Dependency failure:** a missing renderer causes SDK denial ([sdk-permission-handler.ts:285](../../../libs/backend/agent-sdk/src/lib/sdk-permission-handler.ts#L285)) and AskUserQuestion recommended selection ([ask-user-question.service.ts:102](../../../libs/backend/agent-sdk/src/lib/permission/ask-user-question.service.ts#L102)); Copilot has no equivalent settlement (finding 2).
5. **Missing requirement:** define owner identity and acknowledgement across process, window, session, tab, and lane generation; define deadline on close/reload/resume (findings 3â€“8).

## Tests that would pin routing

- Electron integration: MCP approval in sessions A/B, answer B while A active; assert only B's MCP promise resolves, including after renderer reload and no-window delivery.
- Concurrent SDK chat and lane requests: switch active tab, answer each card, assert each exact pending request ID and process receives its own decision; test missing/rebound tab IDs.
- Lane resume: emit permission before `setAgentId`, after resume/reparent, and after lane exit; assert the request shows only on the owning lane and settles on timeout or teardown.
- Copilot bridge: broadcast rejection, destroyed window, timeout, and duplicate/stale response each settle once and leave no pending resolver.
- Codex chat/gateway: two contexts with same native request ID, tab close, `expiresAt`, and wrong-session answer; assert the composite context/process/thread/turn request is the only recipient.
- AskUserQuestion: inactive/closed tab and renderer reload; verify owner-specific rehydration, recommended timeout, and no cross-session answer.
- SDK `always_allow`: parallel same-tool prompts in different sessions and workspaces; only the intended scope should auto-resolve.
- Remote worker: machine A/B and session A/B with reused request ID; wrong machine/session must reject, correct worker process must receive the answer. Renderer relay remains **UNVERIFIED**.

## Decisions and limits

- **Decision:** classify ownerless prompts as a routing risk even when request IDs prevent a cross-process response. Evidence: global renderer predicate and fallback above. Reversible: yes, a dedicated global attention UI with explicit owner could satisfy the intended behavior.
- **UNVERIFIED:** the full remote worker event-to-Electron renderer path, and whether unexpected native Codex lane server requests can occur under `approvalPolicy: never`. No claim of full coverage for these paths.
- No tests were run under the task's memory-safe verification rule; this is a code-path audit. No source files were edited.
