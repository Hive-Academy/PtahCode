# Claude API connection and Ptah CLI lane investigation

## Summary

- Defect A is an explicit frontend and setup-service prohibition, not an Electron capability check.
- The current Claude API wizard saves the key only while switching `authMethod` to `apiKey`.
- Defect B is an explicit dialog exclusion; the runtime also lacks a registered direct-Anthropic provider definition.
- A separate Claude API secret can coexist with subscription routing, but the wizard has no path to store it independently today.
- The smallest complete fix needs a secret-only host write and a lane provider/credential path that cannot leak the key into the main agent.

## Defect A root cause

The literal footer is in `libs/frontend/chat/src/lib/settings/providers/provider-setup-wizard.component.ts:1344`. The radio is disabled by `selectionId() === 'anthropic'` at `:1264-1266`; the default is forced to `use-main-agent` at `:2357-2365`. The catalog describes Claude API as activating the main agent at `:1652`. There is no host-capability branch in these conditions. The same Angular renderer and shared RPC path serve Electron and VS Code; `auth:setApiKey` documents shared VS Code/Electron/CLI registration in `libs/backend/rpc-handlers/src/lib/handlers/auth/api-key-methods.ts:83-89`. Thus no host presently gets this wizard choice for Claude API.

The component emits a draft with `providerId`, raw credential, scope, and activation (`provider-setup-wizard.component.ts:2376-2412`); the parent calls `state.connectProvider` (`providers-settings.component.ts:1320-1325`), which delegates to the setup service (`libs/frontend/core/src/lib/services/providers-settings-state.service.ts:554`). The service rejects `anthropic` plus `connect-only` (`libs/frontend/core/src/lib/services/providers-connection-setup.service.ts:488-506`). For other providers, it stores the key through `auth:setApiKey`, expressly because `llm:setApiKey` selects the main route (`:550-562`). It excludes `anthropic` from that write (`:550`). Only `use-main-agent` adds activation (`:653-679`): `activationAuth` sends `{authMethod:'apiKey', anthropicApiKey?, applyTo}` for `anthropic` (`:726-744`). The host writes `authMethod`, clears more-specific values, then writes the direct key via `setCredential('apiKey', ...)` (`libs/backend/rpc-handlers/src/lib/handlers/auth/connection-settings-methods.ts:156-185`); `auth:saveSettings` resets the SDK adapter (`:131-140`). It does not write `anthropicProviderId` for this route (`providers-connection-setup.service.ts:59-66,732-737`). It does not write native Anthropic model tiers (`:576-600`). Therefore finishing the current wizard changes the main agent from subscription to API billing and persists the API key in secret storage. Whether a pre-existing ambient `ANTHROPIC_API_KEY` already changes an individual user's effective route is environment-dependent and unconfirmed.

This is a deliberate guard around a **missing secret-only setup implementation**, not a fundamental inability to store a key apart from routing. `auth:setApiKey` stores per-provider keys without route changes (`api-key-methods.ts:100-126`), but the direct Claude key uses the distinct `getCredential('apiKey')` slot (`connection-settings-methods.ts:175-184`; `libs/backend/auth-providers/src/lib/auth/workspace-provider-profile-resolver.ts:571-579`). Sending `auth:setApiKey` with `provider:'anthropic'` would use the wrong slot. Git history: `git log -S "Connect only is unavailable" --oneline` returned `3c68e11fb feat(chat): mount the providers page and remove the old editors`; `git show` confirms this footer exists in that commit. The related `.ptah/specs/TASK_2026_534/task.md:18-31` and `fix-report.md:25-43` explain the virtual ID and the intentional `authMethod:'apiKey'` activation, but do not establish a product requirement that connect-only stay forbidden.

## Defect B root cause

`libs/frontend/chat/src/lib/settings/providers/add-cli-instance-modal.component.ts:35-39` explicitly excludes `anthropic` and `openai-codex`. Its options map **all connection rows**, filtered by that set, to labels (`:395-403`); it does not filter on `configured`. The same exclusion blocks submit (`:526-540`). `Claude (Subscription)` remains because its ID is `claude-cli` and its auth mode is `cli` (`:412-416`). The rows originate from `auth:getApiKeyStatus`, `auth:getAuthStatus`, and `getAllAnthropicProviders` (`libs/frontend/core/src/lib/services/providers-settings-state.service.ts:432-457`); the service prepends a separate virtual `anthropic`/`Claude API` row even when no key is configured (`:517-529`). Thus A does **not** remove B's row; B's explicit filter does. The create flow sends `{name, providerId, apiKey}` through settings save (`add-cli-instance-modal.component.ts:606-619`). Its required-key mode (`:425-429`) would require a newly typed key if the exclusion alone were removed.

The runtime independently rejects `anthropic`: `PtahCliRegistry.createAgent` requires `getAnthropicProvider(providerId)` (`libs/backend/cli-agent-runtime/src/lib/ptah-cli/ptah-cli-registry.ts:380-389`), while the shared registry says `anthropic` is a reserved **virtual** direct-auth ID absent from `ANTHROPIC_PROVIDERS` (`libs/shared/src/lib/providers/provider-registry.ts:466-475,766-771`). By contrast `claude-cli` is registered (`libs/shared/src/lib/providers/entries/claude-cli-provider-entry.ts:24-31`) and its runtime auth env is intentionally empty to use the local subscription login (`ptah-cli-registry.ts:1505-1516`). A normal lane provider needs a definition with base URL, auth env variable, protocol/proxy behavior and model tier source: the registry builds `ANTHROPIC_BASE_URL` and an auth var from the provider definition (`:1521-1528`), selects direct versus proxy by `requiresProxy` (`:1344-1356`), and persists tier mappings plus an instance key (`:391-406`). A direct Claude API definition does not exist today. The registry's fallback auth var for an unknown ID is `ANTHROPIC_AUTH_TOKEN` (`provider-registry.ts:800-802`), which is wrong for direct Anthropic API key semantics; a correct definition must use `ANTHROPIC_API_KEY` and the official endpoint. The exact supported Claude model IDs at implementation time are unconfirmed.

## Relation and data model

The main route is `authMethod` (`connection-settings-methods.ts:168-174`); the direct API key is a separate secret (`:175-184`). The frontend displays Claude API key presence from `auth:getAuthStatus.hasApiKey` without requiring it to be the active route (`providers-settings-state.service.ts:517-528`). Therefore an independently stored direct key is representable in the host data model today, but the wizard cannot create it without activation (`providers-connection-setup.service.ts:496-497,550,653-664`). The CLI agent has a different per-instance key slot, `${PTAH_CLI_KEY_PREFIX}.${id}` (`ptah-cli-registry.ts:243-254,404-406`), and currently does not fall back to the shared direct Claude secret. Changing A alone would leave B blocked by both UI and runtime; changing B alone would still require typing a separate key and adding a runtime definition.

## Fix design

1. Add an authenticated, Zod-validated secret-only RPC such as `auth:setDirectAnthropicApiKey` in `libs/shared/src/lib/types/rpc.types.ts`, `libs/backend/rpc-handlers/src/lib/handlers/auth-rpc.schema.ts` or a dedicated schema, and `.../auth/api-key-methods.ts`. It writes/deletes only `authSecretsService.setCredential('apiKey', key)`, clears check/status caches, and leaves `authMethod`, `anthropicProviderId`, adapter route, and process env untouched. Use the existing secret abstraction; never persist or log the raw key. Existing `auth:saveSettings` remains the activation path. Confirm Electron and VS Code handler registration, RPC allowlist, and surface guards before implementation.
2. In `libs/frontend/core/src/lib/services/providers-connection-setup.service.ts`, allow `anthropic` plus `connect-only` and call the new RPC for a newly typed key; reuse an already stored key without rewriting it. Keep activation last and only when explicitly chosen. In `libs/frontend/chat/src/lib/settings/providers/provider-setup-wizard.component.ts`, enable the option, default it to connect-only when a main route exists, update the Claude API catalog/footer/button copy, and preserve explicit user choice. The frontend connection row already exposes key presence (`providers-settings-state.service.ts:517-528`). Review the credentials drawer's forced activation at `libs/frontend/chat/src/lib/settings/providers/connection-drawer/credentials-tab.component.ts:82` so subsequent key edits cannot silently switch routes.
3. Add a non-`nativeAuth`, direct Anthropic **lane** definition with stable ID and official base URL, `authType:'apiKey'`, `authEnvVar:'ANTHROPIC_API_KEY'`, `requiresProxy:false`, and valid tier defaults/catalog behavior in `libs/shared/src/lib/providers/provider-registry.ts` (or an entry). Do not reclassify the virtual main-agent ID without auditing `AuthSettingsSchema`, routing, and custom-ID reservation; a separate lane ID or explicit registry lookup is safer. Update `PtahCliRegistry` to resolve that lane ID and read either a per-instance secret or, by explicit opt-in, the shared Claude API secret at spawn (`ptah-cli-registry.ts:243-265,1505-1528`). Pass the key only in the spawned lane's auth env; keep the subscription lane's empty auth env and main-agent env isolated. Update the dialog exclusion, label, key mode and create payload (`add-cli-instance-modal.component.ts:35-39,395-429,606-619`). If sharing the connection key, avoid copying it into settings or stale per-instance secrets.

Recommended product behavior: a CLI instance selected from the saved Claude API connection uses that connection's current key, with an optional explicit per-instance override. This needs a typed credential-source field or distinct create operation; the current `apiKey:string` payload (`add-cli-instance-modal.component.ts:606-619`) cannot express that choice safely. This choice is the only open product decision.

## Risks and open decisions

- A direct key inherited by the main agent or subscription lane can silently change billing. Keep `ANTHROPIC_API_KEY` out of main-agent env unless `authMethod:'apiKey'` is selected; test both active and ambient env paths (`libs/backend/cli-agent-runtime/src/lib/ptah-cli/ptah-cli-registry.ts:1508-1516`; `libs/backend/auth-providers/src/lib/auth/active-provider-resolver.ts:33-45`).
- The current direct key slot is global while route settings are scoped; connect-only should advertise that storage scope accurately (`connection-settings-methods.ts:168-185`). The UI currently requires Global setup storage (`providers-connection-setup.service.ts:496-500`).
- Decide whether CLI instances use the current shared connection key or require their own key. Shared-key use matches the dialog's “Provider connection” wording and rotates automatically; a per-instance override remains useful. This behavior is unconfirmed by existing task specs.
- Rough implementation size: 10–14 source/spec files, about 250–450 changed lines, depending on whether a dedicated lane ID and credential-source type are needed. This is an estimate, not a measured diff.
- Matching Angular skill discovery returned zero results; this investigation used repository code and native `rg`/Git reads. No build, tests, or UI rendering were performed under the read-only task contract.
