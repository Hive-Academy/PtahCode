Budget `handoff` is an advisory stage at 80% by default, or after 3 compactions; it does **not** itself auto-send the command. The auto-send waits for `limit` (100%). The budget stage only rises until reset, so a previous limit can remain with no new usage. Context-window fill is used for rotation advice, not this automatic handoff threshold (`session-budget-stage.ts:127-160`; `session-budget.service.ts:543-549`). There is no budget wall timer; `observe`, `observeLoaded`, and compaction events reevaluate the stored snapshot (`session-budget.service.ts:170-189,270-281`).

## Root cause (proven / probable)

**Proven:** The host counts idle wall time. Its warning timer can wake an idle child by sending a peer message. Its cap handler then replaces an idle child directly, even with no pending work. The existing spec asserts that replacement (`session-spawner.succession.spec.ts:254-276`). The adapter forwards the warning to `sessionLifecycle.sendMessage`, which can start a turn (`libs/backend/agent-sdk/src/lib/sdk-agent-adapter.ts:1846-1868`). The cap path calls `succeedChild`, starts a successor, and settles the predecessor as `handed-off` (`session-spawner.service.ts:2213-2249,2335-2373`).

**Probable for the reported children:** A runtime warning caused the child to call `ptah_session_handoff`, or the cap timer directly created a successor. A budget-limit command is another possible cause. The ages 553 and 663 minutes alone do not identify which path fired: the configured cap may differ from the 120-minute default, and a warning or queued turn can delay handoff. The predecessor cause and message history are needed to choose among them. This investigation did not read session data.

## Why no reason text

The renderer command is only `/session-handoff This session has used … tokens.` It gives no trigger name, threshold, or banner reason (`session-handoff-prompts.ts:30-38`). The child contract mentions both a runtime cap and a usage budget, but gives no current trigger (`session-child-contract.ts:49-51`). The runtime warning **does** name the cap and time left (`session-child-succession.ts:38-53`). A host-created successor task names `runtime cap` or `session ended`; a child-tool handoff is labelled only `child handoff` (`session-child-succession.ts:56-81`). Thus a successor that sees the slash command or contract, but no warning, cannot infer the cause from that text. A banner is UI state, not part of the successor prompt.

## Proposed fix

Use three files: `session-spawner.service.ts`, `session-spawner.succession.spec.ts`, and `session-handoff-prompts.ts` (a fourth prompt spec if needed). At the runtime warning, skip the peer send when the child is truly idle, has no running lane, and has no queued follow-up. At cap expiry, defer succession in the same state; check the cap before the next queued or new turn and hand off then. If the task is known complete, settle it as completed instead. Do not infer completion from idle alone. Preserve existing busy-turn grace and lane transfer. Make the renderer command say `Reason: session usage budget reached 100%` so the cause survives in transcript text. A host runtime warning already says its reason.

Risk: A paused child may have work that has no queued message, so ending it as completed without an explicit completion signal could lose continuation. Deferral is safer; it can leave a live child past the wall cap until a new message arrives. Check queued follow-ups through the adapter before calling it idle (`sdk-agent-adapter.ts:1887-1889`). Change `session-spawner.succession.spec.ts:254-276` to assert no successor for an idle, empty child at cap and a successor on the next message; that assertion fails before the fix and passes after. Add a prompt assertion for the reason text. No tests were run for this read-only investigation.
