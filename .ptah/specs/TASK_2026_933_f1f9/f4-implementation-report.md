## Behaviour

- **(a) Async question across turn completion:** `RuntimeContext.askAsyncUserInput` binds `AbortSignal.any([contextController.signal, asyncInputController.signal])` instead of `turnController.signal`. When the asking turn finishes (`finishActiveTurn()`), `turnController` aborts while the async question's signal stays open and `<ptah-question-card>` remains interactive in `PendingResponseRegistry`.
- **(b) Async question on context/session close and user Stop:** `RuntimeContext.close()` aborts both `contextController` and `asyncInputController`, which aborts the question signal, resolves `AskUserQuestionService` as `null` (releasing `HostAttentionCoordinator`), triggers `cleanupPendingPermissions(sessionId)` in `createCodexChatUserQuestions` to dismiss the webview card, and logs `codex-user-input-undelivered` (`cause: 'turn-ended'`) without exposing answer text. User Stop mid-turn (`RuntimeContext.interrupt`) or while idle between turns (`CodexChatSessionControls.interruptSession` -> `cancelPendingUserInput()`) likewise aborts `asyncInputController` and dismisses the pending card while keeping the native thread reusable.
- **(c) Post-turn answer delivery & UI streaming:** When the user answers after the asking turn has completed, `RuntimeContext` formats the answer (`User has answered your questions: ...`) and invokes `CodexChatAdapter.deliverUserInputAnswer`. Because no turn is active, `CodexChatAdapter` dispatches a follow-up turn on the same Codex thread via `peerQueue.send` -> `publishUntilAdmitted` -> `publish` -> `ports.publish(session.id, stream)`, streaming the follow-up turn's `FlatStreamEventUnion` events through `ChatStreamBroadcaster.streamEventsToWebview`. If the user answers before the asking turn ends, `deliverUserInputAnswer` steers the active turn via `context.steer({ text }, activeTurnId)` (falling back to a follow-up turn if `CodexRequestRejectedError` indicates the turn just ended).
- **(d) Synchronous `item/tool/requestUserInput`:** Server-initiated `onRequest` calls continue to pass `AbortSignal.any([signal, this.turnController.signal])` to `CodexApprovalBridge.handle`, so synchronous blocking questions are still aborted immediately when `finishActiveTurn()` runs at turn end.
- **(e) `HostAttentionCoordinator` resolution races:** `resolve(key, generation)` records the highest resolved generation for request keys in bounded `resolvedRequests`, `claim` rejects stale/already-resolved generations (closing pre-`observe` resolution races), `issueRequest` / `issueFailure` re-check `this.generations.get(key) === generation` immediately after `await metadata.get(...)`, and `drop(key, expectedGeneration)` only evicts matching generations so a stale lookup never evicts a newer generation or resurrects a resolved notice.
- **Second user message while an async question is pending:** Starting the next turn in `RuntimeContext.start()` calls `cancelPendingUserInput()` before issuing `turn/start`, cleanly aborting any unanswered async question card from the prior turn (and clearing `AskUserQuestionService`'s 5-minute idle auto-pick timer so a stale auto-answer cannot fire later). Any answer arriving concurrently while a session is busy or mid-admission is serialized through `CodexChatPeerQueue.send` rather than throwing `CodexChatAdapterError('busy', 'turn')`.

## Differences from the investigation

1. **No `RuntimeContext.deliverAnswer` / `activeTurnId` in `codex-context.ts`:** `investigation.md` referenced a `deliverAnswer` helper (`lines 975-998`) that switched between `steer` and `start` based on `this.activeTurnId`. In the actual codebase (`libs/backend/codex-runtime/src/lib/codex-context.ts`), the active turn field is `private activeTurn?: string`, and `askAsyncUserInput` called `deliverDenialFeedback(text, event.turnId, 'user-input')`, which strictly required `this.state === 'running' && this.activeTurn === turnId` and only called `turn/steer` (dropping post-turn answers with `turn-ended`). Implemented `deliverAsyncUserInputAnswer` with consumer handler delegation (`setUserInputAnswerHandler` / `deliverUserInputAnswer`) plus standalone fallback (`deliverDenialFeedback` when `turnId` is live, `startTurn` when idle).
2. **Host-neutral wiring without editing `apps/ptah-electron`:** `investigation.md` suggested wiring `deliverUserInputAnswer` through `CodexContextOptions` from `CodexChatAdapter.open`, while also forbidding edits to `apps/ptah-electron/src/di/codex-runtime-composition.ts`. Because `CodexChatAdapter.open` only passes an `ApprovalSink` into `ports.createScope(sink)` (composition owns `registerCodexRuntime` options), we exposed optional `setUserInputAnswerHandler` and `cancelPendingUserInput` methods on `CodexContext` (and forwarded them in `ownCodexContext`) in addition to optional `CodexRuntimeOptions.deliverUserInputAnswer`, allowing `CodexChatAdapter.open` to bind session-scoped follow-up publishing with zero `apps/*` changes.
3. **Defect F4-C (`endSessionIfTokenMatches` / `getSessionToken`) was already resolved in `CodexChatSessionControls`:** `investigation.md` proposed returning `null` from `CodexChatAdapter.getSessionToken` so `ChatStreamBroadcaster` would not close `TrackedSession` on turn 2+. In the actual codebase, `CodexChatSessionControls.endSessionIfTokenMatches` (`codex-chat-session-controls.ts:95-100`) already returns `false` with an explicit comment keeping the native thread open across turns, while `ChatStreamBroadcaster` (`chat-stream-broadcaster.service.ts:485-515`) checks `this.sdkAdapter.getSessionToken(sessionId) === null` to decide whether to emit `CHAT_SESSION_ENDED` (and `createNativeSessionControls` checks `getSessionToken(id)` for live model/effort/permission updates). Returning `null` from `getSessionToken` would have falsely broadcast `CHAT_SESSION_ENDED` after every turn and broken live session controls, so `getSessionToken` and `endSessionIfTokenMatches` were preserved as-is and verified in `codex-chat-adapter.spec.ts`.
4. **`HostAttentionCoordinator` API shape and failure-retry invariant:** `investigation.md` referred to `this.active`, `ATTENTION_HOST_EVENT`, and `resolve(kind, requestId)` / `resolveSession(sessionId)`. The actual `HostAttentionCoordinator` uses `generations`, `pending`, and `claimedAt` maps with `resolve(key, generation)`. Additionally, existing spec `drops a failure key when the host gate is off so the same generation can be retried` (`host-attention-coordinator.spec.ts`) requires unpresented `c:*` failure keys dropped internally to remain retryable at the same generation, so `resolvedRequests` specifically tracks resolved non-failure request keys while `drop(key, expectedGeneration)` guards internal drops by generation without blocking failure retries.

## Decisions

- **Two-tier abort signal for async questions (`contextController` + `asyncInputController`):** Used `contextController` for permanent context close and `asyncInputController` (resettable) for turn-level user interrupts (`interrupt`), idle user stops (`interruptSession` -> `cancelPendingUserInput`), and superseding turn starts (`start`), while keeping `turnController` scoped strictly to a single active turn (`finishActiveTurn`) so synchronous `onRequest` approvals/questions still abort at turn end.
- **Superseding unanswered async cards on next turn start:** Chose to cancel any still-pending async question when `RuntimeContext.start()` begins a new turn so a user who ignores a question card and types a new chat message does not leave a stale card open or trigger `AskUserQuestionService`'s 5-minute idle auto-pick into a later turn. Concurrent answer delivery during busy states is serialized via `CodexChatPeerQueue.send`.
- **Skills & tool availability note:** Checked available skills at task start (no backend TypeScript/Nx/tsyringe skill was present in the host skill list; MCP tools and shell commands were denied by headless permissions, so all verification was performed via static inspection of source and spec files).
