## Answers
1. **Call sites correct.** `getPtahCliLaneProvider` (provider-registry.ts:776-780) returns the lane entry for `anthropic-api`, and falls through to `getAnthropicProvider` for every other id, so other providers are unchanged. In `fetchModels`: the OpenCode branch (provider-models.service.ts:299-300) is not entered for this id. Line 396 (inside the dynamic-fetcher block) and line 401 now resolve the entry. With a null key, the `modelsEndpoint && apiKey` branch is skipped (line 407). Control then reaches persisted catalog / static fallback, so no throw. Lines 813 and 968 only read `defaultTiers` and `modelsEndpoint`. The handler sites (provider-rpc.handlers.ts:677, 723) and adapter (lane-model-listing.adapter.ts:299) only read `modelsEndpoint`, `staticModels` and `name`.
2. **Leak check: no leak.** `reapplyTiersForWarmedCatalog` returns at line 1052 unless `providerId === resolveActiveProviderId()`. That id comes from `resolveActiveAuth().providerId` (line 1184-1185), which is the main-agent provider (apiKey/claudeCli -> `anthropic`, thirdParty -> saved id). `anthropic-api` cannot be saved as a main provider because `auth-rpc.schema.ts:57,76` and `config-scope-rpc.handlers.ts:47,53` still use `getAnthropicProvider`. The env writes at lines 644-647 and 722-735 have the same active-id guard, and `scope === 'mainAgent'` is required for set. `resolveEffectiveTiers` (line 811-868) is pure: it reads defaults and does not write env. So no ANTHROPIC_DEFAULT_*_MODEL write or active-tier change for `anthropic-api`. Residual risk: if some path ever made `anthropic-api` the active id, the new lane defaults would be applied; no such path was found.
3. **Other call sites.** Remaining non-spec `getAnthropicProvider(` calls in the two libs are on main-agent auth/proxy/connection paths (auth-manager, strategies, connection-check.ts:78, config-scope-rpc.handlers.ts:47/53, provider-tier-auto-map.ts:20, auth-rpc.schema.ts). None sits on `listModels`/`getModelTiers`/`setModelTier`/`clearModelTier` for a lane id. provider-tier-auto-map.ts:20 is the auto-map helper; it is a main-agent flow and was not traced into the CLI modal (see Not checked). Line 1214 uses the literal `'openrouter'`, fine.
4. **Tests.** The service spec tests (static list for null key; default tiers; set/get/clear on the `cliAgent` scoped key) fail without the fix: `fetchModels` would throw `Unknown provider`, and `resolveEffectiveTiers` would return `{}`. The handler spec does NOT prove the fix (Defect 1). Missing cases: a handler test with the real `ProviderModelsService`; a test that `reapplyTiersForWarmedCatalog('anthropic-api')` leaves `authEnv`/`process.env` untouched while another provider is active; a test of `LaneModelListingAdapter` for `anthropic-api`.
5. **Write path.** Not touched by this diff. `ptahCli:update` -> `PtahCliRegistry.updateAgent` -> `ptahCliAgents` and `resolveEffectiveTiers` in ptah-cli-registry.ts are unchanged. The only behavioural change they see is that `ProviderModelsService.resolveEffectiveTiers`/`getModelTiers` now return lane defaults for `anthropic-api`; other providers resolve identically via the fall-through. (I relied on the implementer's trace for ptah-cli-registry.ts line numbers; I did not re-read that file.)
