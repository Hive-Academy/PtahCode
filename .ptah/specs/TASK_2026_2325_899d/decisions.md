## Design revision 2 rules (R13-R21)

These rules close review findings 13-21. Spec and prototype must agree with them.

- **R13 (invalid Setup pair).** D7 fallback to the workspace pair applies ONLY when Setup is unset. When a
  Setup pair is stored but invalid, a skills request (first run or Re-run) does not start. The previous
  result stays on screen. An error names the provider and the missing or stale part. The recovery action
  matches the cause: provider absent from the catalogue -> "Choose a provider"; stale model or only a
  provider stored -> "Choose a model"; only a model stored -> "Choose a provider"; provider not signed
  in -> "Sign in". No text may say that the workspace model was used in this case.
- **R14 (pair attribution).** Three separate records: (a) the completed Analysis pair, immutable after
  the analysis ends; (b) per skills run, one record per stage (Decision, normal model) with the pair
  attempted and the pair used; (c) the preview pair "next run will use". A Setup change or a Re-run
  never rewrites (a). The run pill shows one badge per stage when the pairs differ, one badge when they
  are equal. An after-start error names the pair of the failed stage, not the live setting. A Decision
  pair appears only when the Decision role is configured.
- **R15 (outcome contract).** The handoff contract is `item -> outcomes[]`; each outcome has `verdict`,
  `reason` and, for Install, `candidateId`. Section 12 must use this shape, not scalar `verdict` and
  `candidate`. A draft opened from a Build outcome uses the reason of THAT Build outcome at the
  generation boundary. Build intro copy: "No registry skill fits" only when the item has no Install
  outcome; otherwise "A project skill can add what the installed skill does not cover".
- **R16 (pool reachability).** One rule: under the "All" filter every candidate of the run pool is
  reachable. Item rows are the authoritative pool. An "Other candidates" section exists only for
  candidates that no item row and no verdict section shows. Under a verdict filter the section is
  hidden and one line "N more candidates - Show all" resets the filter to All. No judge and both-failed
  states have no "Other candidates" section (rows already show the pool).
- **R17 (consent parity).** Production gate, unchanged: one approval per skill that has scripts; Install
  is disabled until every such skill is approved (`stack-skill-consent.component.ts:43-48`). The mock
  shows one unchecked approval per skill, no per-script approvals, and Install disabled until approved.
  The mock is labelled a reduced depiction of the reused production component. The "Selection was
  reset" notice sits directly under the header, below Back and the heading.
- **R18 (draft protection).** Any action that replaces a draft with unsaved edits asks first: another
  row's editor, "Write a skill by hand", a per-item search that closes the editor, and a generation
  retry. While Create is busy, name and content are read-only and Create stays disabled. The "Created"
  path derives from the submitted values.
- **R19 (coverage and identity).** One coverage rule for strip, chips and rail: an item is covered when
  at least one selected skill maps to it, whatever its origin (judge, registry or manual search). A
  chip of an item whose original search failed and that a manual result covers shows both facts
  ("Covered - original search failed"). A card rendered more than once keeps one canonical selection
  key and gets a unique description id per rendering.
- **R20 (ledger and primary action).** The README proposal ledger lists every lane proposal again:
  Setup placement, atomic save and Undo, verdict layout and count rules, custom widths,
  confirm-before-replacement, run-pill layout, AA, placeholders. Navigation and invalid-pair behavior
  are requirements; only their specific controls are proposals. While a draft editor is open, the rail
  Install action is disabled with a visible reason, so consent cannot open and one primary action
  (Create) exists.
- **R21 (capture URLs).** The README lists the exact parameter keys per surface as the script accepts
  them, with one working capture URL. An unknown `surface` or `state` value falls back to the default
  and never leaves the page blank.

## Design revision 3 rules (R22-R23, user feedback D11)

- **R22 (width and density).** The skills step has no narrow centered column: its content uses the full
  width of the renderer window, with normal page padding. Install candidates are compact rows or cards:
  name, source, one-line description, covers badges and ONE line of reason; the full reason and script
  note open on demand (expand per card). Target: at 1100 px wide, 8 Install skills and 3 Build proposals
  are visible within about 1.5 window heights (window 1000 px high); at 1400 px or more the grid adds
  columns. The method banner ("Judged by AI ...") is one line by default with its details collapsed.
  The coverage strip shows at most two lines of chips by default. The selection rail stays sticky.
  Every state, count, reason and action of the earlier design stays reachable; this rule changes
  density, not content.
- **R23 (preview before creation).** The action on a Build row is "Preview draft" (not "Create
  skill..."). It opens the draft with the proposed name, the destination path and the generated
  SKILL.md content in a readable preview with an Edit toggle. The primary "Create skill" is inside that
  view only. Nothing is written to disk before "Create skill". R18 draft protection and R20 (rail Install
  disabled while the editor is open) still apply.
