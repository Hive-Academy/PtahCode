## Findings

1. **Serious — An explicit deprecation notice with “now” leaves a skill eligible for Install.** The expression expects `deprecated` immediately after the copula or `marked`. The leading branch only considers descriptions that start with `Deprecated` or `Marked deprecated`. The current classifier returns false for `This skill is now deprecated. Use the replacement.` and for the same notice with `officially`. Candidate preparation uses that flag to determine eligibility, and the heuristic fallback uses the same preparation. A matched candidate carrying either notice can therefore receive an Install recommendation in either path, contrary to task requirement 3.4. Cover an explicit notice with an intervening modifier in both paths while retaining the React API example as eligible. [skill-judge.service.ts:63](../../../libs/backend/rpc-handlers/src/lib/skills-sh/services/skill-judge.service.ts#L63) [skill-judge.service.ts:110](../../../libs/backend/rpc-handlers/src/lib/skills-sh/services/skill-judge.service.ts#L110) [skill-recommendation.service.ts:217](../../../libs/backend/rpc-handlers/src/lib/skills-sh/services/skill-recommendation.service.ts#L217)
2. **Moderate — A missing Setup model drops the saved provider and asks the user to reselect both fields.** If the user has saved OpenRouter without a model, the resolver returns `model-missing` with the saved provider. Both guidance endpoints carry that metadata, but the copy groups `model-missing` with `provider-missing`. Both render “The Setup pair is incomplete. Choose a provider and model in Settings > Background models.” The current test explicitly expects that sentence with `provider=openrouter`. The user cannot tell which field is incomplete, and the provider name is absent despite task requirement 2.8. The copy should name the saved provider and ask for a model in the first case, and identify the missing provider in the second. [safe-failure-copy.ts:83](../../../libs/frontend/setup-wizard/src/lib/utils/safe-failure-copy.ts#L83) [safe-failure-copy.spec.ts:59](../../../libs/frontend/setup-wizard/src/lib/utils/safe-failure-copy.spec.ts#L59) [workspace-llm-resolver.ts:326](../../../libs/backend/auth-providers/src/lib/auth/workspace-llm-resolver.ts#L326) [task-description.md:187](task-description.md#L187)

## Five logic questions

1. **Where could failure look like success?** The reviewed retry rejection from a previously completed run now fails in the immediate response, terminal broadcast, and reloaded state when the checkpoint still accepts finalization. The harness rejects missing results. Finding 1 remains a false success at candidate eligibility.
2. **Which user action behaves unexpectedly?** Starting or regenerating guidance with only a provider saved leaves the start error visible, but directs the user to choose both fields.
3. **Which input gives a wrong result?** The two original deprecation descriptions classify correctly. An explicit skill-self notice with an intervening adverb remains install-eligible.
4. **What happens when dependencies fail?** A pair-write rejection still reaches the normal Library and propagation pass before the supervisor observes finalization failure and clears the active run. Setup resolver failure or timeout emits fixed RPC copy. A non-Setup transport failure still reconciles through host lookup. Raw provider failure prose does not render in the reviewed bound guidance start path.
5. **What contract remains unspecified?** The tests simulate a failed pair write while the checkpoint remains writable. They establish failed reconnect state in that case. If checkpoint finalization also fails, the live terminal can report failure, but the manifest may still hold the earlier result. Recovery from simultaneous storage failures remains unverified.
