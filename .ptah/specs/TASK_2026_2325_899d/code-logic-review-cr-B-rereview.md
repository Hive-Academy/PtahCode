## Findings

1. **Serious — A deprecated candidate becomes install-eligible and breaks an existing recommendation spec.** [skill-judge.service.ts:64](../../../libs/backend/rpc-handlers/src/lib/skills-sh/services/skill-judge.service.ts#L64) requires punctuation or end of description after a leading `Deprecated`. The existing candidate named Playwright legacy has the description `Deprecated Playwright helper` at [skill-recommendation.service.spec.ts:644](../../../libs/backend/rpc-handlers/src/lib/skills-sh/services/skill-recommendation.service.spec.ts#L644). The fresh run returns `eligible: true` and fails the expectation at :747. The same shared rule removes the install restriction in heuristic fallback. In the other direction, `Marked deprecated APIs in React 19 and how to migrate them` matches the prefix branch despite referring to APIs. Preserve recognizable skill-self notices, including the production-shaped existing fixture, and cover the distinction for both judge and fallback. Task requirement 3.4 requires descriptions that mark the skill deprecated to prevent Install.
2. **Serious — A retry pair-write rejection skips durable failure settlement and post-write propagation.** [wizard-generation-rpc.handlers.ts:1406](../../../libs/backend/rpc-handlers/src/lib/handlers/wizard-generation-rpc.handlers.ts#L1406) rejects before calling `afterSettled`. The supervisor emits a failed terminal and clears its active binding at [wizard-generation-run.supervisor.ts:309](../../../libs/backend/rpc-handlers/src/lib/handlers/wizard-generation-run.supervisor.ts#L309). The retry has already reused the same checkpoint and can have recorded a successful agent outcome through :1370–1372. If the checkpoint previously held `lifecycle: completed`, a fresh `wizard:get-generation-run-state` after the retry still reports completed with the old pair because [wizard-generation-binding.ts:148](../../../libs/backend/rpc-handlers/src/lib/handlers/wizard-generation-binding.ts#L148) reconstructs state from that manifest. A previously failed checkpoint can likewise return stale settlement facts. The rejected pair write also bypasses the Library and propagation pass at [wizard-generation-rpc.handlers.ts:985](../../../libs/backend/rpc-handlers/src/lib/handlers/wizard-generation-rpc.handlers.ts#L985), even when the orchestrator wrote an agent under the harness root. The existing failure spec begins with a completed checkpoint, injects the rejection and checks only the immediate RPC and broadcast at :3075–3100. Exercise the bound lookup and write-follow-up path too. Make successful pair and lifecycle publication consistent, and preserve failed settlement and post-write work when the checkpoint is still writable.
3. **Moderate — The guidance refusal message still omits the specific Setup problem.** [safe-failure-copy.ts:43](../../../libs/frontend/setup-wizard/src/lib/utils/safe-failure-copy.ts#L43) renders the same message for every `SETUP_MODEL_INVALID` reason. The backend supplies an allowlisted cause in the Setup error message at [enhanced-prompts-rpc.handlers.ts:802](../../../libs/backend/rpc-handlers/src/lib/handlers/enhanced-prompts-rpc.handlers.ts#L802). The new store test deliberately uses the `auth` case and expects copy with that detail removed. The user can find Background models, but still cannot tell whether to sign in, update an unavailable model, or complete a partial selection. Task requirement 2.8 calls for naming the provider and the missing or stale part. Carry safe, structured reason and provider information to the view and select fixed copy there.

## Five logic questions

1. **Where can failure look like success?** The four harness methods now return failed envelopes when the runner has no payload. A retry with a failed pair write still leaves a prior completed manifest visible through the bound lookup.
2. **Which action behaves unexpectedly?** Retrying an agent after switching the Setup model can write its file, return a retry failure, and show the earlier completion and model when the bound view is reloaded. Starting guidance with an invalid Setup selection now directs the user to settings but omits the specific problem.
3. **Which input gives a wrong result?** The existing `Deprecated Playwright helper` candidate comes back eligible. API-oriented copy that starts with `Marked deprecated` can exclude a valid candidate. Item suffix collisions and duplicate `no-skill` outcomes are handled by the new validation.
4. **What happens when a dependency fails?** The runner suppresses processing for failed and absent terminals, with fixed RPC copy. A rejected Setup resolution releases the retry reservation. The rejected pair write downgrades the live terminal, while bypassing checkpoint settlement and the Library pass. Unconfirmed non-Setup guidance starts still poll the host.
5. **What contract is missing?** The retry failure spec defines the immediate reply and broadcast but leaves reconnect parity and post-write propagation untested. The deprecation table lacks a case that distinguishes a terse notice about the candidate from a leading phrase that modifies an API. The Setup tests use the real refusal code and independently check safe copy, but do not exercise provider-specific presentation in the actual page.
