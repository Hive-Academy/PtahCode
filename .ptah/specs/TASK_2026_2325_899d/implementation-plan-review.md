2. **Blocking — Generation routing metadata does not pin the provider or auth used by content generation.** `implementation-plan.md:319–325,338–340,496`. `libs/backend/rpc-handlers/src/lib/handlers/wizard-generation-rpc.handlers.ts:441–450,607–612` selects the route only when tab-bound and otherwise retains `parsed.model`. A run could show the Setup provider while querying another one, and multi-agent or resumed runs could resolve more than one pair. Resolve Setup for scoped fresh and resumed launch paths, pass the in-memory snapshot from the handler through generation options and the orchestrator to every setup content query, and keep auth out of checkpoints. Name the server-side error path and assert provider-specific auth and model at `InternalQueryService.execute` for bound and unbound/resume cases.

3. **Blocking — Guidance plan targets a deterministic team-builder service.** `implementation-plan.md:326–340,496`. `libs/backend/rpc-handlers/src/lib/skills-sh/services/project-guidance.service.ts:24–50` builds facts without a model. The setup wizard guidance operations call `enhanced-prompts-rpc.handlers.ts:401–408,773–789,807–848`. `libs/backend/agent-generation/src/lib/services/enhanced-prompts/enhanced-prompts.service.ts:394–399,1002–1035` either consumes a bound route or resolves the workspace provider with the client model. The actual guidance query would bypass Setup and putting a model in the deterministic service could change team-builder behavior. Use the existing enhanced-prompts route seam for Setup-bound requests, pin the snapshot for the applicable unbound wizard path too, and exercise generation and regeneration at the real query boundary. Retain the deterministic facts path and non-setup callers.

4. **Blocking — Global keys and the proposed commit do not provide atomic pair semantics.** `implementation-plan.md:163–167,381–398,480,546`. `libs/backend/settings-core/src/scope/workspace-scope-resolver.ts:83–105,191–201` prefers an app-scoped value when passed `true`. `libs/frontend/core/src/lib/services/providers-commit.service.ts:146–163` performs separate RPCs. Each `settings:set` accepts an unknown value at `settings-rpc.handlers.ts:216–230`. A run can read a half-written or mixed pair, including one whose two strings happen to validate together, and a failed second write can leave it durable. A single renderer commit and Undo cannot resolve this race. Preserve the chosen two keys using a pair-level backend commit with one atomic file update and a pair read from one snapshot. Validate and trim string IDs, support only complete pairs or empty/empty in the normal writer, derive invalid state for persisted partial values, and prevent standalone writes from bypassing the pair operation. Read globally with app scoping disabled. Prove no mixed pair on failure or concurrent start, and prove save, clear, Undo and restart using a fresh file-backed instance.

5. **Blocking — Setup admission cannot establish that the stored pair is usable or that the unset call stays on the workspace pair.** `implementation-plan.md:84–86,134–175,381–382`. `libs/backend/auth-providers/src/lib/auth/workspace-provider-profile-resolver.ts:505–554,581–619` can refuse a runtime, return undefined for a proxy failure, or construct a native Claude profile without checking login. Treating profile success as sign-in and all failures as signed-out gives incorrect Start/Sign in behavior. `workspace-llm-resolver.ts:118–139` can return a snapshot with no auth and ride process-wide auth, which cannot prove use of the intended workspace provider. `provider-models.service.ts:888–900,1033–1039,1058–1074` distinguishes saved tiers, effective tiers and absent catalogues.
