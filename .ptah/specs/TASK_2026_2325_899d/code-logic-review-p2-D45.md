## New findings

1. **[Minor]** `libs/frontend/onboarding/src/lib/analyze/analyze-workspace.page.ts:408-415` (stylesheet `apps/ptah-extension-webview/src/styles.css:3386,3538`) — **Sibling `Continue previous run` CTA still renders with primary styling while disabled.** Commit `801de5a14` fixed Defect 4 on `Start analysis` (`:443-450`) by binding `btn-primary` conditionally on `setupReady()`, bypassing the glass theme specificity tie where `:root[data-theme^='ptah-glass'][data-glass='on'] .btn-primary` (`styles.css:3538`, specificity `(0,4,0)`) beats `:root[data-glass='on'] .btn:is(:disabled, [disabled], .btn-disabled)` (`styles.css:3386`, same specificity, earlier source order). However, `Continue previous run` in the `@else if (interrupted())` section (`:408-415`) still uses `[ptahSetupAction]="'primaryCompact'"` (`libs/frontend/ui/src/lib/extracted/setup-action/setup-action.directive.ts:5`, statically applying `btn btn-primary btn-sm`) with `[disabled]="!setupReady()"`. Failure scenario: an unfinished analysis is detected (`interrupted() === true`) while Setup is invalid/unavailable; the page shows `"Choose a valid Setup model to start."` (`:425-432`) and natively disables `Continue previous run`, yet the button keeps the bright primary gold fill and visually looks enabled. Suggested fix: replace `[ptahSetupAction]="'primaryCompact'"` on `Continue previous run` with `class="btn btn-sm" [class.btn-primary]="setupReady()"` (or scope `styles.css:3538` with `:not(:disabled, [disabled], .btn-disabled)` so all disabled `.btn-primary` buttons in `ptah-glass` automatically receive muted disabled styling).

2. **[Minor]** `libs/frontend/onboarding/src/lib/analyze/analyze-workspace.page.ts:742-748` (template `:238-274`, `describeSetupIssue` `:81-132`) — **`setupActionError` stays stuck if Settings clears Setup onto an invalid or unavailable workspace model.** `refreshSetupModel()` clears `this.setupActionError.set(null)` only when `state.kind === 'set' || state.kind === 'unset'` (`:746-748`). Failure scenario: Setup has an invalid override (`source: 'setup'`), the user clicks `Use workspace model` and `wizard:set-setup-model` fails (`setupActionError` becomes `"Could not switch to the workspace model. Try again."`), and the user then opens Settings and clears Setup while the workspace model itself is invalid or unavailable. On return to onboarding, `refreshSetupModel()` succeeds with `{ kind: 'invalid' | 'unavailable', source: 'workspace', ... }`. Because `state.source === 'workspace'`, `describeSetupIssue()` sets `canUseWorkspace: false` (`:91`), removing the `Use workspace model` button (`:256-268`), yet `<p role="alert">Could not switch to the workspace model. Try again.</p>` (`:272-274`) remains permanently visible even though Setup is already using the workspace model and no action on the card can clear it. Suggested fix: clear `this.setupActionError.set(null)` whenever `state.kind === 'set' || state.kind === 'unset' || state.source === 'workspace'` (equivalently `!describeSetupIssue(state)?.canUseWorkspace`), which still preserves the error when a queued refresh returns the unchanged `source: 'setup'` failure.
