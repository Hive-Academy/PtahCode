# P2 code-logic review — slice A

Reviewer family: Codex (CLI lane). Implementer families: antigravity, Ollama Code, Claude.

## Verdict: REVISE   Score: 5/10

The basic selection, coverage, provenance, and draft state transitions work in isolation. The slice still loses draft edits at result replacement and makes selected or filtered skills unreachable through expected controls. These are user-facing logic gaps across otherwise usable components.

## Findings

1. **[Blocking] A successful rerun can silently discard a dirty draft.** `libs/frontend/onboarding/src/lib/proposal/stack-skill.store.ts:597` closes any non-busy draft when a recommendation result is applied, regardless of its dirty state. Open a manual draft, edit its body, then apply a successful rerun for the same analysis. The edited body vanishes. For a busy draft the result changes the judge under the live Create, and an old proposal missing from the new result can lose its preview row. The in-progress W12 caller observed during review enables Re-run with the editor open (`libs/frontend/onboarding/src/lib/analyze/analyze-skills.page.ts:317`) and applies the response directly (`:551`). Its rerun also advances the page version (`:599`), so a Create already in flight can write successfully and have its result ignored (`:698`), leaving its draft busy. Guard rerun before advancing the version and guard result replacement before changing the store. Test dirty confirmation and a rerun attempted during Create.
2. **[Major] The judged selection bar has no way to inspect or remove individual selections.** `libs/frontend/onboarding/src/lib/proposal/skill-selection-rail.component.html:31` omits the list when the layout is `bar` and responsive mode is off. The judged review uses exactly that combination at `libs/frontend/onboarding/src/lib/proposal/stack-skill-review.component.html:619`. Select a manual-only registry result and replace the query. The store retains the selection, but the previous result is missing from the visible search list (`stack-skill-review.component.ts:271` in the same directory). The bar gives only a count, so the user cannot inspect or remove that skill without reconstructing the search. The bar spec at `libs/frontend/onboarding/src/lib/proposal/skill-selection-rail.component.spec.ts:108` asserts that the list is absent. Restore a compact, keyboard-accessible selected list or disclosure with the existing remove action, and assert that a retained selection remains removable in bar mode.
3. **[Major] “Show all” leaves candidates hidden by the stack-item filter.** `libs/frontend/onboarding/src/lib/proposal/stack-coverage.ts:607` starts with the whole candidate pool and computes visibility within the active stack item. The button at `libs/frontend/onboarding/src/lib/proposal/skill-verdict-filter.component.ts:75` emits only `all`, and `libs/frontend/onboarding/src/lib/proposal/stack-skill.store.ts:605` changes only the verdict filter. With two items and a distinct Install candidate for each, select the first item and the Install verdict. “1 more candidate - Show all” appears. Clicking it hides the notice and leaves the second candidate filtered out. The filter spec at `libs/frontend/onboarding/src/lib/proposal/skill-verdict-filter.component.spec.ts:67` checks the emitted value only. Give the disclosure its own action that resets both filters, or scope its count to the candidates that changing the verdict filter actually reveals. Add a two-filter integration assertion.
4. **[Major] An Install verdict for one item can hide the rejection reason for another.** `libs/frontend/onboarding/src/lib/proposal/stack-skill.store.ts:414` treats any Install rendering as accounting for that candidate globally. `libs/frontend/onboarding/src/lib/proposal/stack-coverage.ts:570` then skips the candidate before collecting its rejections. The review renders per-item candidate assessments only for Not judged rows (`libs/frontend/onboarding/src/lib/proposal/stack-skill-review.component.html:226`). A shared candidate that is installed for one item and rejected for a second judged Build or No skill needed item keeps its Install reason and loses the rejection reason. Even a residual candidate rejected for multiple items keeps only the first rejection (`stack-coverage.ts:585` in the same directory). Render the stored rejection on each affected item's row or carry item-qualified rejection reasons into the card disclosure. Cover a shared candidate with different judgments in one fixture.
5. **[Minor] The coverage overflow control can wrap onto a third line.** `libs/frontend/onboarding/src/lib/proposal/stack-coverage-strip.component.ts:257` stops removing chips once one remains and line 272 forces at least one chip. When All skills occupies line one and a long first chip fills line two, the overflow control moves to line three. When the control is absent during measurement, the fixed width estimate can also miss the width of the rendered label. Allow zero visible item chips if needed and measure the actual overflow control, then assert the overflow control's line as well as the chip count. The geometry mock at `libs/frontend/onboarding/src/lib/proposal/stack-coverage-strip.component.spec.ts:277` gives that control a zero-width rectangle, so the current test cannot catch the wrap.
6. **[Minor] Create fills in a path when the host response supplies none.** `libs/frontend/onboarding/src/lib/proposal/stack-skill.store.ts:1011` substitutes the destination hint for a missing or blank response path, records the slug as created, and closes the draft. The normal RPC contract requires a path. A malformed success receipt would display an unconfirmed Created path and discard the user's edits. Require a nonblank receipt path before recording completion and preserve the draft on an incomplete receipt. The current spec at `libs/frontend/onboarding/src/lib/proposal/stack-coverage.spec.ts:786` explicitly expects the substituted path.

## Five logic questions

1. **How can it fail silently?** Draft or Create state can be replaced while the new result renders normally. A response with no created path can resemble a successful create. See findings 1 and 6.
2. **Which user action is surprising?** “Show all” can make the explanation disappear while a candidate remains hidden. Searching again can strand a selected candidate outside the visible cards. See findings 2 and 3.
3. **Which input gives a wrong answer?** One stable candidate ID with different item-level assessments loses rejection provenance during global grouping. See finding 4.
4. **What happens when a dependency fails?** Matching draft-generation failure tokens enter the editable evidence fallback, superseded tokens are ignored, and matching Create failures keep the form. A malformed success receipt bypasses that protection. See `libs/frontend/onboarding/src/lib/proposal/stack-skill.store.ts:880`, `:954`, and finding 6.
5. **What implicit case needs coverage?** Test an accepted recommendation response racing an open editor and test rejections for a candidate that has a positive verdict elsewhere. Both need representative state across components rather than independent widget assertions. See findings 1 and 4.

- Kept W12 wiring out of the slice verdict. The options were to count the incomplete caller wiring as a Slice A defect or report it as an integration dependency. The active W12 assignment and its explicit call-site contract support the latter. Reversible after W12 lands.
