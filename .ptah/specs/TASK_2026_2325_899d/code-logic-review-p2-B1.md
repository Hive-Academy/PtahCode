# P2 code-logic review — slice B1
Reviewer family: antigravity (CLI lane). Implementer families of this slice: codex.

## Verdict: REVISE   Score: 5/10

Score rationale: The atomic single-`wizard:set-setup-model` call structure, `commitSeq` gating for out-of-order successful receipts, explicit empty-pair clear / Undo to `committed === null`, safe fixed-copy error handling, `source: 'setup' | 'workspace'` recovery attribution, and `'setup'` deep-link routing are sound (above 3–4). However, a Blocking singleton stale-receipt defect breaks Setup state and Undo after an external change (such as the Analyze page's "Use workspace model"), and two Major defects expose a misleading Undo action on rejected saves and drop the latest failure under overlapping saves (below 7–8).

## Findings

1. [Blocking] `libs/frontend/core/src/lib/services/providers-settings-state.service.ts:264-282` (and `libs/frontend/core/src/lib/services/providers-commit.service.ts:94-102`) — Stale `setupReceipt()` overrides fresh `wizard:get-setup-model` reads after external Setup changes — `ProvidersSettingsStateService` and `ProvidersCommitService` are root singletons. After any local Setup write in Settings, `commits.setupReceipt()` stays non-null for the rest of the session. Every later `refreshSetupModel()` (including reopening Settings after `analyze-workspace.page.ts:738` clears Setup directly via `wizard:set-setup-model`, or after an external settings edit) executes `if (receipt) return { ...receipt, state }`, keeping the old `receipt.committed` even when the fresh `state` contradicts it (e.g. `state.kind === 'unset'` paired with `committed: P1`, or `state.kind === 'set'` paired with `committed: null`). Meanwhile `commitSetupPair()` (`providers-commit.service.ts:99-100`) prefers `previousReceipt.committed` over `loadedPair`, and `setupUndoEntry`/`setupCommit` stay populated. As a result, after saving `P1` in Settings, clicking "Use workspace model" on the Analyze page, and returning to Settings: (a) the Setup picker seeds the deleted `P1` (`provider-consumer-rows.ts:280-281`, `provider-consumer-assignments.component.ts:841`) and shows "Clear" instead of "Use workspace model" (`:307-331`); (b) the stale `"Saved P1... [Undo]"` notice remains visible; and (c) saving a new pair `P2` captures the deleted `P1` as `priorPair` instead of `null`, so Undo restores `P1` instead of clearing back to Unset (`committed === null`). — Suggested fix: Track `latestCommitSeq` separately from the cached committed pair in `ProvidersCommitService`; in `refreshSetupModel()`, always derive `committed` from the fresh `wizard:get-setup-model` `state` (`set` -> `state.pair`, `invalid`/`unavailable` with `source === 'setup'` -> `{ provider: state.provider ?? '', model: state.model ?? '' }`, otherwise `null`) while keeping `commitSeq` as the monotonic floor (`receipt?.commitSeq ?? 0`). When a non-superseded read settles (matching `store.generation` and no Setup write in flight) and its derived state/committed diverges from the last receipt, sync `ProvidersCommitService`'s baseline and clear stale `setupUndoState` and `setupCommitState` without lowering `latestCommitSeq`. Add a spec in `providers-settings-state.service.spec.ts` covering local Set -> external Clear (`unset` read) -> refresh -> Save `P2` + Undo back to `committed === null`.

2. [Major] `libs/frontend/chat/src/lib/settings/providers/provider-consumer-assignments.component.ts:410-433` — Stale `Undo` button renders inside `invalid`/`failed` Setup alerts and reverts an earlier valid commit — Outside the popover (`activeEditId() !== 'setup'`), the `Undo` button at `:420` is gated only on `@if (state.setupUndoEntry())`, not on `setupCommit.status === 'saved'`. When a user saves a valid pair `P1` (`setupUndoEntry` holds `{ targetPair: null, committedReceipt: P1 }`), then opens the Setup popover, attempts an invalid pair `P2` (`setupCommit` becomes `{ status: 'invalid', message: 'Choose an available provider and model for Setup.' }`, leaving `setupUndoEntry` intact), and closes the popover, the row renders the error alert `"Choose an available provider and model for Setup."` with an `Undo` button right beside it. Clicking `Undo` does not undo or dismiss the rejected attempt; it reverts the earlier valid `P1` commit back to Unset. The same mismatch occurs after a failed subsequent save or while `'saving'`. — Suggested fix: Gate the outside-popover `Undo` button on `setupCommit.status === 'saved' && state.setupUndoEntry()` (if retry-Undo after a failed Undo is desired, track that explicitly instead of showing Undo on failed new saves), and clear transient `invalid`/`failed` Setup commit feedback when the user cancels/closes the Setup popover after a rejected draft.

3. [Major] `libs/frontend/core/src/lib/services/providers-commit.service.ts:121-132,146-155` — `reportFailure` silently drops the latest overlapping save's failure when an earlier in-flight save commits first — `writeSetupPair` records `startSeq = this.setupReceipt()?.commitSeq ?? 0` at dispatch and only sets `invalid`/`failed` in `reportFailure` when both `request === this.setupRequest` and `(this.setupReceipt()?.commitSeq ?? 0) === startSeq`. If Save 1 (valid `P1`, `request = 1`, `startSeq = 1`) and Save 2 (invalid `P2`, `request = 2`, `startSeq = 1`) overlap and Save 1 resolves first (`commitSeq = 2`), then when Save 2 fails with `SETUP_MODEL_INVALID` or a transport error, `request === this.setupRequest` (`2 === 2`) is true but `commitSeq (2) !== startSeq (1)`, so `reportFailure` silently swallows the failure. `setupCommit()` remains `{ status: 'saved', message: 'Saved P1...' }` with no indication that the latest save (`P2`) failed. The reverse case (Save 2 commits first, then Save 1 fails) is already blocked by `request === this.setupRequest`. — Suggested fix: Remove the `=== startSeq` check in `reportFailure` (or track `latestReceiptRequest` and suppress failure only when `latestReceiptRequest > request`, never when an older request committed earlier). Add a unit test in `providers-commit.service.spec.ts` for Save 1 succeeding before overlapping Save 2 fails with `SETUP_MODEL_INVALID`.

4. [Minor] `libs/frontend/chat/src/lib/settings/providers/provider-consumer-assignments.component.ts:199,334,411,739-741,832-843,896-902` — Setup trigger cell and `toggleEdit` do not check `setupCommit().status === 'saving'`, allowing reopen during save that leaves stale draft open and hides saved/Undo feedback — `busy()` only checks `assignmentSaving() || feedback.saving()`. While a Setup save is in flight, `consumer-edit-setup` is neither `aria-disabled` (`:199`) nor guarded in `toggleEdit()` (`:839`). Closing and reopening the Setup popover during a slow save resets `currentDraft` to a new object holding the pre-save `row.provider`/`row.model`; when the save resolves `accepted === true`, `this.currentDraft() === draft` (`:899`) is `false`, so `cancelEdit()` is skipped. Because `:334` omits `'saved'` inside the popover and `:411` requires `activeEditId() !== 'setup'`, the popover stays open with stale pre-save draft values while the `'saved'` confirmation and `Undo` button are completely hidden. — Suggested fix: Guard `toggleEdit('setup')`, `[attr.aria-disabled]` on the Setup cell, and the deep-link effect (`:721`) for `'setup'` with `setupActionsDisabled()` (or `state.setupCommit().status === 'saving'`).

5. [Minor] `libs/frontend/core/src/lib/services/providers-settings-state.service.ts:255,1100-1114` — `commitHooks.sectionsReady()` omits `this.setupModel()` — `refresh()` calls `this.refreshSetupModel()` (`:255`) during every post-commit refresh, but `commitHooks.sectionsReady()` (`:1100-1113`) checks only the other 11 sections. If `wizard:get-setup-model` fails after a Providers commit (e.g. changing main-agent provider/model or deleting a key), `commit().refreshFailed` stays `false` and omits the partial-refresh warning (the Setup row itself still renders its inline `consumer-reload-setup` Retry UI). — Suggested fix: Include `this.setupModel()` in `commitHooks.sectionsReady()`.

## Checked and OK

- **One atomic `wizard:set-setup-model` per action (`providers-commit.service.ts:142-145`, `provider-consumer-assignments.component.ts:317,327,398,426,857-867,886-903`):** Provider-only and model-only picks in the Setup popover stay local (`onDraftChange` skips `saveDraft` for `'setup'`); `Save` is disabled until both `provider` and `model` are non-empty (`setupDraftComplete`); `Save`, `Clear`, `Use workspace model`, and `Undo` each issue a single `wizard:set-setup-model` call (never two `settings:set` calls).
- **`commitSeq` ordering on successful out-of-order receipts (`providers-commit.service.ts:157-165`):** Older receipts with `receipt.commitSeq < currentCommitSeq` return `false` without mutating `setupReceiptState`, `setupUndoState`, `setupCommitState`, or calling `applyReceipt`. Superseded in-flight `refreshSetupModel()` reads are discarded by `store.generation++` in `setupReceiptHandler()` (`providers-settings-state.service.ts:303-306`).
- **Clear = explicit empty pair & Undo verification (`providers-commit.service.ts:104-113,144,166-173`):** Clearing or Undoing to Unset sends `{ provider: '', model: '' }`; Undo verifies `committed === null` when `targetPair === null` and exact `provider`/`model` equality otherwise, reporting `status: 'failed'` on mismatch while still applying the newer receipt as the sequence floor.
- **No raw provider errors in UI (`providers-commit.service.ts:133-155`, `providers-settings-sections.ts:18,129`, `provider-consumer-rows.ts:335-383`):** `SETUP_MODEL_INVALID` maps to fixed text (`'Choose an available provider and model for Setup.'`); other RPC/thrown failures map to fixed copy; `setupModelIssue()` uses fixed templates by `cause` and `source` without surfacing raw error strings.
- **Row order, unsupported providers, and `source: 'setup' | 'workspace'` recovery (`provider-consumer-rows.ts:21-43,76-79,249-383`, `agents-routing-settings.component.ts:145-151,186`):** Setup is first (`4 roles`), uses `CURATOR_UNSUPPORTED_PROVIDER_IDS` (excluding Codex and provider sessions), names all four setup operations in `helperCopy`, uses `"Workspace model: ..."` and `"Following workspace"` only when unset or `source === 'workspace'`, offers `"Use workspace model"` only when `source === 'setup'`, and routes `'sign-in'` directly to `setupProviderRequested` without opening the Setup picker.
- **Deep link `'setup'` (`settings.component.ts:71-78,335-365`, `agents-routing-settings.component.ts:34-35,190-195,229-263`, `provider-consumer-assignments.component.ts:710-737,876-885`):** `'setup'` routes from both `'providers'` and `'orchestration'` to Providers -> `AgentsRoutingSettingsComponent`, waits for the Setup row to load, opens the popover, focuses `consumer-edit-setup`, and consumes the target once applied; requests carrying `providerId` give precedence to the provider sign-in wizard without opening a competing popover.
