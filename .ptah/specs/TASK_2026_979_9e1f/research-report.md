# Research Report - TASK_2026_979 (issues #1466, #1468, #1469 + MCP gateway)

Base: worktree `mcp-connector-parity`, read-only. Paths below are relative to the repo root. Verified = read the source. Inferred = reasoning, not run. Nothing was built or tested.

## Answer (verdict)
All three bugs come from the same cause. Connector (OAuth + Smithery) overrides are computed in one private method of `ChatSessionService`, and only the `chat:start` / child / handoff launch path calls it. The resume path, the slash-command path and the cron one-shot path never receive overrides. #1469 is a separate defect in harness-sync's MCP retirement/ownership logic. Fix #1466/#1468 with one shared port in `agent-sdk` that resolves connector overrides for every query builder. Fix #1469 in `harness-sync`.

## A. Where overrides are computed and where resume drops them (#1468)
- Compute: `libs/backend/rpc-handlers/src/lib/chat/session/chat-session.service.ts:1002-1031` (`buildMcpServersOverride`). It merges Smithery, then OAuth, then the caller's overrides. Resolvers are built lazily and privately at `:885` (Smithery) and `:929-943` (OAuth: `createMcpOAuthTokenStore` over `authSecretsService` + `McpOAuthInstalledManifestStore` + `McpOAuthService`).
- Used once: `launchSdkSession` `:1872-1874`, then `config.mcpServersOverride` `:1907`. `launchSdkSession` serves `chat:start`, child sessions (`:1661` passes `undefined`, but `launchSdkSession` still rebuilds the overrides) and handoff (`:1769`). Those paths are fine.
- Resume branch (the bug): `chat-session.service.ts:3599-3620` builds an `AgentSessionResumeConfig` with no `mcpServersOverride`. The type `libs/shared/src/lib/types/agent-adapter.types.ts:254+` has no such field (the start config has it at `:238`). `SdkAgentAdapter.resumeSession` config type `sdk-agent-adapter.ts:1430-1445` has none either. Its `executeQuery` call `:1605-1621` omits it, while `startChatSession` passes it at `:1145`.
- It becomes `mcpServersOverride` undefined in `session-query-executor.service.ts:1472` and `:1727`, then `[]` in the log at `sdk-query-options-builder.ts:1603`. The log reads `isResume: true, mcpOverrideKeys: []`, matching the issue.
- Also affected, same cause: slash-command resume `chat-slash-command-router.service.ts:340-353` (config) and `:421` (`executeSlashCommand`), which pass no override. The gateway bridge resume (`libs/backend/gateway-chat-bridge/src/lib/gateway-chat-bridge.ts:849`) is not inspected. Likely also affected, unverified.
- Subagents: inferred. SDK subagents run inside the parent CLI process and use its `mcpServers`, so they inherit whatever the resumed process got. Fixing resume fixes them. CLI lanes (`claude-cli.adapter.ts`) use the shared builder but nothing passes overrides to them. Unverified, see G.
- Minimal fix (smallest): in the resume `prepare` closure (`chat-session.service.ts:~3585-3620`) add `mcpServersOverride: await this.buildMcpServersOverride(undefined)`. Add `mcpServersOverride?` to `AgentSessionResumeConfig` (shared) and to the `resumeSession` config type. Forward it at `sdk-agent-adapter.ts:1605`. Do the same in `chat-slash-command-router.service.ts:340`. Codex/provider-session hosts already strip it (`codex-chat-profile-options.ts:22`, `provider-session-chat-options.ts:36`), so no change there.
- Better fix (all paths, recommended): define an optional DI port `SDK_TOKENS.SDK_MCP_CONNECTOR_OVERRIDES` (`buildOverrides(): Promise<Record<string, McpHttpServerOverride>>`) in `agent-sdk`. Implement it in `cli-agent-runtime`, next to the resolvers in `mcp-directory/`, by moving `chat-session.service.ts:885-943` + `:1002-1031` there. `SessionQueryExecutor.executeQuery` (`:1455-1476`) calls it when `config.mcpServersOverride` is undefined and merges with caller-wins. Start, resume, slash and cron then share one computation. Dependency direction is fine: `cli-agent-runtime` depends on `agent-sdk`, as `job-runner.ts:41` shows for the cron lib.
- Caller-wins today: `mergeMcpOverride` `sdk-query-options-builder.ts:2466-2481` keeps `ptah` from the base. The map shape is `{type:'http',url,headers:{Authorization:'Bearer ...'}}` (`mcp-oauth-override-resolver.ts:65-69`). Tokens are fresh per query (`getFreshAccessToken`, refresh at near-expiry). A resumed session has a new CLI process, so it needs a fresh token anyway.

## B. Scheduler (#1466)
- Interactive vs cron: interactive goes `ChatSessionService` -> `SdkAgentAdapter` -> `SessionQueryExecutor` -> `SdkQueryOptionsBuilder.build` (overrides merged at `:1684`). Cron `JobRunner.dispatch` (`libs/backend/cron-scheduler/src/lib/job-runner.ts:285-295`) calls `InternalQueryService.execute` -> `SdkQueryRunner.runOneShot`. `InternalQueryConfig` (`internal-query.types.ts:33-120`) has no override field. `execute` (`internal-query.service.ts:115-135`) passes only `mcpServerRunning`/`mcpPort`.
- One-shot MCP map: `sdk-query-runner.service.ts:693-705` -> `buildOneShotMcpServers` (`:840`) -> only `ptah`. `settingSources` is `['user','project','local']` (`:744`) and there is no `strictMcpConfig` for `toolAccess:'claude-code'` (`:241` is only the isolated variant). So the CLI loads workspace `.mcp.json` itself, finds unauthenticated `zernio`, and reports "needs authentication". That is the observed failure.
- Why connectors are skipped: no code in the one-shot path ever calls the resolvers (they live only in `ChatSessionService`). Not a token-access issue.
- Tokens: encrypted provider-key slots via `authSecretsService` (`chat-session.service.ts:931-937`), manifest in `McpOAuthInstalledManifestStore`. The scheduler runs in the same Electron main process (`JobRunner` is DI-resolved in the host; Electron path inferred from `apps/ptah-electron/src/di/phase-2-libraries.ts` listing). So it can read them. Verified for the secret service; process identity is inferred.
- Minimal fix: use the port from A in `SdkQueryRunner` one-shot options (`:693`, only when `toolAccess !== 'none'`). Merge it with the `ptah` entry before `filterMcpServersByPolicy`. Keep `ptah` winning (`mergeMcpOverride` semantics). Do not add it for lanes like `memory-curator`/`skill-synthesis` unless wanted. Add an opt-in `includeConnectors?: boolean` to `InternalQueryConfig`, set by `JobRunner` only. This avoids sending connector bearer tokens into background pipelines that process untrusted text. That is a security-relevant choice, so it is flagged under decisions.
- Run status: `job-runner.ts:196-211` marks `succeeded` for anything that does not throw. The stream loop `:300-321` only throws on `error_max_turns` / `error_during_execution`. A "needs-auth" MCP server never surfaces.
- Signal: yes. The SDK `system`/`init` message carries `mcp_servers: [{name,status}]` (read at `stream-transformer.ts:783,796-803`, documented in `session-mcp-status-callback-registry.ts:8`). `msg.type==='system' && msg.subtype==='init'` is available in the `for await` loop at `job-runner.ts:300`. Statuses such as `failed`/`needs-auth` are the failure signal. The exact status enum was not verified against the installed SDK d.ts (unknown, see below).
- Recommended: always append `MCP unavailable: zernio(needs-auth)` to the run `summary` (non-breaking). Failing the run, or `skipped`, is a behaviour change. Offer a per-job `requiredMcpServers: string[]` (needs a schema/store change in `types.ts` + `job.store.ts`) that makes the run `markFailed` when one is not `connected`. Decision for the user.

## C. Merge and URL dedup
- Merge points: (1) interactive `mergeMcpOverride` `sdk-query-options-builder.ts:2466`, called at `:1684`, filtered by policy `filterMcpServersByPolicy`. (2) one-shot `sdk-query-runner.service.ts:693`. (3) file-based servers (`.mcp.json`, user settings) are loaded by the CLI subprocess through `settingSources` (`builder :1631-1663`, `runner :744`), invisible to both builders. That is why `zernio` from `.mcp.json` and the connector coexist.
- Proposal: a pure helper `dedupeMcpServersByUrl(base, overrides, fileServers)` plus `normalizeMcpUrl` (lowercase host, drop default port, trailing `/`, `#fragment`; keep path and query; strip userinfo). Put it in `libs/backend/agent-sdk/src/lib/helpers/` beside `redact-mcp-url.ts`. Call it from both `mergeMcpOverride` and the one-shot builder so start/resume/cron share it.
- To dedupe against `.mcp.json` the builder must read it: reuse `cli-agent-runtime/src/lib/mcp-directory/claude-user-mcp.reader.ts` (verified to exist; its fitness for `.mcp.json` is not checked) or a small reader in `agent-sdk`. Then, for each file entry whose normalized URL equals a connector URL, emit the connector under the file entry's key. Connector wins.
- Whether an SDK `mcpServers` option entry of the same name beats the `.mcp.json` entry is NOT verified. That is the key unknown. Fallback: pass the file key in the SDK `disallowedTools`/server deny path (`filterMcpServersByPolicy` + `capabilityFlags.deniedMcpServers`, `builder :1684-1700`). `strictMcpConfig: true` would also work but drops all the user's other `.mcp.json` servers: behaviour removal, user-reserved.

## D. Harness sync (#1469)
- Trigger: `SessionQueryExecutor.syncHarnessToPolicy` (`session-query-executor.service.ts:1912-1927`) calls `HarnessPolicySync.apply(policy.physicalRoot, fingerprint)` (`agent-sdk/src/lib/harness/harness-policy-sync.ts`) -> `HarnessPreflight`. This runs at every session start, so the child session in the new worktree is a fresh workspace root.
- Writers: `libs/backend/harness-sync/src/lib/targets/mcp/mcp-facet-planner.ts` (plan/apply), `json-mcp-facet.ts` (atomic write + `.bak`, header doc `:1-20`; `copyFileSync` import at `:23`), `codex-toml-mcp-facet.ts`. Manifest: `manifest-store/managed-manifest.ts:110` -> `{ws}/.ptah/harness/<target>.manifest.json`.
- Why `.vscode/mcp.json` zernio is removed: the manifest in the worktree owns the key, and the desired state no longer wants it (retirement), so `applyRetiredMcpRemoval` (`mcp-facet-planner.ts:253-330`) deletes it. The only guards are "entry hash equals manifest hash" and `git ls-files --error-unmatch` = untracked (`retirement-proof.ts:183-215`, probe wired at `claude-target.ts:129`). In a worktree copy where the file is tracked this should return `git-tracked` and keep it. The report shows it removed, so either the file was untracked there or the probe ran with wrong cwd. I could not determine which (see Unknowns). The repointed `ptah` URL in `.agents/mcp_config.json` is the `ptah` key written on spawn as ephemeral (`PTAH_SPAWN_MCP_KEY`, `mcp-facet.port.ts:81`). Whether the harness manifest builder or `antigravity-cli.adapter.ts:1170-1215` wrote the workspace file is not determined. The adapter doc says home `~/.gemini/config/mcp_config.json`.
- Ignore status: this repo's `.gitignore` ignores `.mcp.json` (`:51`), `.vscode/mcp.json` (`:117-118`) and `*.bak` (`:228`). It manages only `.github/skills/` in the `# ptah:harness:begin/end` block (`:231-235`). `.ptah/harness/*.manifest.json` is not ignored by this repo's `.gitignore` (grep found no rule; `.ptah/specs/**/*.log` and `.ptah/tmp/` only). Other user repos' ignores are unknown. The managed block in `gitignore-writer.ts` covers skill dirs only.
- Safest fix, in order: (1) in a git worktree (cwd where `.git` is a file), have the MCP facet and manifest store skip writing and retiring entries in config files that are git-tracked; do not remove user entries there. Reuse `probeGitTracking` for writes as well as for removals. (2) Add `.ptah/harness/` and `*.bak` for MCP config backups to the managed ignore block (`GITIGNORE_BEGIN/END`, `gitignore-writer.ts:43-44`). Or write to `.git/info/exclude`, which needs no tracked-file edit. (3) `git update-index --skip-worktree` is rejected: it hides real user changes. Option (1) is smallest and does not remove capability. Option (2) alters user `.gitignore` (the writer already has an opt-out `harness.manageGitignore`).

So the `ptah` entry is already injected at spawn for every lane. Only user-installed servers and connectors are file-based or Claude-only. Gemini CLI as a separate provider was not found in `cli-adapters/`; only agy.

Gateway judgement (the `ptah` server proxies connectors, one entry per provider):
- Exists: per-lane/session auth tokens (`lane-mcp-credentials.ts`, `IMcpCallerCredentials`, `sdk-query-runner.service.ts:840-860`); a caller-identity URL scheme (`/session/{id}`, `/agent/{id}`, `/workspace/{root}`, `ptah-mcp-url.ts:48-60`); a tool profile/policy layer (`mcp-core/mcp-tool-profile.ts`, `mcp-caller-policy.ts`, `effective-tool-list.ts`); the token holder with refresh (`McpOAuthService.getFreshAccessToken`) and the HTTP override map shape.
- Missing: any upstream MCP client or tool proxy in `vscode-lm-tools/.../mcp-core` (no connector forwarding found in `protocol-dispatcher.ts` by grep); tool namespacing (`oauth-mcp_zernio_com-mcp__*` is today generated by the Claude CLI, not Ptah); `tools/list_changed` (no hits in `mcp-core`/`mcp-http`), needed when a connector is connected or revoked mid-session; per-caller connector scoping in the policy layer.
- Risks: it makes Ptah's MCP server a confused deputy for bearer tokens (every lane credential then reaches the user's connectors); needs per-lane allow-lists; handling of upstream auth expiry and elicitation; streaming/long calls and timeouts (codex uses `tool_timeout_sec`); tool-name length and collisions across providers; a larger effect on the Claude path, where the SDK currently shows connector status in `mcp_servers`. It would remove file-based writes for connectors but not for user-installed servers, so it does not alone fix #1469.
- Verdict: feasible and architecturally aligned (the spawn-injection point exists everywhere), but it is a new proxy feature, not a bug fix. Do not couple it to these three fixes.
