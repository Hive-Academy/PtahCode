## Findings

1. **Major — Interrupted recovery can still send a chat prompt without project guidance after a load failure.** On a reloaded post-install interrupted run, click **Continue without attachments**. The page clears the attachment warning, retries the record, and awaits `loadReview()`. If recommendations fail or the guidance call rejects, `loadReview()` finishes after clearing facts and leaves no successful guidance result. If the guidance call resolves with an error, it sets `guidanceLoaded` to true and keeps the facts empty. In all three cases, `continueInterrupted()` can proceed to `launchChat()`, which checks loading and attachments and clears the review error before dispatch. The installed recovery button also calls `launchChat()` directly. Keep post-install recovery actionable after a failed load and require a successful, current-record guidance response before dispatch. A successful response with zero facts is valid. Add cases for an unsuccessful guidance response and a rejected guidance call, and assert that neither sends chat. `libs/frontend/onboarding/src/lib/proposal/team-builder-start.page.ts:442,494,502,507,520,644,674,690,768` and `libs/frontend/onboarding/src/lib/proposal/team-builder-start.page.html:213`.

2. **Major — Retrying an interrupted record before the cancellation reply arrives silently drops confirmed installed skills.** Start installing in A, switch to B, then return to A and click **Continue** while the install reply is pending. Invalidation clears the install ID, issues the cancel request and interrupts the record. The page retries the same ID, and the store immediately changes it to `needs-input`. A later valid reply carrying A's workspace and a nonempty `installed` array still reaches `recordStoppedInstall()`, but its status gate discards the confirmed writes. The backend may already have written those skills and the UI will omit them. Reconcile stopped attempts by install attempt and record, or hold same-record retry until that attempt has settled. Cover switch away, return, retry, then settle. Preserve the new attempt's status and prevent the old attempt from launching chat. `libs/frontend/onboarding/src/lib/proposal/team-builder-run.coordinator.ts:656,667,764,888,897`, `libs/frontend/onboarding/src/lib/proposal/team-builder-start.page.ts:746`, and `libs/frontend/setup-wizard/src/lib/services/setup-run.store.ts:448,470`.

3. **Minor — The existing global cap can still evict an indexed live record's sidecar checkpoint.** Stale pruning preserves entries for records present in the store. The next step unconditionally evicts the oldest entry when the global sidecar exceeds 20. With one `needs-input` team-builder record in each of 21 workspaces, the oldest live record can lose persisted selection, owner decision and attachment-warning metadata on reload. The Setup index cap is per workspace. This was possible before Batch 18B and is separate from the stale-entry defect. If the live-record retention invariant also applies under genuine capacity pressure, test 21 indexed live entries and retain their metadata in the Setup index or protect live entries from the sidecar cap. `libs/frontend/onboarding/src/lib/proposal/team-builder-run.coordinator.ts:1594` and `libs/frontend/setup-wizard/src/lib/services/setup-run-persistence.ts:25,255`.
