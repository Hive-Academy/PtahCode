### Decisions on the deferred items

1. **Finding 11 · Major · Workspace pinning is an approval dependency.** Start a two-skill install in A and switch to B while the first install awaits I/O. The consent handler captures A for selection and propagation, then awaits an installer that independently resolves the active root for each skill. The next iteration can write to B while selection and propagation still target A. The switch assigns B on the backend, even if the renderer has already stopped this execution or discarded the reply. After an observed switch the renderer leaves `installCompleted` false and starts no chat. A successful reply alone still cannot certify which workspace received each write. The backend changes the root before the renderer updates its workspace, and the ordinary success path checks only the renderer root before setting the checkpoint. There is a second attribution gap if the user Cancels before switching. Cancel removes the execution from the map, so the root observer cannot flag the later switch on that execution. The late handler checks the cancelled record's path against the execution's path, which can still let it credit A with names written in B. See `proposal/team-builder-run.coordinator.ts:479,499,661,726,766`, `libs/backend/rpc-handlers/src/lib/handlers/setup-rpc.handlers.ts:1425,1438,1454,1513,1527`, `libs/backend/rpc-handlers/src/lib/handlers/skills-sh-rpc.handlers.ts:432,450`, `libs/backend/rpc-handlers/src/lib/handlers/workspace-rpc.handlers.ts:389`, and `libs/frontend/core/src/lib/services/electron-layout.service.ts:546,564`. **Fix.** Land the backend follow-up as a dependency or gate availability of installation on a workspace-pinned RPC. Pass a validated originating workspace through each installer invocation and return confirmed effects for that workspace. Make backend cancellation stop remaining skills at a safe boundary and report any already-installed skills. Test a real two-skill handler sequence with the first install paused, switch workspaces before releasing it, and assert write destinations as well as the renderer outcome. This is reversible at the release gate.
2. **Finding 12 · Batch 16 field forwarding can be deferred for the tested recovery path.** Batch 15's `SetupRunStore.report` delegates field application to `applyReportFields`, which still replaces the team-builder payload with only intent and installed names. The revised sidecar preserves the four optional fields during partial saves and repeated renderer reloads with writable localStorage. Forwarding the fields into the index can consolidate the persistence path later. The sidecar has a 20-entry cap and silently falls back to memory if storage fails, so the round 2 result is specific to retained entries with working storage. Finding 14 is a hydration defect independent of either storage format. See `libs/frontend/setup-wizard/src/lib/services/setup-run.store.ts:349`, `libs/frontend/setup-wizard/src/lib/services/setup-run/setup-run-record.ts:29`, and `proposal/team-builder-run.coordinator.ts:302,1357,1371`.

### Five logic questions

1. **Silent failure.** A late successful install response can mask a split-workspace write, and a same-renderer remount can hide an empty attachment tray. See 11 and 14.
2. **Unexpected user action.** Cancel followed by switching workspaces can still let the backend install into the new workspace. A switch past chat dispatch instead leaves the sent conversation in its original workspace when the send succeeds.
3. **Valid input with a wrong result.** A draft with `hadAttachments: true` and empty attachment arrays represents lost payloads after reload. Hydration treats the existence of that draft as sufficient to clear the warning.
4. **Dependency failure.** The tested prompt/send failures keep installed evidence and return the active run to review. A background close refusal bypasses the API's safety checks, and an aborted renderer wait cannot stop backend disk writes. See 11 and 15.
5. **Missing case.** The suite needs both kinds of re-entry (fresh renderer and new page with the existing coordinator), plus a handler-level test for workspace change between two physical skill installs.

4. **Major — Record selection lets users bypass the one-live-run rule and detach from their own new run.** The URL id wins over both the locally started id and the workspace’s live run (`proposal/team-builder-start.page.ts:107–129`).
