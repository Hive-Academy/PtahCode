REVISE

1. **Blocking — Reviews list disappears behind a false modal.** `libs/frontend/review-runs-ui/src/lib/components/review-runs-page.component.ts:226-238` embeds `ptah-review-run-detail` in the detail pane, but the child still declares `role="dialog" aria-modal="true"` and traps Tab/Escape (`review-run-detail.component.ts:11-13,83-95`). Every run selection focuses its heading and tells assistive technology that the concurrently visible repository and run panes are outside a modal. Tab from the last detail control is forced back inside; keyboard users cannot reach the adjacent panes until Close. Minimal fix: provide an inline rendering mode for the detail component that removes modal semantics, focus trap, Escape-to-close, and forced focus; use that mode in the inbox host, retaining its existing modal mode elsewhere.

2. **Serious — Pagination can corrupt the refreshed list and cursor.** `libs/frontend/review-runs-ui/src/lib/review-runs.store.ts:106-132,136-160,164-221` allows `loadMore()` to overlap `load()` (including a refresh-triggered load). If the first-page load settles first, the old page appends to the new list and then assigns its old `nextCursor`; if it settles last, it discards the page, while the page result may still leave an inconsistent cursor. A refresh can therefore show stale/extra runs, repeat pages, or skip pages. Minimal fix: increment a list generation at each first-page load, capture it and the cursor in `loadMore`, and ignore page results unless both still match; serialize or invalidate overlapping first-page loads as well.

3. **Serious — Users can get stuck before a matching page.** `libs/frontend/review-runs-ui/src/lib/components/review-runs-page.component.ts:179-223` renders Load more only when `filteredRuns().length > 0`. With a repository, state, or search filter that has no matches in the first 100 runs, the page shows “No matching runs” with only Clear filters even when `nextCursor()` is non-null. Matching runs on later pages are unreachable. Minimal fix: keep Load more available in the no-match branch, or paginate until a match or the cursor is exhausted. Clarify that search applies to loaded runs if that remains the intended behavior.

4. **Serious — A pending remove confirmation can switch machines under the user.** `libs/frontend/machines-ui/src/lib/components/machines-view/machines-view.component.ts:235-240,275-283,317-326` keeps `confirmingRemove` while `selected()` silently falls back to `machines[0]` if the selected ID vanishes after a store update. The confirmation dialog receives the new machine (`:166-180`), so its Remove button can remove a different machine than the one originally confirmed. The narrow detail stays open because `detailOpen()` is driven by `narrowDetailOpen` (`:248-250`), making this switch especially unobvious on a narrow screen. Minimal fix: when the selected machine disappears, cancel confirmation and clear action state before showing the fallback machine; bind confirmation to a specific machine ID and reject removal if it no longer matches.

5. **Moderate — Review run listbox uses all buttons as Tab stops.** `libs/frontend/review-runs-ui/src/lib/components/review-runs-list.component.ts:34-44,96-105` marks every row `role="option"` but never assigns roving `tabindex`. Every run is individually tabbable; Arrow keys merely move focus to a neighboring row and do not wrap or handle Home/End. In addition, `libs/frontend/review-runs-ui/src/lib/components/review-repositories.component.ts:35-63` has a listbox of option buttons with no Arrow/Home/End handling at all. This does not meet listbox keyboard behavior and becomes onerous with up to 100 runs. Minimal fix: use a single roving Tab stop, support Arrow/Home/End and selection through keyboard in both lists, or use ordinary list/button semantics instead of listbox/option. The `button[ptahInboxRow]` role assignment is in `libs/frontend/ui/src/lib/surfaces/inbox-row.directive.ts:22-29`.

6. **Moderate — Machine list focus can jump to the wrong row after filtering.** `libs/frontend/machines-ui/src/lib/components/machine-list/machine-list.component.ts:195-196,213-240,242-265` stores the focused *index* across changes to `visibleRows`. If the query removes earlier rows while that index remains in range, the single `tabindex=0` moves to a different machine. If the focused row disappears, the browser focus falls off the list. Minimal fix: track the focused machine ID, derive its current visible index, and focus a stable fallback after the filtered DOM changes.

7. **Moderate — Detail drawer styling is only partly neutralized.** The host selectors in `libs/frontend/review-runs-ui/src/lib/components/review-runs-page.component.ts:227-229` do match the real `ptah-review-run-detail > div > aside` structure in `review-run-detail.component.ts:11-12`: they remove `fixed`, `absolute`, backdrop color, max width, border, padding, shadow, and aside background. They leave `z-50`, `inset-0`, `w-full`, and `overflow-y-auto` on the former drawer and do nothing to the child's modal focus behavior. The confirm dialog at `review-run-detail.component.ts:65` is a sibling of the aside and keeps its own fixed overlay and focus handling (`review-confirm-dialog.component.ts:6-9,34-47`); that dialog remains functional, but the outer inline “modal” stays exposed beneath it. Minimal fix: render a real inline detail variant with ordinary section semantics and scrolling owned by the inbox pane; keep the confirm dialog as the only modal when invoked.

8. **Minor — New pagination dedupe is incomplete.** `libs/frontend/review-runs-ui/src/lib/review-runs.store.ts:148-154` builds `known` only from existing runs. Duplicate `attemptId` values within one returned page both pass the filter, producing duplicate `@for` keys (`review-runs-list.component.ts:35`). Minimal fix: add each accepted page ID to `known` while filtering.
