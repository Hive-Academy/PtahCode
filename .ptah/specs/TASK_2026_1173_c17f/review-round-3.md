# Review round 3

**Verdict: major issues remain.** The normal 257th-child path emits a failed card, and both focused suites pass, but the claimed isolation of limited children and canonical early-event linking does not hold for existing spawn/thread hints.

## Findings

1. **Major — confirmed by reading code.** `libs/backend/codex-runtime/src/lib/codex-context.ts:492-503,617-629,743-782`. `thread/started` still links a child to the sole pending spawn, and a later `toolStarted(spawnAgent)` links every matching `pendingChildParents` entry. Either link flushes `earlyChildEvents` immediately under the spawn tool id. The native activity arrives later and relinks to `cardToolCallId`, too late for already emitted events. The new test at `codex-context.spec.ts:514-536` installs `pendingSpawns` directly and calls `bufferEarlyChild` directly, so it never exercises `thread/started` or `toolStarted`. **Fix:** defer tentative spawn links for native-capable child threads until activity admission, or keep buffered events until the canonical card id is known; test notification order `thread/started → child event → spawn start → activity`.

2. **Major — confirmed by reading code.** `libs/backend/codex-runtime/src/lib/codex-context.ts:601-603,492-520,811-821,834-875`. `limitMessage` suppresses only the new `linkNative` call. A limited child can already be in `childTools` through `thread/started`/spawn, or be self-linked by the fallback at line 520 when a spawn is pending. Its own events then emit under that link rather than remaining buffered and dropped. Because it has no `nativeChildren` entry, a root completed terminal sees it as a nonnative child and sets `rootTerminalPending` for up to 30 seconds; its later terminal follows the nonnative branch and can settle that wait. **Fix:** record limited thread ids separately, block all speculative linking for them, and remove any tentative link on overflow; ensure root settlement ignores limited ids. Cover both prelinked and self-linked overflow sequences.

3. **Major — confirmed by reading code.** `libs/backend/codex-runtime/src/lib/codex-context.ts:693-711,720-733`; `libs/backend/agent-sdk/src/lib/codex-app-server/codex-chat-events.ts:388-401`; `libs/frontend/chat-streaming/src/lib/native-codex-status.reducer.ts:16-20,34-39`. A limited `started` is not remembered, so a duplicate `started` repeats the warning and failed status. If another child has meanwhile become evictable, the duplicate is admitted as a normal `child:1` cycle and SDK emits `running` for the same card. The reducer rejects that nonterminal status because the existing `child:1` card is failed; SDK now has an unresolved native card and may wait for its terminal. Later `interacted`/`completed` while still limited are dropped as unknown child (`codex-context.ts:695-699`). **Fix:** retain bounded limited-child identity/deduplication state through the turn, consistently discard or reconcile later activity, and avoid transitioning an already failed cycle to a tracked pending cycle. Test duplicate started before and after capacity changes, plus later interacted/completed.

4. **Minor — speculative impact, mapping behavior confirmed by reading code.** `libs/backend/codex-runtime/src/lib/codex-context.ts:671-682`. History mapping uses `cycles[childId][turn index] ?? state.cycleId`. An unmatched turn is therefore assigned the current cycle without evidence of that association; depending on history ordering, its terminal status could make the current cycle evictable. **Fix:** leave unmatched turns unmapped (or derive a verified turn-to-cycle association) and only set `lastTerminalKey` from a turn explicitly mapped to the current cycle. Test histories with more child turns than recorded started/interacted activities.
